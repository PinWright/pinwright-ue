# Lessons

- When adding error checking to previously-unchecked code paths (e.g., checking TryCreateConnection return values), expect previously-passing tests to fail. These are real bugs being exposed by better error handling, not test regressions. Investigate each failure to determine if the production code has a bug (fix it) or if the error is cosmetic/expected (downgrade to warning).
- BPIR compiler had a systemic issue: TryCreateConnection failures at ~10 call sites were never checked, meaning broken Blueprint wiring was reported as successful compilation. Always check connection return values in Blueprint graph manipulation code.
- BPIR parser's `FindMatchingParen` pattern requires an `else` error branch — 5 instruction types (cast, make/break, subsystem, sequence, make_array) silently accepted unmatched parentheses. When using find-then-process patterns, always handle the not-found case with an error.
- BPIR decompiler silently dropped entire code paths when entry point types were unrecognized. Always add orphan-detection post-passes after graph walks to catch unreachable nodes.
- K2Node_BpirExpression (UK2Node_Composite) works in cooked builds — it generates standard K2 nodes in a subgraph via FBpirSubgraphCompiler, which compile to normal BP bytecode. The node class and BpirText are stripped at cook time. The editor-only plugin must be present during cooking but not at runtime.
- UObject::Rename() with a hardcoded name fatally asserts when another object with the same name exists in the same Outer. Always use MakeUniqueObjectName() when renaming UObjects to a fixed base name.
- When compile errors cross the MCP boundary, generic messages like "Could not resolve value X" cause misdiagnosis — the caller blames the tool instead of their input. Always include diagnostic context (what was searched, what class was checked, actionable suggestions like "check 'Is Variable' in Designer") in errors returned to MCP callers.
- UK2Node_FunctionResult::AllocateDefaultPins() relies on the compiled UFunction existing in GeneratedClass. Before blueprint compilation, newly created FunctionResult nodes get only an exec pin — no return value data pins. When creating FunctionResult nodes during BPIR compilation, discover return value pins from the FunctionEntry node's actual pins as a fallback.
- Widget "Is Variable" in UMG requires BOTH `UWidget::bIsVariable = true` AND a GUID entry in `WidgetBlueprint->WidgetVariableNameToGuidMap`. Setting only the GUID map (via `OnVariableAdded`) is insufficient — `PopulateBlueprintGeneratedVariables` checks `bIsVariable` first. Setting only `bIsVariable` without the GUID entry means external references fail. Use `EnsureWidgetVariableGuid()` / `RemoveWidgetVariableGuid()` from WidgetAuthoringUtils for the GUID side, and set `bIsVariable` directly on the widget.
- When using `FindPin(const TCHAR*)`, be aware it calls `FName(InPinName, FNAME_Find)` which returns `NAME_None` if the FName hasn't been registered in the global name table. This silently fails for dynamically created pins on K2Nodes like `UK2Node_FormatText`. Use `FindPin(FName(...))` with default `FNAME_Add` semantics, or iterate `Node->Pins` directly and match by name string instead.
- When creating widget variables programmatically, set both `Widget->bIsVariable = true` AND register in `WidgetVariableNameToGuidMap` via `OnVariableAdded`. `OnVariableAdded` only does the GUID map registration — you must set `bIsVariable` separately. Without `bIsVariable`, `PopulateBlueprintGeneratedVariables` skips the widget during Kismet compile, so no FProperty is generated.
- When filtering UFunctions by flags, `HasAnyFunctionFlags(FUNC_A | FUNC_B)` uses OR semantics (any flag matches). Use `HasAllFunctionFlags(FUNC_A | FUNC_B)` when you need both flags set simultaneously — e.g., `FUNC_Static` AND `FUNC_BlueprintCallable` for the broad function search cache.
- When configuring UK2Node_BaseAsyncTask subclasses, use `UK2Node_AsyncAction::InitializeProxyFromFunction(UFunction*)` — the public API. Do not attempt to set `ProxyFactoryFunctionName`/`ProxyFactoryClass`/`ProxyClass` directly, as they are protected on `UK2Node_BaseAsyncTask`. Cast to `UK2Node_AsyncAction` first (not `UK2Node_BaseAsyncTask`).
- When extracting a repeated code pattern into a helper function, search for ALL instances of the pattern in the file — not just the ones you are currently working on. Missing instances leads to inconsistent code (some call sites use the helper, others still have the inline version).
- When resolving a `UEnum*` by short name (e.g. `EDoorState`), do NOT use `FindObject<UEnum>(nullptr, shortName)` — `nullptr` outer restricts the search to the root package and misses enums in game/plugin packages. Use `FindFirstObjectSafe<UEnum>(*name, EFindFirstObjectOptions::None)` first, which searches all loaded packages. This is the pattern `CodePinResolver.cpp` already uses consistently; `MakePinType` in `BlueprintHandlerUtils.cpp` still tries `FindObject` first and falls back to `FindFirstObjectSafe`, meaning short enum names silently fail the first lookup before recovering on the fallback.
- When splitting a sequential loop into multiple phases (e.g., entry setup → skeleton recompile → emit/wire), any state registered in early phases that gets cleared between phases (like PinResolver registrations) must be generically re-registered in the later phase. Type-specific re-registration (e.g., only handling CustomEvent and Function entry kinds) misses other entry types with output pins (builtin events with DeltaSeconds, component events with OtherActor, macros with input params). Use a generic approach: cache the entry node pointer and re-register all non-exec output pins.
- When `CreateUserDefinedPin` is called with `PC_Wildcard`, the pin is silently dropped during `ReconstructNode`. Always verify that `ConvertCppTypeToPinType` / `MakePinType` produces a concrete type (e.g., `PC_Real`, `PC_String`, `PC_Object`) before the pin is created — a Wildcard output means a type name was not recognized by the converter.
- There are two pin type converters: `ConvertCppTypeToPinType` (used by the BPIR compiler) and `MakePinType` (used by RPC handlers such as `blueprint_add_event`). When adding support for a new type, update **both** converters. If only one is updated, pins silently become Wildcard in the other path and are dropped by `ReconstructNode` with no compile error reported.
- When refactoring a single-pass compiler into multi-phase (Phase 1: setup, Phase 2: emit), audit every call to state-resetting functions (like SwitchToGraph) in the new phase boundaries. State set in Phase 1 may be cleared by Phase 2's graph-switch calls. Save all mutable compiler state in a per-block state struct (FBlockSetupState) and restore after graph switches — SetEmitMap must come after SwitchToGraph, and CurrentMacroExitTunnel must be restored from saved state.
- When parsing dot-separated reference chains like `%ref.PinName.Property`, split on the LAST dot (FindLastChar) not the first (FindChar) to correctly separate the object path from the leaf property name. Single-dot cases are unaffected, but multi-dot chains through cast result pins (e.g., `%castResult.AsBPGameInstance.MissionIsJustOpened`) require the full intermediate path in TypeArg.
- Before proposing new BPIR language features, check the existing [language reference](wiki-src/bpir.md) — `forEach`, `foreach_break`, `while`, `switch`, and many other constructs already exist. The decompiler may not round-trip them perfectly, but the compiler supports them. Proposing a feature that already exists wastes time and risks creating duplicates.
- When a compile RPC reports success but the containing Blueprint still shows errors in the BP editor, the failure is at BP compile time, not at the IR compile time. BPIR (and similar IRs) only create graph nodes; UE's Kismet compiler validates them against the class afterwards. Always surface `UBlueprint::Status` and `FCompilerResultsLog` entries in the RPC response — never trust a bare "compiled: true" from an IR compiler. Callers must check the BP compile status too.
- When comparing Blueprint pin signatures for equality (custom events, function parameters), compare every field of `FEdGraphPinType`: `PinCategory`, `PinSubCategoryObject`, **`ContainerType`**, and — for maps — `PinValueType`. Omitting `ContainerType` treats `int` and `TArray<int>` as the same signature, producing a silent wrong-type bug where duplicate-rejection or replace-mode logic mismatches actual pin shapes.
- When adding new mutating RPC handlers, always wrap the mutation section in `FScopedTransaction`. Place it after validation, before first mutation. Without it, blueprint recompilation creates `REINST_` class instances that the `UTransBuffer` holds stale references to, causing PIE ensures in `CheckAndHandleStaleWorldObjectReferences`.
- When adding behavior that should apply to all return paths in a multi-branch resolution function, consolidate early returns into a single variable first, then apply the transformation once at the end — don't duplicate the check at each return site. This avoids missed branches when new resolution paths are added later.
- Historical split-test-module checkouts only: when a separate `PinWrightTests` module needs symbols from private headers, mark only those symbols with `PINWRIGHT_API`. In the current tree, tests live under `Source/PinWright/Private/Tests/` and compile into the main module DLL, so most test helpers should stay internal; LNK2019s are usually non-exported UE/editor symbols or missing module dependencies, not a test DLL boundary.
- When debugging UE property crashes (`FClassProperty::Identical`), check if the wrong property handler ran due to inheritance — `FClassProperty` inherits `FObjectProperty`, so `CastField<FObjectProperty>` matches both. The debugger showing `ObjectA` as a `UBlueprint` instead of `UClass` is the telltale sign. Fix: check `FClassProperty` before `FObjectProperty` in the handler chain.
- When implementing undo for UE editor operations: (1) `MarkBlueprintAsStructurallyModified` goes INSIDE `FScopedTransaction`, not outside — skeleton regen doesn't flush undo. (2) Use `GEditor->UndoTransaction()` not `Exec("Undo")`. (3) `Transaction.Cancel()` doesn't reverse `NewObject` creation — use manual cleanup (e.g., `RemoveWidgetSubtree`) for error rollback.
- When working on the BPIR node layout engine, read BlueprintAssist's source on disk before reimplementing layout behaviour — it lives at `Plugins/BlueprintAssist/Source/BlueprintAssist/Private/BlueprintAssistFormatters/` as full readable C++ (not a DLL). The load-bearing files are `EdGraphFormatter.cpp` (3439 lines — `FormatY_Recursive`, the collision loop, same-row marking) and `EdGraphParameterFormatter.cpp` (1789 lines — pure-cluster layout, pin-anchor alignment for pure-above-consumer placement). Our FormatY invariants (direct-parent-skip, no slide-right) come from BA — diverging from its pattern tends to produce diagonal drift or cluster overlaps that look like "layout bugs" but are really missing guards.
- When resolving a widget-variable `FObjectProperty` on a `UBlueprint` during BPIR compilation (e.g. in `CreateComponentEventNode` or similar handlers that read `$WidgetName`), query `SkeletonGeneratedClass` first and only fall back to `GeneratedClass`. `widget.import_xml`'s `MarkBlueprintAsStructurallyModified` regenerates only the skeleton; a pre-existing Blueprint with sibling bindings will have a stale `GeneratedClass` until a full compile runs. Skeleton-first is safe because, by UE's compile invariant, the skeleton class is always a superset of the generated class during authoring — any variable on `GeneratedClass` is also on `SkeletonGeneratedClass`, but not vice versa.
- When a BPIR keyword name differs semantically from the underlying K2 pin it maps to (`event:` → `Delegate`, `target:` → `Target`), `Arg.PinName.Equals(..., ESearchCase::IgnoreCase)` only covers case variance — it does NOT cover the rename. Always add an explicit second branch for the semantically-renamed keyword (e.g., check both `"Delegate"` and `"event"`). Writing the same string twice with `IgnoreCase` is a smell — if both comparisons are spelled identically, you've missed the real rename. Pattern surfaced in the `bind_dispatcher` event-arg pre-scan, where checking only capitalized K2 pin names stripped the `event:` binding silently.
- When doing large-scale renames of automation test category strings across many files, always empirically grep each file for `IMPLEMENT_*_AUTOMATION_TEST` macros with `output_mode: "content"` before editing — file names frequently do not match the actual category prefix in use. A recent refactor found several mismatches where the plan table (built from filename conventions) missed outliers: `TestBlueprintGraphOrphan.cpp` used `OrphanDetection.*` (not `BlueprintGraphOrphan.*`), `TestLevelSaveLoadUtils.cpp` used `LevelUtils.*` (not `LevelSaveLoadUtils.*`), `TestMakePinType.cpp` used `BlueprintUtils.MakePinType.*` (not `MakePinType.*`), and `TestCodeFunctionResolverSafety.cpp` mixed `Compiler.Resolvers.*` and `State.PluginState.*` prefixes. For bulk rename passes, always discover the true prefix per file empirically before applying `replace_all`; verify macro count == new-prefix count per file after editing.
- When emitting a struct break in the BPIR compiler, always emit `UK2Node_BreakStruct` — do NOT redirect to `UK2Node_CallFunction(BreakVector/BreakRotator/etc.)` based on the struct's `HasNativeBreak` metadata. `UK2Node_BreakStruct` already expands to the engine's native-break path internally at compile time, so the redirect gives zero runtime benefit and breaks BPIR round-trip: the decompiler's `EmitBreakStruct` only recognizes `UK2Node_BreakStruct`, not the function-call form. Let the engine handle native routing.
- When iterating placed obstacles in the node layout engine's collision loop (e.g. `ResolveConsumerClusterOverlaps` in `NodeLayoutEngine.cpp`), cache each placed cluster's bounds once in a parallel `TArray<FSlateRect>` instead of recomputing via `GetCurrentClusterBounds` inside the inner loop. `GetCurrentClusterBounds` runs `EstimateNodeSize` on the consumer and each placed pure node, iterating all pins and measuring text widths via Slate — recomputing in the inner loop is O(N² × iter × P) Slate measures. Placed consumers are never moved by later consumers, so bounds are stable after placement; caching drops cost to O(N × P).
- When finding a node's input or output exec pin, use `UEdGraphSchema_K2::FindExecutionPin(Node, Direction)` (engine helper, `EdGraphSchema_K2.h`). Do NOT start with `FindPin(PN_Execute, …)` and assume it works — macro nodes like `ForEachLoop` expose their input exec pin under the macro's entry tunnel name (typically `"Exec"`), so `PN_Execute` misses them. `FindExecutionPin` iterates pins and matches by `IsExecPin` + direction, which is the right primitive for nearly every "find the then/exec pin" case.
- UE has two visually similar but distinct enum types: `EFieldIteratorFlags` (used with `TFieldIterator<T>` templates) and `EFieldIterationFlags` (used with the 3-arg `FindFProperty` overload in `UnrealType.h`). They are not interchangeable; mixing them compiles only in one direction. Always check the header of the API you're calling — the 3-arg `FindFProperty` overload takes `EFieldIterationFlags`.
- `FindFProperty` / `FindPropertyByName` do NOT traverse the parent class chain for delegate and multicast-delegate properties by default — pass `EFieldIterationFlags::IncludeSuper` explicitly. Omitting it causes bugs where an inherited delegate (e.g. `UCommonButtonBase.OnClicked` on a derived widget) silently returns null, and code paths that depend on it (like `InitializeComponentBoundEventParams` for BndEvt nodes) fall into broken fallback branches with `DelegateOwnerClass` set to the wrong class.
- `FindFirstObjectSafe<UEnum>` / `FindFirstObjectSafe<UClass>` alone does not reliably find project-module types (e.g. `/Script/MyGame.EDoorState`) by short name — it works for engine types but misses plugin/game module types. Always add a `TObjectIterator` fallback matching `GetName()` OR `CppType` when short-name resolution must cover non-engine modules. `ResolveUClass` and `ResolveUEnum` both follow this 3-tier pattern: full-path load → fast short-name lookup → iterator fallback.
- The RPC transport implements a response-only timeout: when the timeout fires, the game-thread handler keeps running to completion and its work commits. There is no cancellation mechanism. Any write-side RPC handler must therefore be idempotent — if a client retries after a timeout, the second call must produce the same final state as a single successful call, not accumulate duplicate work. `compile_bpir`'s default `"append"` mode was changed to upsert semantics specifically for this reason.
- `IMPLEMENT_SIMPLE_AUTOMATION_TEST`'s third argument is a flag mask. The correct constant for editor-side tests in this plugin is `EAutomationTestFlags::EditorContext | EAutomationTestFlags::ProductFilter`. Do NOT use `ApplicationContextMask` — it is a mask of all context flags and does not compile as a standalone identifier in UE 5.6. Copy the form from adjacent test files rather than guessing.
- `FAutomationTestBase::TestEqual` has no `UObject*` overload in UE 5.6 — passing `UObject` pointers invokes the `FUtf8StringView`/`FStringView` overload and fails to convert. Compare pointers via `TestTrue(What, A == B)` or cast both sides to `void*`. This affects any equality assertion on resolved `UClass`/`UEnum`/`UObject` pointers.
- When a UE function has both a sync UFUNCTION and an async K2Node form, BPIR's plain `call FunctionName(...)` resolves by parameter-name matching and usually picks the K2Node async-action return (a `UAsyncAction_*` object) instead of the intended sync widget/value. To get the spawned widget reference, call `K2Node_AsyncAction_<Name>` explicitly, use its exec-pin branches (e.g. `AfterPush`), and read the widget from `%action.UserWidget`. Applies to `PushContentToLayerForPlayer` and any other function with an async K2Node override.
- For cross-widget handler discovery in BPIR, the canonical pattern is `GetAllWidgetsOfClass → foreach(FoundWidgets) → cast<Handler_C>(ArrayElement) → call Method(Target: %c.AsHandler)`. The cast result accessor uses the class name with underscores removed from the suffix: `W_SaveHandler_C` → `.AsWSaveHandler`. Use this when the widget has no direct variable reference to a sibling handler.
- BP functions with spaces in their name require backtick quoting in BPIR at both declaration and call sites: `` call `Set Error`(Target: ...) ``. Plain unquoted names fail the parser (splits on the space token); double-quoted names fail the resolver (quotes become part of the resolved name). The decompiler always emits backticks for spaced names, so round-trip output is always canonical. The space-stripped fallback (`SetError`, `Set_Error`) works only when no ambiguity exists.
- When scanning a Blueprint's graphs for event-like entry nodes (bound events, widget events, component events), cast to `UK2Node_Event` or `UK2Node_ComponentBoundEvent` directly — NOT to `UK2Node_CustomEvent`. `UK2Node_ComponentBoundEvent` derives from `UK2Node_Event`, not `UK2Node_CustomEvent`, so any cleanup pass that uses `Cast<UK2Node_CustomEvent>` silently misses every bound event. The prior Replace-mode scan had this bug for `ComponentEvent`/`WidgetEvent` blocks — it never matched anything, and duplicate bound-event nodes accumulated across compiles causing double-fire handlers.
- When a `#define` (e.g. a version-detection macro like `MCP_HAS_METASOUND_FRONTEND_V2`) lives only inside a handler `.cpp`, test files that include a sibling helper header see the macro as 0 — the guarded test body becomes dead code at compile time with no warning. Define version/feature macros in a shared header (e.g. `MetaSoundLiteralFromTypeName.h`) so test TUs can reference them. Check macro reachability explicitly when reviewing guarded test code; the compiler will not flag the undefined-macro-as-0 expansion.
- When adding a new handler subdirectory (e.g. `Private/Handlers/Audio/MetaSound/`), put shared helpers in a dedicated header within that subdirectory rather than copying file-`static` helpers from sibling files. File-`static` helpers cannot be reused across `.cpp` files and drift (different log messages, missing checks) over time. Cross-domain helpers (`McpSafeAssetSave`, `AddAssetVerification`) already live in `Private/Utils/AssetUtils.h` and are reachable via `PinWrightHelpers.h` — do not redefine them locally.
- UBT's include search adds a handler `.cpp`'s own directory and the module's `Private/` root, but NOT arbitrary subdirectories. A header at `Private/Handlers/Audio/MetaSound/Foo.h` must be included from a sibling `.cpp` as `#include "Handlers/Audio/MetaSound/Foo.h"`, not bare `#include "Foo.h"`. The bare form works only from the `.cpp` that lives next to the `.h`; cross-file bare includes silently fail to resolve under other compilation contexts.
- Regression tests for handler bugs must call the same production helper the handler uses — not an inline re-implementation of the fix logic. A test that re-implements the fix as a local lambda still passes after reverting the production code, giving a false-positive green. Promote fixes into namespace-scope helpers with a header declaration (tagged `PINWRIGHT_API`) so tests link against the real symbol. This is the most common false-positive pattern caught by spec-compliance review.
- When resolving the class of a `%ref` target pin in BPIR (e.g. for `ConstructObjectFromClass`-derived nodes like `CreateWidget`, `SpawnActor`, `SpawnActorFromClass`), prefer `UK2Node_ConstructObjectFromClass::GetClassToSpawn()` over `Pin->PinType.PinSubCategoryObject`. The pin's subcategory can lag behind the authoritative spawn class after `ReconstructNode` under some class-loading edge cases, whereas `GetClassToSpawn()` reads `ClassPin->DefaultObject` directly. Exposed in the codebase as `FBpirCompiler::GetAuthoritativePinClass(UEdGraphPin*)`.
- When post-hoc validation keeps blocking valid authoring with false positives, prefer source-level fixes and narrow sanity checks over heuristic detection. Enumerating every legitimate engine-synthesized pattern (`ExecuteUbergraph_`, `BndEvt__`, `InpActEvt_`, async-action `<PinName>_<GUID>` proxies, etc.) from outside the engine is a losing fight — every new K2Node that synthesizes class-layer metadata breaks the whitelist. Prevent corruption at the source (Phase-0c scrub of deleted-node UFunctions, `RefreshBpirDelegateNodes` after the full compile) and trust UE's own `CompileBlueprint` status for class-layer validity. The integrity gate should only assert invariants UE itself would never emit (invalid FNames, null pin targets, cross-graph pin links, canonical-GUID mismatches on `UK2Node_CreateDelegate`).
- `FKismetEditorUtilities::CompileBlueprint(BP, EBlueprintCompileOptions::RegenerateSkeletonOnly)` does NOT clear `GeneratedClass->Children` or `FuncMap` — it only rebuilds `SkeletonGeneratedClass` via `FastGenerateSkeletonClass` and explicitly skips `FKismetCompilerContext::CompileClassLayout` (and thus `CleanAndSanitizeClass`, the only engine pass that scrubs the generated class's field chain). If a plugin deletes a `K2Node_CustomEvent` / function graph during a Phase-0 sweep and then does only a skel-only recompile, the backing UFunction survives on `GeneratedClass` as an orphan and crashes `TFieldIterator<UFunction>` on cold reload. A subsequent full `None`-mode compile DOES scrub via `CleanAndSanitizeClass`, but the belt-and-suspenders fix is a targeted per-UFunction scrub (`RemoveFunctionFromFunctionMap` + `FLinkerLoad::InvalidateExport` + unlink from `Children` linked list + rename into transient) in the same transaction as node deletion. Do NOT call the engine's public `FBlueprintEditorUtils::RemoveStaleFunctions` — it wipes all non-native UFunctions, including user-authored ones.
- `widget_export_xml` with `resolve_geometry=true` returns bogus `abs_h` values for stretched-Y child slots nested under a `CanvasPanel` root that isn't itself at viewport size. Symptom: after correctly setting `LayoutData` with stretch anchors (`min.Y=0.94`, `max.Y=1.0`), the exporter shows `abs_h=0` or negative values, even though the actual runtime layout is fine. The stored `Slot.LayoutData` field reflects the correct intent. Workaround: trust the stored `LayoutData` and verify at runtime via screenshot; don't chase the exporter numbers.
- Historical split-test-module checkouts only: if a separate `PinWrightTests` module calls a main-module utility such as `WidgetAuthoringHelpers`, the called declaration needs `PINWRIGHT_API`. In the current main-module test layout, do not add API macros just because a test under `Private/Tests/` calls the helper; reserve exports for real cross-module callers.
- In UE 5.6 `FVector2D` stores `double`-precision components (the `FVector2d` variant is active). `TestEqual(What, Pos.X, 50.0f)` triggers an overload ambiguity between the `float` and `double` variants of `FAutomationTestBase::TestEqual`. Pass a `double` literal (`50.0`) when the actual side is an `FVector2D::X/Y` component. `TestEqual` with `FVector2D` values directly has no ambiguity — the scalar overload set only engages when comparing individual components.
- `FJsonObject::Values` is a `TMap` (hash-ordered), not insertion-ordered. Any code that writes JSON to disk for diff/round-trip use MUST sort keys at serialization time — iterating `Values` or calling `FJsonSerializer::Serialize` directly produces non-deterministic line order across runs. Reference: `SerializeSortedJsonObject` / `WriteSortedObject` / `WriteSortedValue` in `Handlers/Asset/AssetDumpHandler.cpp` — recursive writer that sorts keys per object before emitting.
- Before calling `IFileManager::DeleteDirectory(Path, /*RequireExists*/false, /*Tree*/true)` on a path derived from user input, validate the target is a STRICT subpath of an authorized root — not equal to it. Normalize both sides with `FPaths::NormalizeDirectoryName`, then check `Dir.StartsWith(Root + TEXT("/"))`. Plain `StartsWith(Root)` passes when `Dir == Root` and will recursively delete the root itself. Reference: `AssetDumpWriter::WriteAssetDump` in `Utils/AssetDumpWriter.cpp`.
- `IAssetRegistry::ScanPathsSynchronous` is NOT a cheap no-op even with `bForceRescan=false` — it acquires the registry's `InterfaceLock` write-lock and calls `WaitForInMemoryObjects`, re-evaluating every loaded asset in the path. A full `/Game/` sweep can take hundreds of milliseconds. Guard with `!IAssetRegistry::IsLoadingAssets()`: if the editor's initial scan has completed, skip `ScanPathsSynchronous` entirely and let `GetAssets` return fresh data. Only call the scan when `IsLoadingAssets()` is true. Reference: `asset.dump_folder` handler body in `Handlers/Asset/AssetDumpHandler.cpp`.
- To detect whether a Blueprint property value is locally overridden vs inherited from its parent class, get pointers via `Property->ContainerPtrToValuePtr<void>(CDO)` on both the child CDO and the parent CDO, then call `!Property->Identical(ChildPtr, ParentPtr, PPF_DeepComparison)`. `PPF_DeepComparison` matters for struct/array properties — `PPF_None` gives shallow identity checks that miss value-wise equality for nested containers. Note: `Property->GetOwnerClass()` tells you which class DECLARED the property, which is a separate question from whether the value is overridden. Reference: `ExportPropertyToJsonValueWithInheritance` in `Utils/PropertyUtils.cpp`.
- When calling `Property->Identical(Child, Parent, PPF_DeepComparison)` with pointers from `Property->ContainerPtrToValuePtr(Child/ParentCDO)` to detect local-override status, guard against the property NOT existing in the parent's class layout. If the property was declared on the leaf asset class (e.g. via `TFieldIterator<FProperty>(LeafClass, IncludeSuper)` surfacing a leaf-declared property), the parent CDO has no slot at that offset and `ContainerPtrToValuePtr(Parent)` returns a pointer into unrelated memory — `Identical` then crashes on non-POD types (`FSoftObjectPath`, `FText`, `TArray`, anything with heap-allocated state). Guard with `ParentContainer->GetClass()->IsChildOf(Property->GetOwnerClass())` before the `Identical` call; skip (treat as overridden) when false. Reference: `ExportPropertyToJsonValueWithInheritance` in `Utils/PropertyUtils.cpp`.
- `FEditorDelegates::OnEditorClose` does NOT exist in UE 5.6. For engine/editor-shutdown cleanup hooks, use `FCoreDelegates::OnPreExit` from `Misc/CoreDelegates.h`. It fires on the game thread during engine pre-exit and is the stable replacement. Reference: `PinWrightModule.cpp` uses this to tear down the `asset.dump_folder` ticker.
- `TArray::Pop(bool bAllowShrinking)` is deprecated in UE 5.6. Use `TArray::Pop(EAllowShrinking::No)` or `TArray::Pop(EAllowShrinking::Yes)` — the boolean overload compiles with a warning and will be removed in a future engine release. Same deprecation applies to `Remove(bool)`, `RemoveAt(int, bool)`, etc. — they all moved to the `EAllowShrinking` enum.
- `RPC_PARAM_DEF(Name, Type, Desc, Default)` macro wraps `Default` in `TEXT(...)` — it MUST be passed a string literal, not a bare bool/number. `RPC_PARAM_DEF("diff", "boolean", "...", false)` expands to `TEXT(false)` → `Lfalse` → compile error. Write `"false"`, `"true"`, `"1.0"` as literals. All existing uses across the plugin follow this convention (grep `RPC_PARAM_DEF` to confirm).
- When binding to UE multicast completion delegates that may fire multiple times (e.g. `FEditorDelegates::OnLightingBuildFailed`/`OnLightingBuildKept`), guard with a `TSharedRef<bool, ESPMode::ThreadSafe> bFired` captured into all resolve closures — `Failed` and `Kept` can both fire on a cancelled build per UE editor comments in `Editor.h`. Without the guard, `OnComplete` fires twice and corrupts `FJobRegistry` ticket state. See `LevelBuildBinds.h::BindLightingBuildCompletion` for the reference implementation.
- When using `FTSTicker` to poll-detect completion of an async UE operation (nav build, shader compile, proc exit), require an observed `inProgress=true` tick before treating `!inProgress` as completion. Otherwise the first tick at t=0.5 s fires a false-positive because the operation hasn't started yet. Pattern: `TSharedRef<bool> bHasSeenInProgress` + cap warm-up at N ticks, then complete with `"nothing_to_do"` if the predicate never goes `true`. See [ue-async-completion-delegates](ue-async-completion-delegates.md) for code example.
- For long-running RPC handlers, prefer manual opt-in (`Ctx.StartJob`) over transport-level auto-promotion at a time threshold. Auto-promotion only catches handlers that hold the HTTP request open past the threshold; fire-and-forget handlers respond before the threshold and can never be promoted — exactly the cases that need ticketing most. Manual opt-in forces the handler to declare its async nature explicitly at the call site.
