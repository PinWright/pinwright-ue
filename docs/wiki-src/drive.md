# drive

The agent-facing surface for observing, acting on, and verifying live running UI: it reads a surface's addressable elements, injects real input at their geometry, and asserts conditions against what is actually on screen. Use it to drive and test UI that is already running, versus `ui.*` for runtime UMG instance ops (create/mutate a live widget) and `widget.*` for authoring the `UWidgetBlueprint` asset on disk.

## Surfaces

Every verb takes a `surface` param naming which live UI it targets:

- `game` — live PIE/game UMG. This is the default surface. With no root selector every live UMG root on the viewport is walked (a HUD plus an always-on overlay are one surface), in viewport z-order, bottom-most first; each element carries `root` (its root's backing widget name), handles stay unique across all roots, and `root_name` lists the walked roots comma-separated. `instance_name` (substring-matched against the backing widget name) or `root_index` (the Nth root, 0-based, which wins over `instance_name`) narrows the walk to one root; a substring matching several roots is `AMBIGUOUS_LIVE_ROOT`. Resolve handles under the same selector you observed with. `world` picks the PIE instance, in `editor.console_command`'s grammar (`server`, `client`, `client:N` 1-based, `pie:N` raw PIEInstance). Omitted, it is the only PIE instance with a game viewport (a dedicated server has none); in a listen-server or multi-client session that is several, and every game-surface verb refuses with `TARGET_AMBIGUOUS` listing the instances rather than following whichever one the engine ticked or the user clicked last. `drive.observe` reports the answering instance as `world` (`pie:N`, re-passable) and `world_kind` (`server` | `client` | `standalone`), and its screenshot captures that instance's viewport. `world: "client:2"` with one client is `WORLD_NOT_FOUND`; `server` on a dedicated server is `GAME_VIEWPORT_NOT_FOUND`. Target-less `drive.key` still types into the focused widget whatever `world` says; `world` scopes its settle observation only.
- `editor_chrome` — open editor Slate windows (main frame, asset editors, dialogs, transient popups). Selected by `window_title` (substring) or `window_index` (positional, wins); both unset picks the active top-level window. Enumerate targets first with `drive.list_windows`.
- `web` — the embedded CEF HUD (a WebUI browser, e.g. a PIE HUD). Selected by `browser_index` (default 0). Fully asynchronous — every observation/action is a CEF DOM round-trip — with real input for the action verbs (see Web surface).

`surface` defaults to `auto`, which resolves to `game`. Any unrecognized token also resolves to `game`, so a handler never sees `auto` downstream. Acting on a surface with no live UI yields a clean coded error (`PIE_NOT_RUNNING`, `WEB_BROWSER_NOT_FOUND`, `SURFACE_NOT_SUPPORTED`), never a hang.

## Observation

`drive.observe` is the entry point. It returns the surface's `elements[]` — each with a stable `handle` (the addressing token every action verb consumes), `type`, `label`, `value` (present only for an editable input: its **live typed text** — what `drive.type` just entered; omitted when empty, since `label` instead carries the accessible/**hint** text), `enabled`/`visible`/`focused`/`interactable` flags, `geometry` (see below), and `surface`. Static text/labels are included for verification with `interactable:false`; only `interactable:true` elements are real action targets.

`enabled` and `visible` are **effective** state, folded down the widget's ancestor chain — a control under a disabled or `Collapsed`/`Hidden` parent reads `false` even though its own Slate flag says otherwise. (`visible` means "is drawn", so a `SelfHitTestInvisible` HUD label still reads `true`, while a control lying wholly outside the rect of a clipping ancestor (`ClipToBounds`, e.g. a closed dropdown parked above its panel by a render translation) reads `false`; a partly clipped control stays `true`.) Such an element is still listed, so `widget_present`, `count` and `text_*` keep working against it; only its state flags go false.

`geometry` is `{ absolute: {x,y,w,h}, space: "desktop", stale?: true }`. `absolute` is in **desktop pixels** — the owning window's screen origin is already included, so it is directly what `drive.click`/`drive.hover`/`drive.drag` inject at and what an external OS-level injector needs; do not add a window origin to it. `space` names that space in-band so it never has to be inferred from this page. `stale:true` appears only when the element was not arranged for the current frame (it or an ancestor is `Collapsed`/`Hidden`, or it is clipped out entirely), and in that case `absolute` is zeroed rather than reporting the last frame that did draw it — a stale element is never a valid click target, and `drive.click`/`drive.drag` refuse one with `TARGET_CHANGED`. Absence of `stale` means the rect is live, with one caveat: a widget that is visible but has never been painted (or was culled this frame) is not detected as stale and reports whatever it last stored.

One exception to `space:"desktop"`, which drive cannot currently detect: content under a retained `SRetainerWidget` (UMG's `URetainerBox`) is painted into an `SVirtualWindow` rooted at (0,0), so those elements' `absolute` is **retainer-local**, not desktop. Neither `drive.*` nor an external injector can aim at such an element by its reported rect.

By default the observation also attaches a Set-of-Mark `screenshot`: a PNG (base64) with numbered marks painted over the **interactables only**, capped at `mark_cap` (default 50). The screenshot honestly reports `marks_drawn` versus `marks_omitted` (offscreen, too small, or past the cap) so the agent knows which elements the image actually labels. On `game` and `web` the image is the game viewport's composited frame (scene, post-process and the UMG/Slate layers — the same pixels `editor.screenshot` reports as `captureMode: nativeBackBuffer`), falling back to the scene-only render target only when no back buffer can be read (headless / `-RenderOffScreen`); on `editor_chrome` it is the selected window. Marks are placed at each element's desktop rect minus the captured surface's desktop position, so they land on the element's pixels wherever the viewport or window sits on screen. Pass `screenshot:false` to skip it.

A rich HUD can carry 170-200+ elements, so `drive.observe` can compact its list on request: `interactables_only:true` drops static text/labels and returns only the actionable widgets (often a ~7x reduction), and `max_elements:N` (0 = unlimited) caps the array and reports how many were dropped via a top-level `omitted_count` (never a silent truncation). Both apply to every surface.

The async action and wait verbs do **not** embed a full observation by default — that was the main source of oversized responses. They carry one back under an `observation` field only when you opt in via the `observe` mode: `none` (the default — settle/diff result only, no element list or screenshot), `list` (elements, no screenshot), or `list+screenshot`. Set `include_journal:true` (with an optional `journal_since` cursor) to also attach a journal delta.

## Timing and settle

There are no blind sleeps. After a game/editor action, the settle driver samples the live UI each engine frame and runs a pure change-detection decision: it waits for the UI to **change then hold stable** for `stable_ticks` (default 2) consecutive ticks within `settle_budget_ms` (default 1500), or — if nothing ever moved — reports a clean quiet once `quiet_budget_ms` (default 500) elapses. The per-frame loop watches the UI's *shape* (element types, geometry, visibility), deliberately not handles or text, so churn does not keep it from settling. The response's `diff` compares the pre-action and final element sets by handle and live `value`, and `outcome`/`changed` never contradict it: a non-empty `diff` always reports `changed:true`, and when the shape held still the whole quiet budget yet the diff is non-empty (a list that recreated its rows under new handles, or a value-only `drive.type` into a fixed-geometry field) the outcome is `settled_changed`, not `no_change_within_budget`. So `no_change_within_budget` means the final UI matches the pre-action one exactly. Neither signal says the action *caused* the change: background churn shows up too, so confirm a specific effect with `drive.expect`/`drive.wait_for` (`text_equals`, `widget_present`, ...). `changed:true` with an empty `diff` means the UI moved during the settle and came back. Outcomes are `settled_changed`, `no_change_within_budget`, `wait_for_met`, `timeout`, or `continue`.

After an action, the `diff` — a per-handle before→after delta whose `changed` set counts any element whose type, geometry, visibility, **or editable `value`** changed (so a pure `drive.type` edit surfaces here even when the settle `changed` above is false) — is reported as a compact **summary** by default: `{ appeared_count, disappeared_count, changed_count, appeared_sample, disappeared_sample, changed_sample, omitted }`, where each sample carries at most the first 15 handles and `omitted` flags any category that overflowed. Pass `full_diff:true` to get the complete appeared/disappeared/changed handle lists instead.

The web surface runs the same settle decision (`stable_ticks`, `quiet_budget_ms`, `settle_budget_ms`, or `wait_for` until `timeout_ms`) and returns the same `{ outcome, changed, settled, condition_met, elapsed_ms, ticks, input_path, diff }` shape, but a web sample is a CEF DOM query rather than a frame, so a tick there is one completed query (tens of ms) and the baseline is the DOM queried just before the input. Note the value-aware `diff` above is native-only: the web harvest folds an input's live value into the element's text/label, so `value` is empty on web and a value-only web edit does **not** surface in the `diff` — confirm typed web text with `drive.expect`/`drive.wait_for` `text_equals`/`text_contains` instead. `drive.wait_for` on web polls the DOM on a fixed ~0.25s interval until the condition holds or `timeout_ms` elapses.

Any verb can pass an explicit `wait_for` condition object instead of relying on settle-on-change: the driver then polls until that condition is met (outcome `wait_for_met`) or `timeout_ms` (default 5000) elapses (outcome `timeout`). In wait_for mode the change/stability tracking is bypassed — the condition and its timeout are the only terminal states. See Verification for the condition shape.

## Verification

`drive.expect` evaluates a single condition against a surface **right now**, synchronously, with no settle — use it to assert a post-state you already expect to hold. It shares one condition engine with the `wait_for` mode of the action/wait verbs, so the same condition object asserts immediately (`expect`) or polls over time (`wait_for`).

A `condition` object is `{ "type": <kind>, ... }`. The `type` is required; only the fields relevant to the type matter:

- `widget_present` / `widget_absent` / `widget_enabled` / `widget_visible` — `target` names the widget. An element matches when `target` is its full `handle` (case-sensitive), its `label` (case-insensitive), or a whole `/`-separated run of its handle's segments (case-sensitive). The last form covers a UMG widget name (`OkButton` matches `W_Popup_C_0/OkButton/SCommonButton`), a sub-path (`OkButton/SCommonButton`), or the handle's trailing Slate type segment. A partial segment (`OkBut`) never matches. Single-element conditions prefer an exact handle or label match over a sub-path match. `widget_enabled` / `widget_visible` read the **effective** flags described under Observation, so a control under a disabled or collapsed ancestor is correctly not met — these are usable as gates ("wait until the Create button becomes clickable") and as hidden-assertions.
- `text_equals` / `text_contains` — `target` + `expected_text`. Compares the element's live typed `value` when it has one (an editable input after `drive.type`), otherwise its `label`; the result's `actual` names the field it read (`value="..."` vs `label="..."`). So after typing into a search/edit box you can assert the text actually entered, not just a static label.
- `count` — `target` + `expected_count`, compared with `count_op` (`eq` default, `ne`, `lt`, `lte`, `gt`, `gte`).
- `geometry_in_bounds` — `target` + `expected_bounds` (`{ "min": {x,y}, "max": {x,y} }`).
- `journal_event` — `target` names the event; reads the live journal tail.
- `journal_severity` — `severity` is the threshold (e.g. `error`); reads the live tail.

Every type except `journal_severity` requires a non-empty `target`. An empty one matches nothing, so `widget_absent` would pass without checking anything, and the condition is rejected with `CONDITION_INVALID`. An action verb's `wait_for` of type `widget_absent` must also name something that is on the surface before the action. If the target matches no element in the pre-action sample, the call is refused with `CONDITION_INVALID` and nothing is injected, because a target that was never there reads as absent on the first tick whatever the action did. `drive.wait_for` and `drive.expect` do not apply that baseline rule, because a dialog that already closed is a legitimate `widget_absent` answer there. Take the target from a `drive.observe` handle, segment or label.

Journal conditions read the running session's event tail. To inspect that tail directly, poll `drive.events_since` with a `since` cursor: it drains newly emitted events plus changed variables and returns the next cursor (empty delta, no error, when no PIE/session is active).

## Web surface

Every drive verb works on `surface=web`. Web targets a browser by `browser_index` (default 0) instead of `instance_name`/`root_index`; with no live CEF browser the call returns `WEB_BROWSER_NOT_FOUND` synchronously.

`drive.click`, `drive.hover`, `drive.scroll`, `drive.drag` and `drive.key` deliver **real input**: the page sees trusted events (`isTrusted: true`), CSS `:hover` applies, and keys perform their default actions (a printable key types into the focused field, Enter activates, Tab moves focus). Each call first resolves the handle inside the page. A hidden element, or a disabled one, is `TARGET_CHANGED`. An element whose center is off the page viewport is scrolled into view. Then the page hit-tests the center (`document.elementFromPoint`). If another element is on top, the call is refused with `TARGET_OCCLUDED` and nothing is injected; `occluding_element` names the element on top (`tag#id`), and `x`/`y` give the point in CSS pixels. Otherwise the center is mapped to the desktop and the input is routed through Slate along the hit-test path at that point. The browser widget forwards that input to CEF, and the response's `input_path` is `"slate"`. The path is found by Slate's own window order, not by the platform's window-under-cursor, so no pointer warp has to land first; the same reason makes web input work under `-RenderOffScreen`. If that path does not reach the browser, the call is refused with `TARGET_OCCLUDED` and nothing is pressed. `occluding_window` names another window that holds the point, and `occluding_widget` names a widget drawn over the browser. `drive.drag` hit-tests both `handle` and `to_handle`.

Differences from the `game` surface:

- `drive.drag` needs `to_handle`; `to_x`/`to_y` have no web meaning (`INVALID_ARGUMENT`). It sends a real press, the interpolated moves and a release, so pointer- and mouse-event drag code works. HTML5 drag-and-drop (`draggable` with `dragstart`/`drop`) does not: the engine's CEF host does not implement drag sourcing, so Chromium cancels the native drag.
- `drive.key` takes a DOM `KeyboardEvent.key` value (`Enter`, `ArrowDown`, `Backspace`, `a`, `A`) or an FKey name (`SpaceBar`, `F5`). Anything else is `INVALID_KEY`. With a `handle` the element is hit-tested and DOM-focused, not clicked. Without one the key goes to the page's focused element. Either way the browser widget takes Slate keyboard focus first.
- `drive.type` still writes the value through the DOM (`input`/`change` events, `input_path: "dom"`) and replaces the field's text instead of typing at the caret. For real keystrokes use `drive.key`.
- `os_input` is refused with `INVALID_ARGUMENT`.

## No renderer (headless mode)

Under `-NullRHI` (mode `headless`) `drive.observe` and the action verbs' `observation` return elements (and journal) but no `screenshot`: no capture is attempted, because the readback would be an all-black frame. Use mode `offscreen` or `visible` for Set-of-Mark screenshots. The `web` surface is unchanged.

## See also

- `call("ui")` — runtime UMG ops on a live widget instance (create a HUD, push/pop activatable stacks, set live text/visibility). `drive.*` reads and drives whatever UI is already on screen; `ui.*` puts specific widgets there.
- `call("widget")` — author and edit the underlying `UWidgetBlueprint` asset on disk (survives editor restart).
- `call("editor")` — drive the editor app itself (PIE play/stop, viewport, screenshots). Start PIE here so `drive.observe` on `surface=game` has a live world.

### drive.observe

Capture one observation of a surface. Params: `surface` (default `auto`→`game`), `instance_name`/`root_index` (game root, with `instanceName`/`rootIndex` aliases; omit both to walk every root), `world` (game PIE instance, see Surfaces), `window_title`/`window_index` (editor chrome), `browser_index` (web), `screenshot` (default true), `mark_cap` (default 50), `interactables_only` (default false — return only actionable widgets), `max_elements` (default 0 = unlimited — cap the list COUNT, reporting drops via `omitted_count`), `max_bytes` (default 0 = unlimited — cap the elements' total serialized SIZE, reporting drops via `omitted_count`), `include_journal` (default false), `journal_since` (default 0). Returns `{ surface, root_name, world?, world_kind?, frame, timestamp, elements[], omitted_count?, screenshot?, journal? }` (`world`/`world_kind` on `game` only), each element carrying its `label`, its `root` on `game`, and — for an editable input — a distinct `value` holding the live typed text (omitted when empty). Start here to get the element `handle`s every action verb needs; reach for `interactables_only`/`max_elements` on verbose HUDs.

On every surface, a capture that reads back entirely empty (a `game`/`web` viewport that has never presented a frame, an `editor_chrome` window that was never drawn) fails with `BLANK_CAPTURE` rather than painting its marks over an all-black frame and returning it as a successful observation of a scene that was never rendered. On `game`, start PIE (`call("editor.play")`) and let it run a frame before observing; on `editor_chrome`, restore or show the window first.

Each element's `handle` is the full Slate/UMG widget-tree path, which dominates the payload — so on `editor_chrome` (and deeply-nested game/web UIs) `interactables_only` + `max_elements` bound the element COUNT but not the byte size, and a handful of capped elements can still overflow the inline display budget and spill to a file. Set `max_bytes` (e.g. `max_bytes:8000`) to bound the element list inline: it keeps adding elements until the serialized budget is reached, then reports the remainder in `omitted_count` (at least one element is always returned). `max_bytes` caps only the element list, so a scan/discovery observe must ALSO drop the default inline screenshot (`screenshot:false`, or `screenshot_mode:file`) — a single inline base64 screenshot alone exceeds the inline budget regardless of `max_bytes`. For a pure presence check — "is control X on this surface?" — prefer `drive.expect` with a `widget_present` condition instead: it returns a small fixed `{ met, actual, expected, detail, root_name }` shape (matching the control by `label`, so you need no handle) and never spills.

### drive.click

Move to a live element's center and inject a mouse-button click. Params: `handle` (required, from a `drive.observe` element), `button` (`left` default, `right`, `middle`), `os_input` (default false, see below), plus the common settle/observe/journal params (`observe` defaults to `none`, `full_diff` defaults to false). Re-resolves the handle against the live UI (a hidden/disabled re-resolve is `TARGET_CHANGED`, not a silent no-op), clicks, then settles.

Before the button goes down, the pointer is moved to the element's center and the click waits (up to ~0.3 s) until Slate routes that point to the element's **own** top-level window. If another window still owns the point, typically a `Message Log` or plugin window the editor opened over a PIE viewport, the click is refused with `TARGET_OCCLUDED`: the payload's `occluding_window` and `occluding_window_type` name that window, `recovery` names the call that clears it, and nothing is clicked. An editor notification toast (`occluding_window_type: "Notification"`, untitled) is cleared with `editor.dismiss_notifications`; `editor.resize_window` cannot shrink one. Any other window can be shrunk with `editor.resize_window` or closed (`drive.list_windows` finds it); then retry. The wait also covers Linux, where the platform's window-under-cursor updates a frame or two after a warp. Without it, the first click into a different window was hit-tested in the window the pointer had just left, did nothing, and still came back as `no_change_within_budget`. `drive.hover`, `drive.scroll`, `drive.drag` (press point), and `drive.type`/`drive.key` with a handle apply the same gate. `os_input:true` skips the wait, because it never warps the Slate cursor and the X server routes its events itself. It gets two checks instead, both before anything is injected: the same window-order check without the wait, and an X-level gate (below). Returns the compact `{ outcome, changed, settled, condition_met, elapsed_ms, ticks, input_path, diff (summary), journal? }` — no element list/screenshot unless `observe=list`/`list+screenshot`. The web surface returns the same shape (see Web surface).

`os_input:true` swaps the injection layer (`input_path` reports which one ran: `"slate"` or `"os_x11"`). The default `"slate"` path enters at `FSlateApplication::ProcessMouseButtonDownEvent`/`UpEvent` after an `ICursor::SetPosition`, and temporarily forces `SetHandleDeviceInputWhenApplicationNotActive(true)` so a click lands while the editor is not the active OS window. That is fast and reliable for editor chrome, but it *skips the OS and SDL layers entirely*: SDL mouse confinement (`EMouseLockMode::LockOnCapture`) and relative mode (`UseHighPrecisionMouseMovement`) never engage, and the forced inactive-input flag perturbs every `FSlateApplication::IsActive()`-dependent path — so capture/confinement bugs simply do not reproduce on it. `os_input:true` instead asks the X server for **real pointer events** (XTEST): an interpolated 24-step motion path from the pointer's current position to the element's center, then a genuine ~80 ms button hold. It never calls `ICursor::SetPosition`, never touches the inactive-input flag, and never calls `FSlateApplication::ProcessMouse*` — the input arrives over the same X → SDL → engine route a human's mouse takes. Element geometry needs no translation: `geometry.absolute` is already X11 root-screen coordinates.

Before `os_input` injects anything, it walks the X window tree at the element's center (`XTranslateCoordinates` from the root down) and reads each window's `_NET_WM_PID`. The deepest window that names a pid is the one that would get the real input. If that pid is not this editor's, or no window at the point names a pid (a bare WM frame or the desktop), the call is refused with `TARGET_OCCLUDED` and nothing is moved or pressed. The payload carries `occluding_window` (the X title), `occluding_window_id` and `occluding_pid`, so a peer editor, game or splash stacked over this editor on a shared display is named. Raise this editor's window (or move the other one) and retry. `drive.click` checks again after the motion, just before the press. A window raised over the point during the ~0.25 s motion aborts the press, and the call fails with `INPUT_FAILED`. The X gate is only about process ownership. Another window of this editor stacked over the target, such as a `Message Log`, a plugin window or a notification toast, is caught by the check that runs first: Slate's own window order (`TopWindowAtPoint`, the order Slate keeps in step with activation, with top-most windows above) must name the target's window at its center. If it names another window, the call is refused with `TARGET_OCCLUDED`, carrying the same `occluding_window` / `occluding_window_type` / `recovery` fields as the Slate path and no `occluding_pid`, and no X event is sent.

An X display has one pointer, so two editors injecting at once would interleave their motion and presses. Every `os_input` injection therefore holds a per-display lock across the whole gesture: `flock` on `/tmp/pinwright-os-input-<uid>-<display>.lock` (`:0` and `:0.0` share one file). A second editor waits up to 5 s for it, then fails with `OS_INPUT_BUSY`, injecting nothing; the payload's `holder_pid` names the editor holding it and `lock_file` the file. The lock binds only PinWright injectors, not a human's mouse or a raw `xdotool` script, so `drive.click` also reads the pointer (`XQueryPointer`) right before the press. If it is not exactly on the target (another client moved it, or a pointer grab clamped the motion), the call fails with `POINTER_MOVED`, payload `{x, y, pointer_x, pointer_y}`, and the button is not pressed.

While any X client holds an active **pointer grab**, every real pointer event goes to the grabber: the motion is clamped to its confine window and the press never reaches the target, with no error anywhere. So `drive.click` and `drive.hover` with `os_input` first probe for a grab (the same probe as `drive.input_state`'s `os_grab`) and refuse with `POINTER_GRABBED`, moving and pressing nothing; the payload's `held_by_this_editor` says whether this editor's SDL holds it. The usual holder is this editor itself: a PIE viewport that captured the mouse in relative mode (a `CapturePermanently` HUD with a hidden cursor) grabs the pointer after a click into it, and the grab can outlive `editor.stop`. Release it with a properly held Shift+F1 with X focus on the editor (`xdotool keydown Shift_L keydown F1 keyup F1 keyup Shift_L`; a bare F1 switches the PIE viewport to wireframe instead), or by quitting the editor. On a shared display such a grab also confines **every other session's** pointer to this editor's window, so release it rather than wait it out.

`os_input` is **mouse only**, and runs on Linux/X11 and Windows. On any other platform, when no X display can be opened, or in an editor with no visible window, it is refused with `INVALID_ARGUMENT` naming the reason rather than silently falling back to the Slate path. `drive.key` has no OS variant yet, so it does not accept `os_input` and the dispatcher refuses it there. That is an unimplemented path, not an impossible one: XTEST key events **do** reach the editor. In a visible Linux editor (UE 5.8, display `:0`, PIE in the level viewport) `xdotool keydown ctrl; sleep 0.3; xdotool keydown z; sleep 0.3; xdotool keyup z; sleep 0.2; xdotool keyup ctrl` fired the game's Ctrl+Z handler, and Ctrl+Y, Ctrl+C and Ctrl+V behaved the same. Two conditions were measured: X keyboard focus must be on the editor window, and each key must stay down across at least one engine tick (the 0.2-0.3 s holds above). A zero-length tap was not tried. Until `drive.key` grows an OS path, such a raw `xdotool` sequence is the faithful hotkey path; it bypasses the display lock and the ownership gate, so check the focused window (`xdotool getwindowfocus getwindowname`) first.

On a **Wayland** desktop the editor's X display is XWayland, so `DISPLAY` is set and `os_input` is accepted, but whether XTEST motion and button events, pointer grabs and confinement behave there is unverified: XWayland routes XTEST through the compositor, and the ownership gate cannot see native Wayland windows stacked over the editor. Every `os_input` result therefore carries `session`: `"wayland"` when the editor's environment has `WAYLAND_DISPLAY` set or `XDG_SESSION_TYPE=wayland`, `"x11"` otherwise, and a Wayland result adds a `warning` saying the input may not have arrived (a `no_change_within_budget` there proves nothing). It has not been verified on any Wayland compositor: PinWright's development host is an X11 session, so GNOME and KDE Wayland behaviour is unknown. Options when it does not work: log in to an X11 session, or start the editor on a private X display (`editor_start` `display: "xvfb"` / `"xephyr"`, see [mcp-transport](mcp-transport.md)), which sets `DISPLAY` to its own X server and clears `WAYLAND_DISPLAY`, so `session` reads `"x11"` there.

The gesture is paced with real sleeps (motion steps ~8 ms apart, ~80 ms press, ~120 ms after the release), so an `os_input` click blocks the editor for roughly half a second before the settle loop starts; pair it with `drive.input_state` to read who owned the mouse before and after.

### drive.type

Click an input element to focus it, then type a string one character at a time. Params: `handle` (required), `text` (required), plus the common params. Returns the same settle/diff/observation shape as `drive.click`. Supported on web. Use for text fields; use `drive.key` for individual keystrokes like Enter/Escape. A subsequent `drive.observe` surfaces entered text as the element's `value` field, and `drive.expect`/`drive.wait_for` `text_equals`/`text_contains` assert against that `value` — so the `drive.type` -> `drive.expect text_*` round-trip verifies what was typed (`label` still holds the input's hint/placeholder).

### drive.key

Inject a key event to the focused widget; with a `handle` it clicks that element to focus first. Params: `key` (required, e.g. `Enter`, `Escape`, `A`, `SpaceBar` — validated against `EKeys`, unknown names give `INVALID_KEY`), `handle` (optional focus target), `modifiers` (e.g. `ctrl+shift`, from shift/ctrl/alt/cmd), `action` (`press` default, `down`, `up`), plus the common params. On web `key` is a DOM key value and a `handle` is focused without a click (see Web surface). Use for keyboard shortcuts and submit/cancel keys. It is always Slate injection: `os_input` is refused here. When a repro needs a real OS keystroke, a held `xdotool` key sequence with X focus on the editor works (measured; see the `os_input` notes under `drive.click`).

`modifiers` sends a **real chord**, the way a keyboard does: each modifier's own key-down (`LeftControl`, `LeftAlt`, `LeftShift`, `LeftCommand`, in that order) before the key's down edge, and their key-ups in reverse after the key's up edge. `action: "down"` leaves the modifiers held and `action: "up"` releases them, so pass the same `modifiers` to both. A handler that reads held-key state (a game viewport's key map, `UPlayerInput`) sees the chord, not only the event's modifier flags. On Linux the platform modifier state that `FSlateApplication::GetModifierKeys()` reports is held for the chord too; the PIE game viewport hands that state to the editor's play-world chords, so `drive.key {key:"F1", modifiers:"shift"}` releases a PIE mouse capture instead of switching the viewport to wireframe. Windows keeps that state private, and a Linux editor started with `-RenderOffScreen` runs the null platform application, which reports no modifiers whatever is held; there, chords checked only through `GetModifierKeys()` (the PIE Shift+F1 mouse release among them) still see a bare key. So with `modifiers` and a press or down edge the response carries `modifiers_platform_held`, read back from `GetModifierKeys()` at the key's down edge, and, when it is `false`, a `warning` saying which handlers saw a bare key.

This is the **UI** keystroke: it goes to whatever widget holds keyboard focus and never resolves a game destination, so it cannot drive a pawn. To send a key into a running PIE session — focus moved onto the game viewport, delivery verified against the player controller's input stack — use `editor.simulate_input` with `type: "key_down"` / `"key_up"` (see the [`editor`](editor.md) page).

### drive.scroll

Inject a mouse-wheel event at an element's center. Params: `handle` (required), `delta` (default 1; positive scrolls up), plus the common params. Returns the settle/diff/observation shape. Supported on web. Use to scroll a list or scrollbox into range before observing.

### drive.drag

Press at one element's center, drag to a second point, and release. Params: `handle` (required, the press point), and a release point as either `to_handle` (its live center) or both `to_x` and `to_y` (absolute **desktop** pixels, the same space as an element's `geometry.absolute`) — missing both is `INVALID_ARGUMENT`; `duration_ms` (default 200) spreads the interpolated moves; plus the common params. On web `to_handle` is required and HTML5 drag-and-drop is not delivered (see Web surface). Use for sliders, reorderable lists, and drag-drop.

`os_input:true` (default false) drags with the real pointer instead, with the same gates and refusals as `drive.click`'s `os_input` (`TARGET_OCCLUDED` at the press point, `OS_INPUT_BUSY`, `POINTER_GRABBED`, and `POINTER_MOVED` unpressed when the pointer is not on the press point right before the press). Left button, ~80 ms held, then interpolated motion to the release point over `duration_ms`, then the release. Only the press point is gated: once a button is down, X sends the motion and the release to the window that took the press. Like an `os_input` click it is paced with real sleeps while the editor is blocked, so the engine pumps the whole drag in one frame. That suits Slate drag-and-drop, which is event-driven. For game code that polls the mouse every frame, use `drive.os_gesture`. On web, `os_input` is refused with `INVALID_ARGUMENT`.

### drive.os_gesture

A real-pointer click or drag at a **PIE game-viewport pixel or a world actor**, not at a UMG handle. Use it for 3D viewport interaction: clicking a placed actor or a gizmo, a gizmo drag, a box select, an unsteady click, a zero-hold click, a right-button drag. Params:

- `at` (required): the press point. Either `{x, y}` in game-viewport pixels (origin top-left, the `FViewport` size, so the same pixels as a viewport capture), or `{actor, component?}`. The actor is named by label, name or path in the PIE world, and the verb aims at its bounds center (or at the named component's), projected through the local player's view. An actor behind the camera, or a press point outside the viewport, is `OUT_OF_BOUNDS`. Mixed or unknown keys are `INVALID_ARGUMENT`.
- `to` (optional, same forms): the release point. The pointer moves there while the button is held (a drag).
- `waypoints` (optional, at most 64): `[{dx, dy}, ...]` viewport-pixel offsets from the press point, visited in order while the button is held, before `to`. The release is at `to`, else at the last waypoint, else at the press point.
- `button`: `left` (default), `right` or `middle`. Anything else is `INVALID_ARGUMENT`.
- `hold_ms` (0-10000, default 80): how long the button is held before the pointer moves on, or before the release when nothing moves.
- `world`: the PIE instance, using the same grammar as the other drive verbs.

Unlike `os_input` on `drive.click`/`drive.drag`, the gesture is **paced across engine frames**. A ticker sends each step when it is due: approach motion 8 ms per step, a 60 ms pause, the press, the hold, pressed motion with 192 ms per segment, the release, then 120 ms for the app to pump it. Every step due at a tick goes out in that tick. Per-frame mouse polling therefore sees the button held, the motion while pressed, and the release on later frames. `hold_ms: 0` with no motion releases in the same frame as the press. The editor is not blocked. The call answers once the release has been pumped.

The gates are those of `os_input`, all checked before anything moves. If another window of this editor or another process's X window is on top of the viewport at the press point, the call is refused with `TARGET_OCCLUDED` (`occluding_window` / `occluding_window_type` / `occluding_pid`). The per-display lock is held for the whole gesture (`OS_INPUT_BUSY`), and a held X pointer grab is refused with `POINTER_GRABBED`. Right before the press, the call re-checks that no foreign window has been raised over the point (`INPUT_FAILED`) and that the pointer is on the point (`POINTER_MOVED`), and leaves the button up if either check fails. Platform support is that of `os_input`: on a host where it is unavailable (no usable X display, for example) the call fails with `INVALID_ARGUMENT`. With no PIE session it fails with `PIE_NOT_ACTIVE`.

Returns `{ input_path, button, hold_ms, press: {x, y, screen: {x, y}, target?, hit_actor}, release: {x, y, screen, target?}, press_frame, release_frame, elapsed_ms, pointer_after: {x, y}, pointer_on_release }`. `target` names the resolved actor and the world point aimed at. `hit_actor` is the actor a visibility trace from the press pixel hits, read before anything moved, or null. Compare it with `target.actor` to see whether something stands in front. `press_frame`/`release_frame` are `GFrameCounter` when each edge went out. The verb does not settle on UI or diff anything, so read the game state back yourself (for example with `object.call_function`).

### drive.hover

Dispatch a real mouse-move to an element's center so hover state fires. Params: `handle` (required), `os_input` (default false — the same OS/X11 injection opt-in documented under `drive.click`, moving the pointer along an interpolated XTEST path with no button press), plus the common params. Returns the settle/diff/observation shape plus `input_path` (`"slate"` or `"os_x11"`). Supported on web, where CSS `:hover` applies. Use to surface tooltips or hover-only UI before observing — and with `os_input:true` to move the real pointer over a viewport that confines or hides the cursor, which the Slate path cannot exercise.

### drive.wait_for

Poll a surface across frames until a condition holds or the timeout elapses — no input injection. Params: `surface`, `instance_name`/`root_index` and `world` (game, see Surfaces; or `browser_index` for web), `condition` (required, see Verification), `timeout_ms` (default 5000), `stable_ticks`/`quiet_budget_ms`/`settle_budget_ms` (carried for parity), `observe` (default `none`), `include_journal`, `mark_cap`, `journal_since`. Pre-checks for live UI so a no-PIE/no-browser case errors immediately instead of polling the full timeout. Returns the compact `{ met, outcome, elapsed_ms, ticks, matched?, journal? }` — `matched` is the single matched element when the condition is met (no full element list unless `observe=list`/`list+screenshot`). Web returns `{ met, elapsed_ms, matched? }`. Use to wait out an async transition (a screen appearing, a count reaching N) before asserting.

### drive.expect

Evaluate a condition against a surface immediately, synchronous, no settle. Params: `surface`, `instance_name`/`root_index` and `world` (game, see Surfaces; or `browser_index` for web), `window_title`/`window_index` (editor chrome), `condition` (required, see Verification). Returns `{ met, actual, expected, detail, root_name }` (web omits `root_name`). Use to assert a state you expect to hold now; reach for `drive.wait_for` when the state may still be settling.

### drive.events_since

Drain the live journal tail from a cursor. Params: `since` (default 0; pass back the previous response's `cursor` to poll incrementally). Returns `{ events[], changed_variables[], cursor }` — an empty delta with cursor 0 (not an error) when no PIE/session is active. Use to inspect journal events/variables, or to feed `journal_event`/`journal_severity` verification with the right cursor.

### drive.list_windows

Enumerate open top-level editor windows so an agent can target editor chrome before observing/acting on it. No params. Returns `{ windows[{ title, type, index, maximized, geometry.absolute{x,y,w,h} }], count }`. A window's `index` selects it via the `window_index` selector and its `title` via `window_title` (substring) on the editor-chrome drive verbs. `maximized` is the live `SWindow::IsWindowMaximized()` state — the same signal `editor.resize_window`'s `WINDOW_MAXIMIZED` gate and `editor.set_window_state`'s readback use — so a `maximized:true` window must be restored first (`editor.set_window_state {state:'restored'}`) before `editor.resize_window` will act. (No `minimized` field: this enumeration excludes minimized windows, so one never appears here — an empty `windows` array on a live editor means the whole editor is minimized, not that Slate is down. `editor.set_window_state` is the only verb that can resolve a minimized window; call `editor.set_window_state {"state": "restored"}` with no selector to recover from that state, then re-list. It is a control verb, not an observation one — it changes the state it reports.) Use first whenever `surface=editor_chrome`.

### drive.input_state

Read-only snapshot of **who owns the mouse right now**. No params of its own: it accepts `surface` and `instance_name`/`root_index` for symmetry with `drive.observe` and ignores them, because everything it reports is per-application or per-game-viewport rather than per-UMG-root. Returns:

- `slate_active` — `FSlateApplication::IsActive()`. The Slate injection path (`drive.click` without `os_input`) temporarily forces `SetHandleDeviceInputWhenApplicationNotActive(true)` around its injection; `os_input` never touches it, so this is the field that tells you whether the app was genuinely foreground when something happened.
- `cursor_captor` — `null`, or `{ type, debug_path }` for the widget holding the cursor user's mouse capture.
- `focused_widget` — `null`, or `{ type, debug_path }` for the cursor user's focused widget.
- `viewport_has_mouse_capture` / `viewport_is_captor` / `viewport_has_focus` — the game viewport widget's own state. `has_mouse_capture` is true for the viewport **or a descendant**; `is_captor` is the exact identity test, so the two disagree precisely when a child widget stole the capture. All three are `null` when no game viewport exists (no PIE session).
- `mouse_capture_mode` / `mouse_lock_mode` / `hide_cursor_during_capture` — the `UGameViewportClient` policy, as enum member names (`CapturePermanently`, `LockOnCapture`, …). `null` with no game viewport.
- `show_mouse_cursor` — the first local player controller's `bShowMouseCursor`; `null` when there is no controller.
- `os_cursor` — `{ x, y }` from `FSlateApplication::GetCursorPos`, in the same absolute desktop pixels as an element's `geometry.absolute`, so you can verify where the pointer actually ended up after an `os_input` action.
- `os_grab` — `{ pointer, keyboard, held_by_this_editor }`, the X server's view, which the Slate fields above cannot see: they disagree in both directions (a stuck X grab with `cursor_captor: null`, or `viewport_has_mouse_capture: true` with no X grab). `pointer` / `keyboard` are true while some X client holds an active grab. X does not name the holder, so PinWright probes: its own X connection tries `XGrabPointer` / `XGrabKeyboard` on the root and releases at once (`AlreadyGrabbed` means someone else holds it). `held_by_this_editor` is SDL's own view: a window grab, or relative mouse mode on its input-focus window, which SDL implements as a confining pointer grab. A PIE viewport that captured the mouse with a hidden cursor (`CapturePermanently`) is the usual cause. It is `null` when this engine's SDL lacks the entry points to tell. The whole field is `null` without an X display (non-Linux, or `DISPLAY` unset). For any other holder, `xdotool key XF86LogGrabInfo` writes every grab with its client pid to the Xorg log.

It changes nothing (a free grab probe costs the window under the pointer a grab/ungrab crossing pair, which SDL ignores), and it does not require PIE — outside a session the viewport-scoped fields are `null` and the Slate-scoped ones still answer. Fails only with `SLATE_NOT_INITIALIZED`. Use it on both sides of a `drive.click`/`drive.hover` to see what the injection did to capture and focus, and to tell a Slate-path artifact from a real capture bug: pair it with `os_input:true`, which is the only path that exercises SDL confinement and relative mode.
