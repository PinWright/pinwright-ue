# pcg

Author `UPCGGraph` assets and their node/edge structure: create graph assets, append nodes by `UPCGSettings` subclass, wire pins, and use typed convenience handlers for common families. This namespace is the imperative per-node path; use the linked text-IR/decompiler surface for bulk graph work.

## Availability

`pcg.*` (including the `pcg.pcgir` decompile surface) requires the **PCG** engine plugin. The integration auto-loads when that plugin is enabled in the host project; when it is disabled, these methods are unregistered and calling one returns `PLUGIN_DISABLED` (enable the PCG plugin and restart the editor).

## Conventions

- Class paths for `add_node`'s `nodeClass` argument follow the `UPCGSettings` subclass convention, e.g. `/Script/PCG.PCGCreatePointsSettings`. The graph creates the matching `UPCGNode` wrapping that settings instance.
- `call("pcg.create_graph")` takes an optional `graphClass` (default `/Script/PCG.PCGGraph`) naming the `UPCGGraph` **subclass** to instantiate — the graph asset's own type, as opposed to `add_node`'s per-node settings class. It is resolved by reflection and gated on `IsChildOf(UPCGGraph)` plus non-abstract, so any subclass whose module is loaded works without PinWright linking it; the resolved class is echoed back as `graphClass` so a default is distinguishable from a requested subclass. The stock UE 5.8 subclass is `/Script/ProceduralVegetation.ProceduralVegetationGraph`, which needs the experimental Procedural Vegetation Editor plugin enabled — with it disabled the class does not resolve and the call returns `PLUGIN_DISABLED` naming the plugin, not `CLASS_NOT_FOUND`.
- `call("pcg.create_graph")` is a durable create operation: it force-saves the new `.uasset` before responding and includes the shared `saveRequested`, `saved`, `saveState`, `saveDetail`, `sizeBytes`, and measured `existsOnDisk` fields; `pendingFlush` is included when a requested save is not durable. It returns `SAVE_FAILED` with the measured save report when the package does not reach disk; an in-memory registry entry is never reported as a successful create.
- `x` and `y` are mandatory per the project's no-auto-layout rule for imperative per-node RPCs. The bulk text-IR path `call("pcg.pcgir")` is exempt.
- `call("pcg.inspect")` exposes implicit graph input/output endpoint ids, even though those nodes are not returned by `UPCGGraph::GetNodes()`.
- Endpoint-aware handlers such as `call("pcg.connect_pins")` resolve `GetInputNode()` / `GetOutputNode()` in addition to user-created nodes. Mutating user-node operations still treat those endpoints as immutable.
- **`call("pcg.connect_pins")` into a single-connection input pin DESTROYS the edge already on it.** That is the engine's semantic (`UPCGPin::BreakAllIncompatibleEdges`), and the new edge is always the survivor, so incremental authoring displaces earlier authoring. Every Procedural Vegetation node's `In` pin is single-connection (`UPVBaseSettings::InputPinProperties` / `UPVGrowerSettings::InputPinProperties`), so a whole PV plant graph is wired through pins that behave this way. The response discloses it rather than refusing: `connected` is measured (the target pin's edges are read back after the write, not echoed), `replacedExistingEdge` is a measured bool, `replacedEdges[]` names every destroyed edge with all four endpoints (`fromNode`/`fromPin`/`toNode`/`toPin` — enough to restore it with a second `connect_pins`), and `warnings[]` carries one line per loss. `fromNode`/`fromPin`/`toNode`/`toPin` at the top level are echoes of the request, not read-backs. The write runs inside an `FScopedTransaction`, so editor undo also restores the displaced edge. Note that `call("pcg.inspect")`'s edge **count** cannot detect the loss (measured 1 → 1); only the edge set can.
- `call("pcg.remove_node")` refuses to delete the implicit input/output nodes (`GetInputNode()` / `GetOutputNode()`) and returns `IMMUTABLE_NODE`.
- PCG handlers live in the gated `PinWrightPCG` sub-module, which loads only when the PCG plugin is enabled (see Availability above); the handler `.cpp` files additionally keep `__has_include("PCGGraph.h")` guards so the module still builds on UE installs without PCG.
- Shared helpers live in `Source/PinWrightPCG/Private/Handlers/PCG/PCGHandlerHelpers.h`.

## Typed helpers

Convenience handlers that wrap a settings subclass with the right field names and pin defaults, so callers don't have to know each `UPCGSettings` derivative's metadata layout. All take `(graphPath, x, y, …)`:

- `pcg.add_slope_filter` — adds a `UPCGNormalToDensitySettings` node (the UE 5.6 class that exposes the slope-based density adjustment older docs call "slope filter"). A supplied `normal` must be exactly three finite JSON numbers in an array (`[X,Y,Z]`) or an object containing all three numeric axes (`X/Y/Z`, case-insensitive); malformed input returns `INVALID_ARGUMENT` before a node is created. The success response includes the measured `normal`, `offset`, and `strength` settings. Source: `PCGAddSlopeFilter.cpp`.
- `pcg.add_noise_filter` — adds either `UPCGSpatialNoiseSettings` (spatial / world-space noise) or `UPCGAttributeNoiseSettings` (per-point attribute noise), routed by the `kind` arg. `noiseType` is optional but, when present, must be one of the documented modes; an unknown spatial or attribute mode returns `INVALID_NOISE_TYPE` before a node is created. Source: `PCGAddNoiseFilter.cpp`.
- `pcg.add_subgraph` — adds a `UPCGSubgraphSettings` node pointing at another `UPCGGraphInterface` asset. Rejects self-reference with `RECURSIVE_SUBGRAPH` and non-graph assets with `INVALID_SUBGRAPH_ASSET`, then calls `UPCGSubgraphSettings::SetSubgraph` (the editor-callback-wiring path, not a bare property write). Source: `PCGAddSubgraph.cpp`.
- `pcg.set_self_pruning_settings` — typed setter for the `UPCGSelfPruningSettings` node's parameters. Source: `PCGSetSelfPruningSettings.cpp`.

There is a typed setter for three settings classes and `pcg.add_node` resolves every `UPCGSettings` subclass the engine defines, so **`pcg.set_node_property` is what configures all the others** — one reflected property on a node's settings object, by name. Its method section is at the bottom of this page. The typed setters stay the better call where one exists: they know the field names and the version-specific layout.

## Graph parameters

Graph-level user parameters (the "Graph Parameters" panel of the PCG Graph editor) are the overridable inputs of a `UPCGGraph`, stored as an `FInstancedPropertyBag`. This is the asset-authoring CRUD surface for that bag, so an agent can build a parameterized/overridable graph without `python.execute`. Source: `PCGGraphParameters.cpp`.

- `pcg.add_graph_parameter` — add (upsert) a typed scalar parameter with an optional initial `value`. Supported `type`: `bool|int|int64|float|double|name|string`. Numeric and boolean values are parsed as full-string, finite, range-checked literals before the bag is mutated; malformed values return `INVALID_VALUE` and leave an existing parameter unchanged. Successful responses include the stored typed `value` read back from the bag, separate from the request text.
- `pcg.list_graph_parameters` — list parameters as `{name, type, value?}` (value present for scalar types).
- `pcg.remove_graph_parameter` — remove a parameter by `name`; refuses a missing name with `PARAMETER_NOT_FOUND`.

Value-typed parameters beyond the scalar set (struct/object/enum/text/...) list by name+type but are not yet addable/settable through these handlers.

## Running a graph

`pcg.generate` is the only executor here. It starts a **ticketed async job**; poll `call("system.job_status", {ticket_id})` for the terminal result. **Which field answers "did this work" depends on what the graph produces, and there is no single number that always answers it.** A graph that spawns instances is judged by `instanceCount` / `instancesByMesh`; one that spawns actors by `spawnedActorCount`; one whose product is data at the graph's Output node by `dataTypes[]` / `dataCount`, because `pointCount` counts only `UPCGBasePointData` and is *omitted* — never reported as `0` — when the output holds none. Generation runs from `UPCGSubsystem::Tick` under a per-frame budget, so it completes over many frames only while the editor ticks; wall-clock time follows the editor's frame rate. See the `pcg.generate` method page for the full contract.

## Engine-side traps when driving PCG

These are `UPCGComponent` / PCG-element behaviours, not PinWright behaviours — they bite equally through `python.execute`. Verified against UE 5.8 engine source.

- **`PCGComponent.cleanup()` from Python does NOT remove generated components.** Python binds the `UFUNCTION Cleanup(bool bRemoveComponents)` (`PCGComponent.h`), and a missing argument defaults to `false` → `CleanupLocal(false)`, which releases the managed resources but *keeps* the generated components for reuse. The next generate then reuses them and looks partially inert — silently, because the call is `void` and logs nothing. Call `cleanup(True)`. From PinWright, pass `cleanupFirst: true` to `pcg.generate` instead: it schedules `CleanupLocal(bRemoveComponents=true)` and the generate task chains after it. Note PCG's own pre-pass inside `Generate` only does `CleanupLocal(false)`, so a plain re-generate never starts from an empty slate.
- **`PointsPerSquaredMeter` is bounded by `PointExtents` in `UPCGSurfaceSamplerSettings`, in both grid modes.** With the default `bUseLegacyGridCreationMethod = false`, the density sets a target area per point but the derived cell size is then floored at `2 × PointExtents` (`PCGSurfaceSampler.cpp` — "Enforce that the grid is at least the provided extents"), and every cell emits a point (`Ratio = 1.0`); so once the extents dominate, raising `PointsPerSquaredMeter` changes nothing. With the legacy method on, cell size comes purely from `PointExtents × (1 + Looseness)` and `PointsPerSquaredMeter` only acts as a thinning ratio clamped to ≤ 1 — it can remove points, never add them. Either way the knob that actually changes spacing is `PointExtents`, and the relationship is non-linear (cell size ∝ √(1 / `PointsPerSquaredMeter`), floored by `2 × PointExtents`).

### pcg.generate

**Ticketed async job.** The kickoff returns `{status:"running", ticket_id, actor, graph, graphPath, partitioned, ...}` synchronously; the generation then runs on the PCG scheduler and the point count arrives on `call("system.job_status", {ticket_id})` once the status is terminal (`completed` / `failed`). Treat the kickoff as *accepted*, never as *done*. Streaming-capable clients (the request carries a `progressToken` and `Accept: text/event-stream`, and `args` did not set `wait: false`) block-and-stream instead: the finished result comes back inline, with a progress frame every ~5s carrying elapsed seconds and the same `ticket_id`. **If that stream drops or the transport deadline fires, poll the ticket** — the ticket is authoritative and stays queryable for an hour (`Completed ticket TTL`), so a generation that outran the request is never lost and the verb never reports failure for work that succeeded.

Why it cannot be synchronous: PCG executes graphs from `UPCGSubsystem::Tick` on the game thread under a per-frame time budget, and only signals completion from `UPCGComponent::PostProcessGraph` inside that tick. RPC handlers run on the same game thread, so a handler that waited for completion would starve the very tick the scheduler needs — a true self-deadlock. It also means wall-clock duration tracks the editor's frame rate: a graph that finishes in seconds on a focused editor can take minutes on a throttled background editor, which is the normal state in an agent session.

Completion result: `{actor, graph, graphPath, graphOutputAvailable, resourceCountsAvailable, instanceCount, instancedComponentCount, spawnedActorCount, instancesByMesh, distinctMeshCount, instancesByMeshTruncated, partitioned, completionSignal, elapsedSeconds}`, plus `dataCount` / `dataTypes` / `distinctDataTypeCount` / `pointDataCount` **only when `graphOutputAvailable` is true**, plus `pointCount` **only when `pointDataCount` is above 0**, plus `warnings[]` when anything was omitted.

- **`instanceCount` answers *whether* a SPAWNER generation did work — not *what* it produced, and not whether any other kind of graph did anything.** It counts the ISM/HISM instances PCG actually spawned and still manages (read from the component's managed-resource list), so it is non-zero exactly when the graph spawned instances it still owns. **It is structurally zero for every graph that spawns neither instances nor actors** — one terminating in an Export node, or in anything that hands its product to the graph Output node — so `instanceCount: 0` on such a graph is not evidence of failure and must never be read as "produced nothing". `spawnedActorCount` is the same idea, with the same limit, for spawned actors. These are different numbers — points, instances, actors, output data — and the response never conflates them.
- **`instancesByMesh` is what you compare across two generations.** It attributes `instanceCount` per static mesh: rows of `{mesh, instanceCount}` sorted by count, plus `distinctMeshCount` (the full species total) and `instancesByMeshTruncated`. The rows sum to `instanceCount` unless truncated. **`instanceCount` on its own cannot detect a mesh-entry or weight edit** — `UPCGMeshSelectorWeighted` (what `PCGStaticMeshSpawner` ships with) emits exactly one instance per input point, so weights *partition* a fixed point set: re-meshing an entry, dropping a species from a band, or re-weighting it all leave the total byte-identical while changing everything about what is standing there. `instancedComponentCount` is not a substitute — it moves only when the mesh set's cardinality changes. A row keyed `(no static mesh)` means PCG is managing an instanced component with no mesh (a spawner entry whose `StaticMesh` is unset or unresolvable); it renders nothing and is reported rather than dropped.
- **`dataTypes[]` is what tells you a non-spawner graph worked.** Rows of `{class, pcgDataType?, count}` — one per distinct output data class, sorted by count then class path — naming what actually reached the graph's Output node, plus `distinctDataTypeCount`. `class` is the UObject class path (`/Script/PCG.PCGParamData`); `pcgDataType` is PCG's own `EPCGDataType` name (`Point`, `Param` — the editor's "Attribute Set" — `Spline`, `Other`, …) and is **omitted, not guessed**, when the reflected enum does not name the value. Rows sum to `dataCount`; a row keyed `(null data)` means PCG emitted a tagged entry with no data object. `dataCount` on its own cannot do this job — it is a container count, so `dataCount: 3` reads identically for three point datas, three attribute sets, or three of some plugin's own type carrying a finished result.
- **`pointCount` is omitted for TWO different reasons, and neither is "the graph produced no points".** (1) `graphOutputAvailable: false` — `UPCGComponent::GetGeneratedGraphOutput()` holds exclusively the data wired into the graph's Output node, so a graph ending in a Static Mesh Spawner with an unconnected `Out` pin emits nothing there while spawning thousands of instances; `dataCount` / `dataTypes` are omitted too. (2) `pointDataCount: 0` with the output available — the graph emitted real data, but none of it is `UPCGBasePointData`, which is the only shape this readback can count. That is the case for an attribute set, a spline, a texture, or any plugin-defined spatial type (UE 5.8's `UPVData` from Procedural Vegetation, for one, whose result lives in an `FManagedArrayCollection`). Reporting `0` there would claim a measurement that never happened, so the field is absent and a `warnings[]` entry names the classes. **Never treat a missing `pointCount` as "produced nothing"** — read `pointDataCount` to learn which of the two cases you are in, then `instanceCount` / `spawnedActorCount` for a spawner graph and `dataTypes[]` for anything else. Convert to point data before the Output node if you specifically want a point count.
- `partitioned: true` means the component is HiGen/partitioned: it owns no resources itself, because its output and spawned instances live on the local components of the `APCGPartitionActor`s. On UE 5.7+ the verb walks those local components and the counts cover them (`localComponentsWalked: true`, plus `localComponentCount`); on 5.3–5.6 the engine exposes no way to enumerate them, so `localComponentsWalked` is `false` and a `warnings[]` entry says the counts are a lower bound.
- `completionSignal` names the path that closed the job: `generated_delegate` (the normal `OnPCGGraphGeneratedDelegate` broadcast), `already_generated` (nothing was scheduled and existing output was read back inline), `state_poll` (the pass ended without a broadcast; the component's own state decided the outcome), `timeout`.

Parameters worth knowing:

- `force` (default `true`) — generate even when the component is not dirty. With `force:false` on an already-generated, non-dirty component nothing schedules and the existing output is returned inline (no ticket).
- `cleanupFirst` (default `false`) — schedule `CleanupLocal(bRemoveComponents=true)` first, so the pass starts from an empty slate. Use it when a re-generate after a graph edit looks partially inert; PCG's own pre-pass only cleans with `bRemoveComponents=false` and keeps the previously generated components. See "Engine-side traps when driving PCG" on the [`pcg`](pcg.md) page.
- `timeoutSeconds` (default `1800`, clamped 5–21600) — caps how long the **job** waits, not the generation. On expiry the ticket fails with `PCG_GENERATION_TIMEOUT` and says the pass is still running; the generation is *not* cancelled, so re-reading later (e.g. `pcg.generate` with `force:false`) still returns the points. `call("system.job_cancel", {ticket_id})` is what actually cancels the generation (UE 5.4+).

Error codes answered **inline**, before any ticket exists: `ACTOR_NOT_FOUND`, `GRAPH_NOT_FOUND`, `NO_PCG_GRAPH`, `CREATE_COMPONENT_FAILED`, `PCG_GENERATION_NOT_SCHEDULED` (component deactivated, no PCG subsystem, or managed by the runtime generation scheduler — *and* the component reports no prior generation and no surviving generated resources; a component that has already generated is answered inline with `already_generated` instead). Error codes reported **on the ticket**: `PCG_GENERATION_CANCELLED`, `PCG_COMPONENT_GONE`, `PCG_GENERATION_ENDED_WITHOUT_OUTPUT`, `PCG_GENERATION_TIMEOUT`.

### pcg.set_node_property

The generic per-node settings editor: resolves the node's `UPCGSettings` object and writes ONE reflected property on it, so every settings subclass without a typed helper is still configurable. Takes `(graphPath, nodeId, property, value)`; `propertyName` is accepted as a spelling of `property`. `nodeId` is the id `call("pcg.inspect")` reports.

- **`value` in the response is MEASURED, `requestedValue` is the request.** The value is read back off the property *after* the write and after the change notification ran, so a narrowing conversion (a `double` on the wire landing in an `FFloatProperty`), an enum name that did not resolve, or a `PostEditChangeProperty` override that clamped are all visible instead of being papered over. `valueMatchesRequest` compares the two: it tolerates float precision, and treats an enum's ordinal and its symbolic name as the same value. For a shape it cannot compare — structs, arrays, object references — the field is **omitted** and a `warnings[]` line says so; it is never guessed.
- **A dotted `property` reaches into a nested struct member**, e.g. `Parameters.PruningType` on a `UPCGSelfPruningSettings` node (UE 5.4+ moved those knobs into the nested `Parameters` struct; on 5.3 they are flat, so the path is just `PruningType` there). Resolution is the same dotted-path primitive `property.set` uses.
- **The write reaches generation.** The notification is dispatched to the *settings object*, whose `PostEditChangeProperty` is the only thing that broadcasts `OnSettingsChangedDelegate` → `UPCGNode::OnSettingsChanged` → `UPCGGraph::NotifyGraphChanged`. A store with no notification, or one addressed to the `UPCGNode` (whose own override only broadcasts `Cosmetic`), leaves a value that reads back correctly and that generation never sees. `changeNotified` reports that the engine's change path ran — not that anything downstream recomputed.
- Enums accept the symbolic name (`"SmallToLarge"`, case-insensitive) or the ordinal. `null` is refused by the dispatcher for every declared type, so this verb cannot clear an object reference.
- The write runs inside an `FScopedTransaction`, so editor undo restores it; a conversion failure cancels the transaction rather than leaving a no-op undo entry.
- `settingsPath` names the settings sub-object the write landed on. `call("pcg.inspect")` reports only the settings **class** path, so this response is where that object path comes from — hand it to `property.get` to re-read the value later.
- `markedDirty` is the settings package's observed dirty state, not a request echo. Nothing is saved: persist with `editor.save_all` / `asset.save`.
- A node whose settings live outside the graph asset (a shared settings object) gets a `warnings[]` line — the write lands on the shared object and every graph instancing it reads the new value.
- Error codes: `GRAPH_NOT_FOUND`, `NODE_NOT_FOUND`, `IMMUTABLE_NODE` (the implicit graph input/output endpoints are not writable here), `NO_NODE_SETTINGS`, `PROPERTY_NOT_FOUND`, `PROPERTY_CONVERSION_FAILED`, `INVALID_PROPERTY`, `INVALID_VALUE`.
