# PinWright Model (`.pwmodel`) — format reference

A `.pwmodel` file is a **model source file** in the OBJ/STL family: one file, one model, one asset.
Unlike OBJ it stores the *recipe* — an ordered list of geometry operations — rather than the
triangles those operations produce. A mesh cannot be decompiled back into its recipe, so the text
is the only source and is meant to be committed and re-edited.

Four rules govern everything below:

1. **One source file produces exactly one `.uasset`.** No construct emits a second.
2. **The op vocabulary is the geometry verb set**, not a hand-picked subset — minus three verbs
   whose inputs the grammar cannot express (see [Verbs `pwmodel 0` does not carry](#verbs-pwmodel-0-does-not-carry)).
   There is no escape hatch because there is nothing to escape from.
3. **The artifact is data, not code** — no variables, loops or functions, deliberately.
4. **`pwmodel 0` carries no compatibility promise.** See [Version policy](#version-policy).

This is a **file format, not an IR**. `docs/ir-authoring.md` and its Ephemeral IR Invariant govern
IRs, which are isomorphic to their assets and can be regenerated by a decompiler; `.pwmodel` is
generative and has no decompiler, so its text is durable project data. Rationale and prior art are
in `docs/pwmodel-design.md`.

## This page is not a parameter reference

**Per-op parameter lists are deliberately absent.** Call `model.describe_ops` for the compact index,
then query each name for its complete parser metadata:

```js
call("model.describe_ops", {})                // compact names, contexts and parameter counts
call("model.describe_ops", { op: "bevel" })   // one complete op, possibly in two contexts
call("model.describe_ops", { op: "lightmap" }) // one complete param set, see below
call("model.describe_ops", { op: "uv_layout" }) // merged-atlas param set
```

The no-argument response has `index: true`; each entry carries only `name`, `context`, and
`parameterCount`, keeping the discovery call below the transport's inline display budget. A
narrowed response has `index: false` and each entry is self-describing: the description, the flags
that decide where and how it may be used, and every parameter with its type, default, allowed
values, and — when the parameter is bounded — an inclusive `min` / `max`. The range fields are
**absent rather than zero** on an unbounded parameter, since a published `0`/`0` would read as a
domain of exactly zero; they are how an author learns that `uv channel` is 0-7 from the vocabulary
instead of from a `PWSRC_BAD_VALUE` rejection.

**`min` / `max` is the REFUSED domain, and a clamped count does not have one.** The parser rejects a
value outside `min` / `max` outright (`PwParseCursor.cpp`, `PWSRC_BAD_VALUE`), so the pair means "this
value is illegal", not "this value is out of range". Every segment and step count is *clamped and
warned* instead — see [Segment counts below the engine's floor](#segment-counts-below-the-engines-floor)
— and publishing those floors and ceilings as `min` / `max` would convert each clamp into a refusal
and destroy the two-tier rule that a value `<= 0` reads as unset and takes the verb's default. So
**their domain is carried in the parameter's own `description`** — "Clamped to 3-256 with a warning;
0 or less reads as unset and takes the default 16" — and it is still `model.describe_ops` that
publishes it. Read the description as well as the range fields; only 14 of the vocabulary's 417
parameters have a refused domain, and all of them are UV channels, UV-layout gutter resolutions,
and the lightmap resolution.

**The response carries two arrays, not one.** `ops` is the op index or detail table. `paramSets`
(counted by `paramSetCount`) is the corresponding index or detail table for the three parameter
sets that are *not* ops and therefore cannot live in it: the `uv_layout` and `lightmap` statements
(`context: "model"`) and the `part <name>` header's `at=` / `rotate=` / `scale=`
(`context: "part_header"`). Index
entries carry `name` / `context` / `parameterCount`; detail entries add `description` / `params`
and, for ops, the authoring flags. `op=` narrows both arrays, which is why `op=uv_layout`,
`op=lightmap`, and `op=part` answer rather than returning `UNKNOWN_OPERATION` with a did-you-mean pointing at an
unrelated op.

**Read the response, not a summary of its shape.** These are the same static tables the parser
validates against, so they cannot describe an op that does not compile. A hand-maintained copy on
this page would drift the first time a parameter struct was renamed, and nothing would fail when it
did; the copy this paragraph replaced had already fallen five fields behind. That argument only
holds while the verb is described completely — every field above landed after this section was
written, so re-read the verb rather than this paragraph when they disagree.

What lives here instead: grammar, semantics, contracts, diagnostics, and the places the format
deliberately differs from the RPC surface.

## What the format deliberately is not

No variables, no loops, no functions, no expressions. This is not an omission awaiting a feature
request: **enumerable geometry is re-editable geometry.** An agent asked to enlarge the third of
eight holes edits one line of eight explicit blocks; the same agent facing `for i in range(8)` must
restructure the loop and re-derive every other hole's position. Re-editability is the whole reason
this format exists rather than 89 imperative RPC verbs.

Procedural generation belongs one layer up: a Python (or any) builder that *emits* `.pwmodel` text
gets loops and math while the committed artifact stays enumerable. That builder needs no plugin API;
the committed artifact is still the text.

The format also does not define materials (it binds them — MGIR owns material graphs), does not
place anything in a world, and does not describe terrain.

## Example

```
# comments run to end of line
pwmodel 0

materials {
    Shell = "/Game/Materials/M_Metal"
    Trim  = "/Game/Materials/M_Rust"
}

part body {
    box size=(80, 50, 40) material="Shell" color=(0.8, 0.8, 0.8, 1)
    subtract {
        sphere radius=18 at=(25, 0, 0)
    }
    bevel distance=2.5 segments=3
    uv channel=0 mode=box scale=(1, 1)
    uv channel=1 mode=patch_builder auto_pack=false
}

part trim at=(0, 0, 22) rotate=(0, 0, 15) {
    torus major_radius=42 minor_radius=3 material="Trim"
    uv channel=0 mode=cylindrical
    uv channel=1 mode=patch_builder auto_pack=false
}

uv_layout channel=1 texture_resolution=256
lightmap channel=1 resolution=256

collision {
    complexity = simple_and_complex
    box size=(78, 48, 38)
    hull { cylinder radius=20 height=60 }
}
```

## Lexical

| Element | Rule |
|---|---|
| Encoding | UTF-8. |
| Comment | `#` to end of line. Emits nothing; the line's newline is still significant. |
| Identifier | `[A-Za-z_][A-Za-z0-9_]*` |
| Number | Optional leading `-`, digits, **one** optional `.`, **and an optional exponent** (`e`/`E`, optional sign, digits). `1e-5`, `-2.5E+3` and `40` are each one token. |
| String | Double-quoted. Escapes: `\\`, `\"`, `\n`, `\r`, `\t`. Nothing else is an escape. |
| Tuple | `(a, b, c)` — a fixed-arity list of numbers. |
| List | `[(…), (…)]` — a list of tuples. |
| Frame list | `[(x, y, z, roll, pitch, yaw), …]` — a list of 6-tuples, position + rotation. A `List` at the lexical level; the type `frame_list` is what constrains its entries. |
| Harmonic list | `[(order, amplitude, phase), …]` — a list of 3-tuples, one azimuthal harmonic term each. A `List` at the lexical level; the type `harmonic_list` is what constrains its entries, and it is the only list type whose **first component has a domain of its own** — an `order` must be a whole number of at least 1. |
| Punctuation | `{ } ( ) [ ] = ,` |
| Newline | **Significant.** One statement per line; there is no statement terminator. A block's `{` must therefore open on its header line — a `{` on the next line is a new statement, not that construct's block. |

Whitespace inside a line is insignificant. A tuple or list may not span lines.

The exponent rule is the reason the tokenizer is purpose-built rather than shared with the IR
layer: `FIrTokenizer`'s number scanner stops before `e` (`IrTokenizer.cpp:54-82`), so `1e-5` would
lex as three tokens.

## Document structure

The **first non-comment, non-blank line must be `pwmodel 0`**. It is required — a file without it
is not a model document (`PWSRC_MISSING_VERSION`), and a different integer is refused by number
(`PWSRC_UNSUPPORTED_VERSION`).

After the header, in any order:

| Construct | Cardinality | Meaning |
|---|---|---|
| `part <name> [at= rotate= scale=] { … }` | one or more | A named sub-region of the single output mesh. |
| `materials { Slot = "/Game/…" }` | at most one | Binds slot names to material assets. |
| `collision { … }` | at most one | Simple-collision geometry and complexity flag. |
| `uv_layout channel=N [texture_resolution=M]` | at most one per channel | Packs that channel on the merged mesh with world-space texel density. |
| `lightmap channel=N [resolution=M]` | at most one | Sets `LightMapCoordinateIndex`, and `LightMapResolution` when `resolution=` is given. |
| `use <kind> from "<path>"` | any | Cross-file skeleton reference; the valid kind is `skeleton`. |
| `skeleton { … }` / `animation <name> { … }` | any | **Reserved signposts** for `.pwskel` / `.pwanim`; rejected with `PWMODEL_CONSTRUCT_IN_WRONG_FORMAT`. |
| `skin { smooth … }` | at most one | Real model-level skin rule for the single skeletal-mesh output. |

A document with no `part` is an error (`PWMODEL_NO_PARTS`). Part names must be unique
(`PWMODEL_DUPLICATE_PART`). A second `materials`, `collision` or `lightmap` is
`PWMODEL_DUPLICATE_MATERIALS` / `PWMODEL_DUPLICATE_COLLISION` / `PWMODEL_DUPLICATE_LIGHTMAP`.
A second `uv_layout` for the same channel is `PWSRC_BAD_BLOCK`; distinct channels are allowed.

**The part header is the one place the grammar is not `keyword params` on a line.** `part` takes a
name, then optional transform parameters, then the opening brace, all on one line:

```
part trim at=(0, 0, 22) rotate=(0, 0, 15) scale=(1, 1, 2) {
```

The optional `allow_floating=true` part-header parameter is a specific acknowledgement for an
intentional detached ornament. It suppresses only that named part's floating warning; the compiler
still measures the component and returns its triangle count, centre, volume and nearest distance.
It is not a model-wide switch.

`{` opens on the statement's line. Putting `}` alone on its own line is a **convention, not a rule**:
the parser accepts a closing brace anywhere after the last entry, so `part body { box size=(10, 10, 10) }`
compiles with no diagnostic. Follow the convention anyway — a one-line part reads as a single
statement, and the line number a later diagnostic anchors to is then the op's rather than the whole
part's. An unclosed brace at end of file is `PWSRC_UNCLOSED_BRACE` reported on **the line the brace
was opened on**, not on the end-of-file line.

### One file, one asset

`part` is a *region*, not an output. Every part merges into one dynamic mesh, which becomes one
`UStaticMesh` for an ordinary model or one `USkeletalMesh` when the document uses a compiled
skeleton. Nothing opts out. A part exists to (a) group ops under a name, (b) carry a transform
applied once to that group, (c) tag geometry with a material slot, and (d) provide the rigid-binding
unit and bone pivot for skeletal output.

The compile result reports per-part triangle and vertex counts for diagnostics. Those are
informational; there is exactly one `assetPath`.

### Reserved constructs

`skeleton` and `animation` are **parsed and brace-checked, then rejected at compile
time** with `PWMODEL_CONSTRUCT_IN_WRONG_FORMAT`, anchored to the source line. Each is a
signpost for its own source format: `.pwskel` is documented in `docs/pwskel-format.md`,
and `.pwanim` in `docs/pwanim-format.md`. The diagnostic points to the appropriate page.

- `use <kind> from "<path>"`, `<kind>` ∈ `skeleton`. The path must be a direct mounted Unreal asset path, such as `/Game/Rigs/Robot`. It resolves to a compiled `USkeleton`; the compiler does not read a source file or infer a format from an extension.
- `skeleton { … }` is the `.pwskel` signpost; `animation <name> { … }` is the `.pwanim` signpost.
- `skin { smooth … }` is a real `.pwmodel` construct. It configures the single skeletal-mesh output and is not a reserved signpost.

### Skeletal output

`use skeleton from "<asset path>"` selects skeletal output. A part with `bone="name"`
uses that compiled skeleton bone for rigid binding. The bone must exist. If no `skin`
block is present, every part must provide a bone binding.

**`bone=` binds weights; it does NOT change the part's coordinate space.** A bound part's
geometry is authored in the same mesh space as every other part — the skeleton's component
space, where the ref pose puts the bones — and the binding only overwrites that part's
vertices with a single full-weight influence after the merge
(`PwModelCompiler.cpp:2962-2990`). It does not reparent the geometry into bone-local space
and it does not translate anything to the bone. So a staff held by a hand bone at
component `(-54, 10, 99)` is authored with its shaft running up `x = -54`, not at the
part-local origin. The one worked example, `Examples/pwmodel/robot_arm_skin.pwmodel`,
cannot settle this on its own: its bones are stacked along `+Z` and its `at=` values are
plausible under either reading, which is exactly why this paragraph exists.

`skin { smooth ... }` asks the compiler to solve smooth weights for the merged mesh.
The `max_influences`, `stiffness`, `method`, and `voxel_resolution` values are passed to
the engine skin solver. Parts with explicit `bone=` bindings remain rigidly bound after
the smooth solve. Smooth output requires complete vertex influence coverage.

**Rigid parts are how you keep a stiff attachment off the nearest bone.** The smooth solve
has no selection input, so it weights every vertex — including a frond tip 50 uu out from
the neck, whose nearest bone is an upper arm, and a staff finial 150 uu above the hand.
Both smear under animation. Giving the part a `bone=` is the only way to say "this mass is
rigid to that joint", and it is applied after the solve, so it wins. Expect
`skeleton.audit_skin_weights`'s `influenceReach` check to list every vertex of such a part
as an offender at a large `normalizedDistance` with several `closerBones`: that check
measures bind-pose distance and has no way to know the distance was deliberate. It only
returns a verdict when you pass `maxReachDistance`, so the default `reported` status is
the right reading — do not gate on its offender list for a model that uses `bone=`.

**No generator can be aimed at a bone.** Every origin-capable generator is centre-placed
along its own local `+Z` (see [Where a generator's origin sits](#where-a-generators-origin-sits)),
and there is no `from=` / `to=` form, so a limb drawn between two joint positions `A` and
`B` has to be spelled as a centre, a height and an `FRotator`:

    at     = (A + B) / 2
    height = |B - A|
    rotate = (roll, pitch, yaw) such that local +Z maps onto normalize(B - A)

With `t = normalize(B - A)` and Unreal's `Rz(yaw) Ry(pitch) Rx(roll)` composition, the
yaw-free solution is `roll = asin(t.y)`, `pitch = atan2(-t.x / cos(roll), t.z / cos(roll))`,
`yaw = 0`. That leaves the twist about the primitive's own axis unconstrained, which is
invisible on a round primitive and load-bearing the moment the op also carries a
non-uniform `scale=` — the flattening axis is local `Y`, and with `yaw = 0` it lands
wherever the two-angle solution put it. Pin it by building the full frame instead: choose
the axis image `Zw = t` and the intended local-`Y` image `Yw` (for a flattened leaf, the
normal of the surface the leaf lies in), take `Xw = Yw x Zw`, and read the angles off the
columns — `pitch = asin(Xw.z)`, `yaw = atan2(Xw.y, Xw.x)`, `roll = atan2(-Yw.z, Zw.z)`.

This is arithmetic the format cannot express and therefore has to happen in whatever emits
the document. A 21-bone character costs ~100 of these conversions.

Skeletal output is one `USkeletalMesh` and its response identifies the referenced
`USkeleton`. `collision` and `lightmap` are not valid on a skeletal model. Author those
concerns in a separate static model or in the asset workflow for the target skeleton.

## Transform spaces

Every construct that carries a transform names its space. An unnamed transform is how a mesh ends
up silently misplaced.

| Construct | Space | Applied |
|---|---|---|
| op `at=` / `rotate=` / `scale=` | part-local | Composed into the primitive's `Append*` call. |
| op `from=` / `to=` / `up=` | part-local | Resolved into that op's own `at=`, `rotate=` and length before it runs. See [Aiming a generator at two points](#aiming-a-generator-at-two-points). |
| part `at=` / `rotate=` / `scale=` | part-local → mesh | Once, after the part's ops have run. |
| `transform` op | part-local | In sequence, mutating the accumulated mesh. |
| collision element `at=` / `rotate=` | mesh | At collision build. |

`at=` is a translation in Unreal units (centimetres under Unreal's fixed unit convention).
Dimensions and extents use the same unit; there is no per-document unit declaration. `rotate=` is
`(roll, pitch, yaw)` in degrees. `scale=` is a per-axis factor.

**`scale` bakes into vertex positions.** It is not a component scale, so non-uniform scale is safe
here in a way it is not on an actor: there is no inherited transform to shear, no normal-matrix
surprise at runtime, and nothing downstream can see that a scale was ever applied. The editor
intuition transfers wrongly, which is why this is stated rather than assumed.

### Where a generator's origin sits

**Every generator that offers an origin is centre-placed, `pipe` included.** `at=` therefore lands
the mesh's *centre*, not its base: a primitive of height H spans `-H/2 … +H/2` on its own axis. The
rest take no origin choice at all, and the one `Base` in the family is `Base` on a different axis.

| Generator | Origin | Note |
|---|---|---|
| `box`, `sphere`, `cylinder`, `cone`, `capsule`, `torus`, `arch` | centre | `EGeometryScriptPrimitiveOriginMode::Center`, passed explicitly on every call. |
| `pipe` | centre | No origin enum exists on its path — the revolved profile spans `-height/2 … +height/2` by construction. |
| `plane`, `disc`, `ring` | centre of the flat surface, in local X-Y | No origin parameter. |
| `stairs`, `spiral_stairs`, `revolve` | the generator's own layout | No origin parameter. |
| `ramp` | base **on the extrusion axis** | `OriginMode::Base` puts the extrusion span at `0 … width` along local Z; the ramp *profile* is separately corner-at-origin in local X-Y. A different construction, not a "sits on the ground" convention. |

**"The generator's own layout" measured, for the two that trip authors up.** Both from single-op
probes with no `at=` and no `rotate=`, read off `static_mesh.describe` bounds:

| Op | Written | Occupies |
|---|---|---|
| `stairs` | `step_size=(90, 15, 30) num_steps=8` | x `0 … 240`, y `-45 … 45`, z `0 … 120` |
| `ramp` | `size=(90, 240, 120)` | x `0 … 240`, y `0 … 120`, z `0 … 90` |

So `stairs` runs its **depth** along +X from the origin, carries its **width** on Y centred, and
rises from z 0 — the transpose of the parameter text's "per-step width, rise and depth along local
X, Z and Y". And `ramp`'s three `size` components do not land on X, Y and Z in the order written.

The practical consequence is a pairing that looks obvious and is wrong: `ramp` + `stairs
floating=true`, intended as treads on a raking wall, puts the wedge *beside* the treads rather than
under them and crosses them in plan, because the two ops' long axes are not the same axis. It
compiles clean and every count is green; only a render shows it. Prefer a single `stairs` with
`floating` left off — its own understructure **is** the raking wall — and rotate that one op.
`rotate=` applies before `at=`, so `stairs … rotate=(0, 0, 90) at=(0, -380, 0)` occupies
x `-45 … 45`, y `-380 … -140`, z `0 … 120`.

**`pipe` was base-placed (z `0 … H`) until it was rebuilt as a swept annulus.** It was the family's
one base-placed primitive and belonged to no rule: every other origin-capable generator is `Center`,
the stair verbs take no origin, and `ramp`'s `Base` is on its extrusion axis with a corner-at-origin
profile. **This is a behaviour change — a recipe written against the old placement now sits half a
height too low relative to the `at=` the author wrote.** Raise `at=` by `height/2` to restore it.

The old placement also silently mis-covered the deformers. `twist`, `taper` and `bend` measure their
`extent` symmetrically about the mesh **origin** (see [Deformer extents](#deformer-extents)), so a
base-placed pipe got the deform applied to its lower half only.

### Aiming a generator at two points

Every origin-capable generator is built along its **own local +Z**, so putting one *between* two
known points — two joints, two ends of a strut, a socket and its target — used to be spelled by
hand: a centre, a length, and a rotation derived off-format. `from=` / `to=` / `up=` spell it
directly, on every op that takes `at=` / `rotate=` / `scale=`.

```
cylinder radius=8 from=(0, 0, 0) to=(120, 0, 90)
```

**What an aim sets.** The op is centred on the midpoint of the two points and its local +Z is
aimed from `from` towards `to`. `at=` and `rotate=` are then **refused**, because the aim computes
exactly those two values and keeping either written one would discard an answer silently.

**What it does to the length is per-op**, because the parameter carrying the extent along local Z
differs. `model.describe_ops` publishes it as `aimExtent` and `aimExtentParam` on every op, which
is the authority; the table is here because the `box` spelling needs explaining.

| Op | `aimExtent` | The distance becomes | Also write |
|---|---|---|---|
| `cylinder`, `cone`, `pipe` | `scalar` | `height` | — (writing `height` too is refused) |
| `capsule` | `capsule_length` | `length` = distance − 2·`radius` | — (writing `length` too is refused) |
| `box` | `size_z` | the **Z** of `size` | `size=(x, y, 0)` — the zero says "take it from the aim" |
| everything else | `none` | nothing — the op keeps its own size | its own size parameters |

**A `capsule` subtracts its caps, and this is the reason the aim kind exists.** `length` measures
the cylindrical section only, with a hemisphere of `radius` added at each end, so an aimed capsule
takes `distance − 2·radius`. Handing it the raw distance overshoots `to` by exactly one radius at
each end — invisible in every count, green on every check — and a capsule is the primitive most
often aimed between two joints. A distance no greater than `2·radius` names no capsule at all and
is `PWMODEL_AIM_TOO_SHORT`.

**An op with no extent along local Z still aims.** Turning a `plane` or a `disc` to face along a
direction is the point; the distance simply goes unused, and `PWMODEL_AIM_LENGTH_UNUSED` says so
rather than leaving you to assume the geometry stretched to reach `to`.

#### `up=` pins the twist, and without it the twist is still pinned

Aiming fixes **two** of three degrees of freedom. The third — the rotation about the aimed axis —
is invisible on a round primitive and load-bearing the moment the op carries a non-uniform
`scale=`, because **the flattening axis is the primitive's local Y**. Any solve that answers only
"which way does it point" leaves that wherever the arithmetic dropped it, and a fan of flattened
cards then comes out half lying flat and half standing on edge, with every parameter in the
document correct and nothing to grep for.

- **`up=` given**: local +Y is set perpendicular to both `up` and the aim direction, so a
  flattening `scale=(1, k, 1)` squashes the op **towards `up`** whichever way it points.
- **`up=` omitted**: the frame is `roll = 0` — `pitch = -acos(z)`, `yaw = atan2(y, x)` on the
  normalised direction. For every non-vertical aim this is exactly `up=(0, 0, 1)`.

The two differ only where world up lies **along** the aim. An explicit `up=` there names no frame
and is refused (`PWMODEL_AIM_UP_PARALLEL`); the default is **not** refused, because a vertical limb
is ordinary — it falls back to `yaw = 0`, which puts local +Y on world +Y.

**`scale=` is unchanged and still bakes into the vertices**, after the aim has set the length. Its
X and Y shape the cross-section, which is the intended use with an aim. A **Z** other than 1
multiplies the span, so the geometry no longer ends at `to`; that is legal, occasionally deliberate,
and warned about (`PWMODEL_AIM_AXIAL_SCALE`) rather than refused.

**Aiming is refused, never resolved, wherever two placements could be derived.** Half an aim
(`PWMODEL_AIM_INCOMPLETE`, which also covers `up=` with nothing aimed), an aim beside `at=` or
`rotate=` (`PWMODEL_AIM_CONFLICT`), two identical endpoints (`PWMODEL_AIM_DEGENERATE`), a second
spelling of the length (`PWMODEL_AIM_EXTENT_CONFLICT`) and a `up=` on the axis
(`PWMODEL_AIM_UP_PARALLEL`) are all errors from the **parser**, so `model.validate` reports them
without building a mesh. Only `PWMODEL_AIM_TOO_SHORT` comes from the compiler, because it needs the
capsule's radius default.

## Ops

A statement inside a part is an op: a bare identifier followed by `key=value` pairs.

```
bevel distance=2.5 segments=3
```

**The vocabulary is the extracted geometry verb set.** An op's name is its `geometry.*` verb minus
the namespace, and generator verbs additionally drop the `create_` prefix — `geometry.create_box`
is `box`, `geometry.bevel` is `bevel`. Get the authoritative list from `model.describe_ops`.

**Parameter names come from the `F<Verb>Params` struct that both front-ends compile against**, not
from the RPC handler's published names. There is exactly one parameter vocabulary and neither
front-end can drift from it. Where the RPC verb carries a legacy name for backward compatibility,
the handler translates it onto the struct; `.pwmodel` maps onto the struct fields directly. So
`geometry.create_box`'s `width`/`height`/`depth` is `size=(x, y, z)` here.

`actorName` has no struct field and simply does not exist in the format. The compiler builds on
transient meshes; no actor is ever spawned.

**The first op in a part must be a generator** — there is nothing to modify otherwise
(`PWMODEL_PART_NEEDS_PRIMITIVE`). An empty part is a warning.

### Path-driven ops

`sweep`, `extrude_along_spline` and `array_along_path` take a **frame list** — `path=[(x, y, z,
roll, pitch, yaw), …]`, position and rotation per frame, part-local, the same `(roll, pitch, yaw)`
ordering every other rotation in the format uses. `frame_list` is the only value kind that is not
also used by an older op; it exists because the widest fixed-arity list constraint the format had
was `point_list4`, and a frame needs six.

**There is no spline and no actor.** `geometry.sweep` and `geometry.extrude_along_spline` read a
`USplineComponent` off a named actor and sample it into exactly this frame list; the format writes
the frames directly instead. `steps` / `segments` therefore do **not** resample `path=` — they size
the fallback cross-section (and, for `sweep`, the fallback path). To follow a level spline, sample
it with `spline.*` and paste the frames in, or build the shape with `geometry.*` and accept the
result as detached (see [Provenance and the overwrite rule](#provenance-and-the-overwrite-rule)).

```
part rail {
    box size=(6, 6, 6)
    sweep profile=[(0, 0), (10, 0), (10, 40)] path=[(0, 0, 0, 0, 90, 0), (0, 0, 100, 0, 80, 0), (30, 0, 180, 0, 69, 0)]
}
```

Six things about `sweep` and `extrude_along_spline` that the names do not say:

- **The profile lands in each frame's local Y-Z plane; the sweep advances along the frame's local
  +X.** Measured: `extrude_along_spline profile=[(10,0),(10,4),(-10,4),(-10,0)]
  path=[(0,0,0,0,0,0),(200,0,0,0,0,0)]` gives a bar spanning x `0 … 200`, y `-10 … 10`, z `0 … 4`,
  so profile `u` is the frame's Y and profile `v` is its Z. **Frames left at rotation `(0, 0, 0)`
  on a curved path are therefore wrong** — the section holds one world plane while the path turns
  out of it and the tube comes back sheared. Write each frame's `(pitch, yaw)` as the path
  tangent's. For a helix of radius `r` climbing `h` per `a` degrees: `yaw = theta + 90`,
  `pitch = atan(h / (r · a_radians))`.
- **A frame whose local +X is PERPENDICULAR to the segment leaving it sweeps nothing, and both ops
  now say so.** The section slides along inside its own plane, and the span comes back as a flat
  slab: measured, the broken and the corrected form both compiled `success: true`, `isClosed: true`
  and `boundaryEdges: 0` at the same 26 triangles, differing only in 2 degenerate triangles and a
  bounding box with zero extent on one axis. The example above used to be one of the broken ones —
  frames at `(0, 0, 0)` with the path running up +Z. Two warnings name it, both opening with
  `path`: `path frame N sweeps inside its own cross-section plane …` and, when the sweep is the
  only geometry in the part, `path swept a flat result — the mesh has zero extent on X …`. Neither
  refuses the document; there is no substitute path to guess.
- **`cap` works, and `extrude_along_spline` loops only when the path returns to its start.**
  `extrude_along_spline` used to sweep every path as a closed loop, which made `cap` unreachable at
  every path length (`cap` omitted and `cap=true` were byte-identical) and turned an open 3-frame
  path into a tube running A→B→C→A. It now sweeps open unless the last frame comes back within
  0.01 uu of the first — write the ring's first point again as its last to get a loop. On a loop
  `cap`, `scale_start` and `scale_end` do nothing, because a loop has no ends, and the op warns
  saying so rather than leaving it to be discovered. `sweep` has always swept open and is
  unchanged.
- **They are modifiers and they APPEND.** The swept surface is added to the geometry already in the
  part; it does not replace it. Neither may open a part.

  **Being modifiers is also why `PWMODEL_UNUNIONED_OVERLAP` can never fire on them, and why one of
  them silences the check for the rest of the part.** The warning is raised only from the generator
  path (`PwModelCompiler.cpp:1129`), and every modifier *clears* the footprint list it compares
  against (`PwModelCompiler.cpp:2285`) — right in general, since a modifier may move or multiply
  geometry — so a part of deeply interpenetrating swept tubes compiles without a word, and in
  `box … sweep … box` the second `box` is compared against nothing. That makes the warning a
  positive signal only: it names a real pair when it fires, and its absence is not evidence. The
  same holds for `mirror` and the three `array_*` ops. `health.boundaryEdges` and a render are what
  cover a whole part.
- **Without `profile=` the cross-section is a CIRCLE sized from the accumulated mesh's bounding
  box.** Neither op traces the mesh's outline. `profile=` is the way to get the section you drew;
  it is a `point_list2` in exactly the form `revolve` takes, and needs at least 3 points.
- **`scale_start` / `scale_end` interpolate LINEARLY, so `scales=` is how a section follows a
  law.** The two scalars are a straight ramp between the ends, which means a swept tube could
  taper only straight: a power-law taper, an exponential flare and a waist were all unreachable
  along a path. `scales=[(alpha, scale), …]` gives the scale as a piecewise-linear law instead —
  `alpha` is the **normalised position** along the path, 0 at the first frame and 1 at the last,
  not a distance in uu — and it is what the engine always accepted. Both ops build one
  `FTransform` per frame and the scale slot has always been per-frame; only the caller's two
  scalars were not.

  ```
  # r(t) = 22 + 52*(1-t)^1.45, sampled at five stations and normalised on r(0) = 74
  sweep profile=[…] path=[…] scales=[(0, 1), (0.25, 0.72), (0.5, 0.48), (0.75, 0.28), (1, 0.3)]
  ```

  The rules, each refusing rather than repairing because each repair would be a guess: at least
  **2 knots**; `alpha` **strictly ascending** within `[0, 1]`; every `scale` **positive**. A
  non-positive scale is the one worth knowing about — `0` collapses the section onto the path and
  a negative one **reflects** it, which reverses the swept tube's facing normals while
  `isClosed`, `boundaryEdges` and the triangle count all stay identical. Outside the outermost
  knots the law is **held, not extrapolated**, for the same reason: extrapolating a curve that
  stops at `alpha 0.9` is exactly how it reaches a negative scale at `1.0`.

  `scales` together with `scale_start` or `scale_end` is an **error**, not a precedence rule —
  only one can be honoured, and accepting the pair would leave the scalars looking set while the
  curve silently won. Write the endpoints as the curve's first and last knot instead. The two-knot
  curve `[(0, a), (1, b)]` is exactly `scale_start=a scale_end=b`, so `scales` is a superset
  rather than a second dialect.

  Like `steps`, it **does not resample `path=`**: alpha is evaluated at the frames you wrote. And
  like `cap`, it is **dropped on an `extrude_along_spline` path that returns to its start** — the
  engine's loop branch gates path scaling off entirely — where the op warns rather than leaving
  it to be found.

  There is no RPC spelling. `geometry.sweep` and `geometry.extrude_along_spline` carry no way to
  hand over a list of knots, the same position `profile=` is in.
- **They take `material=`, and untagged they INHERIT the slot of the geometry they append onto.**
  These two are the only modifiers that carry the tag, and they carry it for the same reason
  `append_triangle` and `append_buffers` do: they produce triangles of their own, and triangles
  need a slot. `material="<Slot>"` resolves through the model-wide table exactly as on a shape
  primitive.

  Written without it, the appended surface takes the material slot of the geometry already in the
  part. That is the answer an author means by putting a sweep after a tagged generator, and it
  costs no slot — the id already exists in the table, so `materialSlots` is unchanged.

  **When the geometry it appends onto carries more than one slot there is no single answer**, so
  the op takes the slot **most** of that geometry is on (ties to the lower index, so the choice is
  stable) and raises `PWMODEL_MODIFIER_MATERIAL_AMBIGUOUS` naming the candidates and the one it
  picked. The same code covers the other unanswerable case: a sweep with **no** geometry in front
  of it — a `procedural_mesh` that appended nothing — whose triangles keep material ID 0.

  **ID 0 is not a neutral default**, which is why the untagged case needed a rule at all. The slot
  table is model-wide and allocated in first-use order, so ID 0 is whichever slot the *first part
  in the document* tagged. Before inheritance, every swept triangle landed there: part `a` tags
  `Alpha`, part `b` tags only `Beta` and sweeps, and the swept rod came back on **`Alpha`** — one
  part rendering in two materials, on a green compile, with the slot count unchanged and no
  diagnostic anywhere. The workaround was to reorder parts so the wanted slot fell at index 0,
  which breaks the moment a part is added above it. `bridge` and `fill_holes` still carry no tag
  and are unchanged by this: they close faces into an existing shell rather than build a shape of
  their own, and they remain the ops with no answer here.

  `color=` is a separate parameter and these ops still do not take it, which is the one case where
  `set_vertex_color set_all=true` is not redundant: swept geometry has no other route to a vertex
  colour.

`steps` / `segments` reach the fallback circle as `clamp(n / 2, 4, 32)` sides — **halved, and
clamped silently**, unlike every count in [Segment counts below the engine's
floor](#segment-counts-below-the-engines-floor), which warn. It is the shipped behaviour of
`geometry.sweep`; `profile=` is the way to stop guessing at it.

**On `sweep`, `steps` has a second job the name does not carry**: it is also the step count of the
**vertical fallback path** the op sweeps when `path=` is omitted. One parameter therefore sizes two
different fallbacks, and a document that supplies `profile=` but no `path=` is using only the second
of them. `extrude_along_spline`'s `segments` has no such role — that op has no path fallback and
requires `path=`. **Neither ever resamples an authored `path=`**: the frames are taken as written.

`sweep` with no `path=` sweeps vertically through the mesh's own bounding box — the fallback
`geometry.sweep` runs when its spline actor resolves to nothing. `extrude_along_spline` **requires**
`path=`, because it has no fallback and produces nothing without one. A `path=` that is present but
carries fewer than 2 frames is `PWMODEL_OP_FAILED`, not a silent fall back to a shape the document
does not describe; the ceiling is **257 frames**, which is the 256-step spline sampler's reach
(`GeometryOps::SplinePathStepCount`) and is read out of that function rather than re-typed.

`array_along_path` is the third member of the `array_linear` / `array_radial` family and the only
one with no `geometry.*` verb behind it (`geometry.duplicate_along_spline` duplicates *actors* and
never touches mesh data). **The frame list is the count**: N frames produce exactly N copies, so a
leading `(0, 0, 0, 0, 0, 0)` keeps a copy where the original stood and the original is not
additionally left in place — the same rule as `array_linear`, whose original occupies the first of
its `count` positions. 1 to 100 frames.

Two things about frames that the parameter description does not say, both found the hard way while
writing the first example to use the op:

- **A frame places the accumulated mesh's ORIGIN**, not its centre and not its bounding-box centre.
  A generator authored around its own origin lands exactly where the frame puts it; one authored
  with its origin partway along itself — `revolve profile=[(0, -16), …]`, a `box … at=(0, 0, 40)`
  — lands that offset away from it. On `array_along_path` this is usually the difference between
  copies that sit on a surface and copies buried inside it, and it fails silently: the compile is
  clean and the copies are simply somewhere else.
- **The frame list must be on ONE LINE.** The [Lexical](#lexical) section already says a
  tuple or list may not span lines, and this is where that rule is felt: a frame is six numbers,
  `array_along_path` takes up to 100 and `extrude_along_spline` up to 257, so a real path is a
  single line thousands of characters long. A list broken across lines is
  `PWSRC_UNEXPECTED_TOKEN` naming a missing `,` or `]`, reported at the end of the first line.
  Past a handful of frames, generate the line rather than typing it.

### `loft` is not in the op table

`loft` reports `PWSRC_UNKNOWN_OP`, and this is a deliberate omission rather than a gap waiting on
a value kind.

`geometry.loft` does not blend between authored profiles. It reads each profile actor's **world
location** and its mesh's **bounding-box extent**, derives a **circular** cross-section from
`Profiles[0].Extent` — the first profile's, and no other's — and sweeps that one circle through the
locations. Ported honestly it would be "sweep a bounding-box circle through a list of points",
which `sweep path=[…]` already does with a rotation per frame, an authored `profile=`, twist and
scale. Ported under the name `loft` it would promise cross-section blending the code does not have.

A real loft needs a list of profiles — a list of lists of points — and `FPwModelValue` carries
`Tuple` and `TupleList` and nothing deeper, so it has no literal. That is the one shape the value
grammar still cannot hold, and a nested-list value kind is **deferred past `pwmodel 0`**: adding
one before a real model has exercised the kinds that exist would freeze a shape nothing has used.

### Nested blocks

Boolean ops take a block whose ops build the tool mesh:

```
subtract {
    sphere radius=18 at=(25, 0, 0)
    bevel distance=1
}
```

The block is a full op list — it may itself contain a generator, modifiers, and further nested
booleans. The tool mesh is discarded after the operation.

`model.describe_ops` reports `acceptsBlock` per op.

### `material=` and `color=`

Most geometry-*producing* ops additionally accept:

- `material="<Slot>"` — assigns the geometry it creates to the named slot (see [Materials](#materials)).
- `color=(r, g, b, a)` — writes the per-corner vertex color overlay (see [Vertex color](#vertex-color)).

`append_buffers` and `append_triangle` each take `material=` and **not** `color=`. Both open a
part like any other generator. `sweep` and `extrude_along_spline` take `material=` and not `color=`
as well, and are the only *modifiers* that take either — see [Path-driven ops](#path-driven-ops)
for the rule that applies when they are left untagged.
`model.describe_ops` reports `acceptsMaterial` per op — read it there rather than assuming.

`color=` is withheld from `append_buffers` because the op already carries a per-vertex `colors=`
buffer and the scalar is applied to *every* vertex, so the two on one op would silently overwrite
what the author supplied. `append_triangle` carries no such buffer and is withheld from `color=`
only because nothing has needed it; ask if you do.

**`append_buffers` accepts two mutually exclusive ways to say which material its triangles use.**

- `material="<Slot>"` — the slot table, exactly as on every shape primitive. This is the one to
  reach for.
- `material_id=<n>` — a **raw** index written straight onto the triangles, bypassing the table. It
  exists for a generator that already computed IDs. The index is into the model-wide slot list in
  first-use order, which a document cannot see, so an ID past the end pads the list and warns
  (`PWMODEL_MATERIAL_ID_OUT_OF_RANGE`).

Both on one op is `PWMODEL_MATERIAL_ID_CONFLICT`, an error. Only one can be honoured, and the
compiler's tie-break honours `material_id` in silence — so accepting the pair would leave the named
slot doing nothing while looking like it worked.

**`append_triangle` takes `material=`; an untagged patch still opens `Default`.** It resolves
through the same model-wide slot table every shape primitive uses, and it is the only spelling —
`append_triangle` does not take `material_id=`, so `append_buffers` remains the one op with both.
There is no fall-through to slot index 0: an `append_triangle` with no `material=` allocates the
implicit `Default` slot, exactly like every other untagged generator.

That parameter is new, and the defect it closes is worth keeping in view because nothing in a
count showed it. Measured on `Examples/pwmodel/mobius_band.pwmodel` before the fix: a part carrying
`material="Cast"` on both `procedural_mesh` and `append_buffers`, patched with twelve
`append_triangle` ops, compiled to `materialSlots: 2`, and `static_mesh.describe` named them

    [ { slot: "Cast",    path: "…/BasicShapeMaterial" },
      { slot: "Default", path: "…/WorldGridMaterial"  } ]

— the twelve patch triangles shipped rendering in the grid material while the rest of the part
rendered in the bound one, because the op had no way to say what it was made of. Tag the patch and
the model is single-slotted. A part that patches an untagged surface still gets `Default`, which is
correct and is what `materials { Default = "…" }` binds.

### What a boolean does to material slots

**Three rules, and they are the whole contract:**

1. **Triangles the operation KEEPS carry the slot they arrived on.** A boolean never recolours
   geometry. Cutting a bore in a `Barrel`-tagged block leaves every surviving triangle of that
   block on `Barrel`.
2. **Ops inside the block resolve `material=` through the same model-wide slot table** a part-level
   op does. `union { box material="Beta" }` puts the unioned box on `Beta`; `subtract { cylinder
   material="Bore" }` puts the walls that cut opens on `Bore`, because those walls *are* the tool's
   surface. **That shared table is the whole of the ID-space reconciliation** a boolean needs —
   both operands index one table, so the operation's own attribute transfer carries the ids across
   and nothing is remapped afterwards.
3. **`material=` on the boolean itself names the faces the operation CREATES** — the walls a
   `subtract` opens, the tool surface a `union` keeps, the caps `fill_holes` closes. It is the only
   spelling a cut's walls have, since they have no op of their own to tag. Untagged, those faces
   **inherit the slot of the geometry the boolean was applied to**.

Where that geometry carries more than one slot there is no single answer, so the op takes the slot
**most** of it is on (ties to the lower index, so the choice is stable) and raises
`PWMODEL_BOOLEAN_MATERIAL_AMBIGUOUS` naming the candidates and the one it picked. A boolean applied
to an empty mesh has nothing at all to inherit, and its faces keep material ID 0 — the same code,
the other message.

A tag that reaches no triangle of the result is `PWMODEL_BOOLEAN_MATERIAL_UNUSED`. The realistic
source is a **tool solid the operation discards entirely** — most often one that misses the target
while the rest of the block hits it, so the boolean itself reports nothing wrong and only that one
tool is dead. Note this is *not* `trim`: `trim` dispatches the same engine boolean as `subtract`,
so its tool surface becomes the cut face and a tag on it lands on real geometry.

**ID 0 is not a neutral default**, which is why every clause above needed writing down. The slot
table is model-wide and allocated in first-use order, so ID 0 is whichever slot the *first part in
the document* tagged. Before these rules, everything a boolean produced landed there: measured on
an 18-part rifle, **18,559 of 21,420 triangles** shipped on the first part's material — the barrel,
the gas block and every bevel rendering as receiver aluminium — while `materialSlotList`, the
source tags and `static_mesh.describe` all reported the model as correct.

**Booleans still reject `color=`** with `PWMODEL_MATERIAL_ON_BOOLEAN`, and the asymmetry with
`material=` is the decision rather than an oversight: a boolean creates faces but no *vertices*.
Every vertex in the result comes from one of the two operands and already carries the colour its
generator gave it, so a scalar `color=` here could only overwrite what the author already wrote.
Write `color=` on the generators inside the block, or `set_vertex_color` after the op.

### A boolean that changes nothing is an ERROR

The engine returns the target unmodified when the operands are disjoint. That is not advice: the
author asked for material to be removed, none was, and the geometry that would reach the asset is
not the geometry the document describes. `PWMODEL_BOOLEAN_NO_EFFECT` names the op and its line, and
it **aborts the part** — nothing is created, exactly like an op that failed outright.

It shipped as a warning, and that is how twelve visibly broken examples compiled green:
`pipe_junction`'s two `subtract` bores both reported "changed nothing" while `model.compile`
answered `success: true` for a pipe with no hole through it.

### Warnings the compiler emits on ops

**Every warning below names the parameter as this format spells it**, never as the `geometry.*` RPC
spells it. The geometry layer these warnings originate in is shared with the RPC and labels them
with the RPC's parameter name — `heightSteps`, `numSteps`, `widthSegments` — so the compiler
translates the leading name on re-emission. Where one `.pwmodel` vector is three RPC scalars the
translation keeps the vector and adds the axis: `box size=(0, 0, 0)` reports `size.x`, not `width`.
See [Divergences from engine naming](#divergences-from-engine-naming) for the full mapping.

- **Clamping.** Where a dimension or segment count is clamped to the geometry layer's limits, the
  op warns rather than silently altering the value. Every generator's segment counts are clamped at
  this layer, each against its own engine floor; see
  [Segment counts below the engine's floor](#segment-counts-below-the-engines-floor).
- **`bevel` operates on polygroup edges only, and warns at both extremes.** A mesh with no
  polygroups is returned unchanged. A mesh carrying roughly one polygroup per quad — the warning
  fires at ≥ 32 distinct groups *and* `groups * 3 >= triangles` — has every interior quad boundary
  chamfered instead of its silhouette edges. See
  [Polygroups, and what `bevel` actually chamfers](#polygroups-and-what-bevel-actually-chamfers).
- **`extrude` with no face filter selects the whole mesh**, which *duplicates* a closed solid
  rather than thickening it.
- **A `face_direction` that matches NO face makes the op do nothing**, on all four of `extrude`,
  `inset`, `outset` and `offset_faces`, and warns naming the direction, the `face_angle_tolerance`
  used and the mesh's triangle count. It does **not** fall back to the whole mesh: an empty engine
  selection means "the whole mesh" only because no filter was given, and reading it that way for a
  filter that is satisfied by nothing is how a mistyped axis silently operated on an entire part.
  A `face_direction=(0, 0, 0)` warns too — it cannot describe a normal and is read as `+Z`.
- **`extrude` / `offset_faces` with a MATCHING `face_direction` on an OPEN mesh** warn that the
  result is less closed than the unfiltered call. Only a selection covering a *complete connected
  component* is capped into a solid, so unselected faces stay flat with no side walls and a partial
  component is skirted rather than closed. Measured on an open two-sided sheet: 24 triangles
  unfiltered against 14 filtered. This is the engine's contract for a sub-region, not a defect the
  compiler can repair — drop the filter to close the whole sheet, or use `shell`. A closed mesh
  does not trip it.
- **`spherify` / `cylindrify` on strongly oblong source geometry** warn that the radial map is
  anisotropic, naming the bounding box, the factor, the resulting min/max radial scale and the
  remedy. The threshold is `factor · (Emax/Emin − 1) > 1/3`, measured perpendicular to `axis` for
  `cylindrify`. **This is not a warning that the op folded the surface — neither op can.** Both
  are purely radial and radially monotone, and boxes up to 10:1 spherified at `factor=1` measure
  0 inverted, 0 degenerate and 0 self-intersecting triangles. What they leave is uneven triangle
  sizes, and the *next* op is what folds: a `noise_deform` whose magnitude approaches the local
  edge length self-intersects. Put a `remesh_uniform` between them, keep the source near-cubic, or
  lower the factor. Separately and not yet diagnosed: `cylindrify factor=1` (the default) is not
  injective and collapses any geometry near the axis — on a 100³ cube it produces 24 degenerate
  and 28 inverted triangles where `factor=0.82` produces none.
- **`collision { auto } max_hulls=` is the old spelling of `max_hulls_per_component`** and warns
  naming the rename; supplying both warns too, and `max_hulls_per_component` is the one that runs.
  A third warning fires whenever the generated element count exceeds the budget, naming the budget,
  the element count and the merged mesh's connected-component count. See [`auto`](#auto).

### Ops that refuse a mesh with no UVs

`shell` on an **open** mesh and `bevel` on any mesh both fail with `NO_UV_ELEMENTS`, reported as a
line-anchored `PWMODEL_OP_FAILED` diagnostic. This is a crash guard, not a style rule: both engine
routines rebuild UVs across the geometry they create and dereference the primary UV overlay without
checking it, so the unguarded call **terminates the editor** with an access violation rather than
returning an error.

The two ops ask different questions of the same overlay, because they read it differently:

| Op | Refuses when | Why that question |
|---|---|---|
| `shell` (open mesh only) | UV channel 0 is absent, empty, **or set on only some triangles** | The boundary stitcher reads a *specific* triangle's UV elements with no `IsSetTriangle` check, so a half-filled channel indexes the element array out of range exactly as an absent one does. |
| `bevel` (any mesh) | there is no UV layer or no normal layer at all | Its UV routine *writes* before it reads, and its one read of existing UVs is `IsSetTriangle`-guarded, so an empty or partly-set layer is safe. Only the zero-layer shape crashes. |

An **empty** mesh is exempt from both. `shell` on a mesh with no triangles succeeds with a warning
and changes nothing - there is no boundary to stitch, so the crash cannot occur, and
`procedural_mesh` followed by `shell` must not be told to add UVs to a mesh that has no triangles to
put them on.

The state is reachable from ordinary text. `append_buffers` with no `uvs=` leaves the mesh with no UV
layer at all — the engine call behind it sets the target's layer count to exactly the number of UV
sets it was handed — so this document used to kill the editor on compile:

```
part nouv_shell {
    procedural_mesh
    append_buffers vertices=[(0,0,0), (100,0,0), (100,100,0), (0,100,0)] triangles=[(0,1,2), (0,2,3)]
    shell thickness=5
}
```

**`shell` also refuses a mesh whose UVs cover only *part* of it**, and that state is reachable from
text just as ordinary as the one above:

```
part partial_uv {
    plane size=(100, 100)
    append_buffers vertices=[(500,0,0), (600,0,0), (600,100,0)] triangles=[(0,1,2)]
    shell thickness=5
}
```

The `plane` fills UV channel 0; the appended triangle carries no UVs and is left *unset* in that
same channel. The channel therefore has elements — enough to satisfy any "does this mesh have UVs"
test — while the engine's per-triangle read of the appended triangle still runs off the end of the
element array. `append_triangle`, `bridge` and `edge_split` add triangles the same way, so the same
document shape reaches the same state through any of them.

Fix it by giving the mesh UVs first — supply `uvs=` on the append, or run a `uv mode=box` op before
the `shell` / `bevel`. A **closed** UV-less mesh still shells: the engine only stitches along
boundary loops, and a closed mesh has none, so the crash is unreachable and the op is left alone.

The compiler's own box-projection fill runs at the *merge* stage, after every part's ops, so it
cannot rescue an op that needs UVs while it is running — and for the *partial* case it does not
rescue the mesh at all, because it skips any channel that already carries elements. A part that
mixes UV-carrying generators with UV-less appends therefore bakes with some triangles unmapped.

**The same engine call used to destroy UVs the document never touched.** Because it sets the
target's UV layer count rather than merging into it, `box size=100` followed by an `append_buffers`
with no `uvs=` deleted the *box's* UVs as well. `append_buffers` now pads the incoming buffers with
placeholder `(0,0)` UV sets whenever the mesh already carries UV data, so nothing is lost, and warns
that it did. Pass `uvs=` when the appended geometry needs real ones. A mesh whose UV layers are
*empty* has nothing to preserve and is not padded — which is why the crashing document above still
reproduces its UV-less state, and why the guard is still needed.

### The element-edit ops, and what an index costs

`set_vertex_position`, `append_vertex`, `delete_vertex` and `delete_triangle` are the only
constructs in `pwmodel 0` that address geometry by index; `convex points=[…]` is the only other
place explicit mesh data appears. Together with `procedural_mesh`, `append_buffers` and
`append_triangle` they form the **machine-generated tier** — a generator emits them and the whole
block is regenerated together or not at all. The wiki page `model.explicit-geometry` carries the
authoring guidance; the semantics that belong here are these.

**Ids come from the emission order, and nothing pins that.** [Reproducibility](#reproducibility)
lists vertex and triangle order under "Not guaranteed, and do not assume". Measured on UE 5.8: a
fresh `procedural_mesh` filled by one `append_buffers` hands out ids in supply order, so triangle
`k` of the supplied list is id `k`. Appends never disturb existing ids. **Deletes leave the id space
sparse rather than renumbering**, so an id taken before a delete is still valid after it — the one
exception is `uv mode=xatlas`, which compacts and renumbers (see [UV](#uv)).

**`delete_triangle` already drops the vertices it orphans, so `delete_vertex` after it is a no-op.**
The engine's triangle removal deletes isolated vertices as it goes, so by the time the last
triangle of a patch is gone its interior vertex is gone too. Naming that vertex is harmless and
reported:

    PWMODEL_VERTEX_ALREADY_REMOVED  'delete_vertex' names vertex 4, which the mesh no longer
                                    carries …

There is still no way to strand a vertex by deleting triangles, so the cleanup has nothing left to
do — but writing it no longer aborts the compile, which it did (`PWMODEL_OP_FAILED` carrying
`INVALID_VERTEX`) over work the engine had already done and that no document can see. The no-op
covers **only** an id that is sparse-but-present: deletes leave the id space sparse rather than
renumbering, so an id below the mesh's `MaxVertexID` was a vertex once, and an id at or above it
never was and is still a hard failure.

`delete_vertex` is otherwise a *cut* op — it removes the vertex and its whole triangle star — and
on a quad grid triangulated on one diagonal that star is **six** triangles with a sheared
six-vertex one-ring, not the eight an unsplit quad neighbourhood suggests.

**`append_triangle` takes three positions, not three ids.** No op in the format builds a triangle
from vertex ids, so a patch laid against existing geometry duplicates the positions it meets and
needs `weld_vertices` afterwards to become one surface. The weld matches coincident *edges* and
succeeds only because both sides parse to identical doubles — regenerate the patch whenever the
geometry it meets moves. A patch that fails to weld leaves boundary edges and no count reports it;
`health.boundaryEdges` (see [Mesh health](#mesh-health)) is the signal.

**`PWMODEL_UNUNIONED_OVERLAP` never fires on `append_triangle`**, or on any other op whose geometry
has boundary edges. The check compares sibling bounding boxes, and the boxes of two triangles
sharing an edge always interpenetrate — a twelve-triangle patch produced nine of these warnings on
`Examples/pwmodel/mobius_band.pwmodel`. Its remedy, wrapping the second op in `union { }`, cannot
apply to a triangle, which encloses no volume. Both operands must now be closed; see the
[diagnostics table](#diagnostics) for what that trades away.

### Warp deformers repair the normal overlay before they run

`bend`, `twist` and `taper` each drive an engine space-deformer op, and all three of those ops walk
the mesh's primary normal overlay with the same unchecked pair of lines: an element passes
`IsElement`, and its **parent vertex** then goes straight into `FDynamicMesh3::GetVertex`.
`IsElement` does not imply a parent — an element that was appended and never assigned to a triangle
answers `-1` — and `GetVertex`'s bounds test is compiled out of a Development build over an index
type that is unsigned, so `-1` reads out of bounds at a fixed offset. That is an
`EXCEPTION_ACCESS_VIOLATION` inside a `ParallelFor`, no assert and no error return: **the editor
process dies mid-compile and the caller sees only a truncated stream.**

**The three ops now free those orphaned elements themselves and carry on**, warning that they did.
They do *not* refuse, and that is deliberate: an unparented element is a legal engine-produced state
— the overlay API documents `FreeUnusedElements` as its own cleanup, and building a mesh from a
shape generator leaves one behind for every generator normal no triangle referenced — it carries no
geometry by definition, and no `.pwmodel` op could clear it. Refusing would reject valid input.

The one shape they **do** refuse is a mesh whose attribute set has *no normal layer at all*: the
same engine ops dereference the layer pointer before they reach any element, which is a null
dereference one step earlier. That fails with `INVALID_NORMAL_OVERLAY` in a line-anchored
`PWMODEL_OP_FAILED`; add a `recalculate_normals` op before the deformer. No op in this format is
known to produce that state, so the arm exists to make the crash impossible rather than to reject
anything reachable.

Note for anyone re-deriving this: the trigger is **not** the deformers' `extent`. An extent many
times larger than the mesh's own half-height is ordinary input — the span reaches the deforming math
only through a value clamped to `[0, 1]` — and the crash reproduces at any extent once the overlay
carries an orphan.

### Segment counts below the engine's floor

Every `Append*` primitive floors its own segment counts internally and reports nothing, so a
below-floor value used to compile successfully while the geometry ran at a number the author never
asked for: `cylinder segments=0`, `=1`, `=2` and `=3` all returned the same 18-triangle triangular
prism, and `segments=-5` did too. Every count below is now clamped **and warned** at this layer,
each against the engine's own floor read out of `MeshPrimitiveFunctions.cpp` — the floors are not
uniform, and guessing 3 for all of them is wrong three ways:

| Op | Parameter | Engine floor | `<= 0` falls back to |
|---|---|---|---|
| `box` | `segments` | 0 (see below) | 0 (legal — no subdivision) |
| `sphere` | `subdivisions` | 2 | 16 |
| `cylinder`, `cone` | `segments` | 3 | 16 |
| `cylinder`, `cone` | `height_steps` | 0 | 0 (legal — no intermediate loop) |
| `capsule` | `segments` | 3 | 16 |
| `capsule` | `hemisphere_steps` | **2** | 4 |
| `torus` | `minor_segments` | 3 | 8 |
| `torus` | `major_segments` | **3** (a torus always closes — see below) | 16 |
| `arch` | `minor_steps` | 3 | 8 |
| `arch` | `major_steps` | **2**, or **3** at `angle=360` (see below) | 16 |
| `disc` | `segments` | 3 | 16 |
| `ring` | `segments` | 3 | 32 |
| `pipe` | `radial_steps` | 3 | 24 |
| `pipe` | `height_steps` | 0 | 0 (legal — no intermediate loop) |
| `plane` | `subdivisions` (both axes) | 0 | 0 (legal — a single quad) |
| `stairs`, `spiral_stairs` | `num_steps` | 1 | 8 |
| `revolve` | `steps` | **2**, or **3** at `angle=360` — its default (see below) | 16 |

The two-tier behaviour is the whole family's, not a special case: a value `<= 0` reads as *unset*
and takes the verb's default, while a positive value under the floor reads as a typo and is raised
to the floor. Both warn, naming the value passed and the value that ran.

`height_steps` counts **additional** wall loops rather than the total, on `pipe` exactly as on
`cylinder` and `cone` (`SweepGenerator.cpp:547`, `FCylinderGenerator::LengthSamples`) — which is why
0 is legal there and means one wall segment, not none.

Every one of these is also capped and warns there. The cap is not a taste judgement:
`GeometryUtils.h`'s stated purpose for the constant is preventing OOM, and until this sweep the
radial counts reached the engine ungated, so `segments=1000000` was an unguarded allocation on
the one code path the limit exists to guard.

The ceiling is `GEOM_MAX_SEGMENTS` (256) for every count **except** `stairs` / `spiral_stairs`
`num_steps`, which is `GEOM_MAX_STAIR_STEPS` (400). A step count is not a segment count and had
been taking the segment ceiling by inheritance, which capped a 300-step staircase for no measured
reason. 400 is measured: the solid stair generator builds each side as a filled silhouette
(`NumQuadsPerSide = TriangleNumber(NumSteps)`, `StairGenerator.cpp`), so it costs `2n^2 + 10n`
triangles — 324,000 at 400 steps, inside `GEOM_MAX_TRIANGLES_PER_DYNAMIC_MESH`, where 512 steps
would be 529,408 and breach it on its own. `floating=true` uses a different generator that is
linear (`16n - 4`) and never approaches either number.

`box` `segments` is the one count whose ceiling was **not** measured that way, and it does not
survive the same arithmetic. `FGridBoxMeshGenerator` draws `2 * 3 * (n - 1)^2` quads, so
`segments=(256, 256, 256)` — every axis exactly at `GEOM_MAX_SEGMENTS`, and warning-free once
clamped — is 390,150 quads, 780,300 triangles, and fails the merge with `PWMODEL_MESH_TOO_LARGE`.
The clamp therefore advertises a ceiling `box` alone cannot reach on all three axes at once: two
axes at 256 with the third at 1 is 262,140 triangles and fits. Neither limit is wrong — they are
independent guards — but a document that maxes a box out is rejected *after* being told its
segment counts were in range.

`plane` and `box` are the two entries whose floor is 0 *and* whose 0 is meaningful and honoured:
`plane subdivisions=(0, 0)` is a single quad with no interior loop and `box segments=(0, 0, 0)`
is an unsubdivided cube, where `cylinder segments=0` is read as unset. `AppendBox` floors its
counts at 0 exactly as `AppendRectangleXY` does (`GridBoxGenerator.EdgeVertices = FMath::Max(0,
StepsX)`, `MeshPrimitiveFunctions.cpp:236`), so `box` now takes the same bare range clamp the
plane takes.

**`box` used to route through the `<= 0` default substitution instead, and this section used to
call that a silent extra subdivision. It was not one.** Both counts are VERTICES PER EDGE, and
both generators raise them to 2 before doing anything — `N.A = FMath::Max(2, N.A)`
(`GridBoxMeshGenerator.h`), `WidthNV = (WidthVertexCount > 1) ? WidthVertexCount : 2`
(`RectangleMeshGenerator.cpp:28`). So `0`, `1` and `2` all build the same minimum mesh and `3` is
the first value that adds a quad along an edge. The substitution's real cost was a WARNING about
a change it had not made, on a value the author was entitled to pass — which is why correcting it
changed no existing document's geometry, contrary to what was recorded here.

The same reading applies to every row above: these columns say *segments* because the parameters
do, but the engine counts vertices, so the effective minimum is 2 wherever the floor reads 0.

`stairs` / `spiral_stairs` `num_steps` and `revolve`
`steps` are echoed back by their RPC verbs, and before the clamp ran there those echoes reported
the requested value for geometry the engine had already floored — `num_steps=0` answered
`numSteps: 0` for a one-step staircase.

`hemisphere_steps` floors lower than the radial counts because it steps a half-arc profile rather
than a closed loop, and `arch major_steps` / `revolve steps` floor lower **on a partial sweep**
because they drive the revolve generator (`Steps = Max(Steps, 2)`) rather than a profile circle.
A torus's two counts therefore do **not** share a floor for the same reason even though both read 3.

**The floor of a revolve follows its sweep angle: 2 below 360, 3 from 360 up.** The engine's own
floor is 2 everywhere, and that is right for a *partial* sweep — `arch major_steps=2 angle=180` is
a sound half-arch, because its sweep does not close, and it is left exactly as written. A **closed**
revolution at 2 cannot close, so `torus major_segments` (always a full turn), `arch major_steps` at
`angle=360` and `revolve steps` at `angle=360` (its default) clamp to 3 and warn like every other
clamp: `major_segments clamped from 2 to 3 (valid range 3-256)`.

Before that conditional floor existed, both degenerate documents compiled `success: true` with **no
warning at all** — correctly, since nothing was clamped: 2 was inside the published range. The only
diagnostic was the merge-stage `PWMODEL_MESH_NOT_CLOSED` (and `PWMODEL_DEGENERATE_GEOMETRY` for the
revolve), which names the symptom one stage after the cause and never mentions the parameter.
What that produced, measured on this build with `model.validate`:

| Document | Triangles | Boundary edges | `isClosed` | Degenerates |
|---|---|---|---|---|
| `torus major_segments=2 minor_segments=8` | 16 | 16 | **false** | 0 |
| `torus major_segments=3 minor_segments=8` | 48 | 0 | true | 0 |
| `revolve steps=2 angle=360` (4-point profile) | 8 | 10 | **false** | **6** |
| `revolve steps=3 angle=360` (same profile) | 24 | 0 | true | 0 |

**Three is the first value that closes either**, which is why 3 is the floor and not a
recommendation. The two rows at 2 are no longer reachable: those documents now compile at 3 with a
clamp warning naming the parameter, and the `false` / `6` columns are what they used to produce.
`arch major_steps=2 angle=180` is unaffected and still compiles silently.

`sphere subdivisions=1` was the first of these to be given a floor — `AppendSphereBox` draws the
identical 12-triangle cube for 1 and for 2, and the default substitution only fires at `<= 0`, so
`1` was accepted and did nothing. The rest of the table followed for the same reason.

### `harmonic_deform` is a period, where `noise_deform` is a field

Both displace vertices and neither is spelled like the other on purpose. `noise_deform` samples a
spatial Perlin field: the displacement of a vertex is a pure function of its **position**, so it
has no period and repeats nowhere. `harmonic_deform` is the opposite — the displacement is a pure
function of the vertex's **azimuth about an axis**, so it repeats exactly `order` times per
revolution and is identical at every height and every radius along that azimuth. A shape that
needs both an azimuthal period and variation along the axis is this op plus a warp deformer, not a
parameter on either.

`terms=[(order, amplitude, phase), …]` is the whole vocabulary, and it is a list of literals
because the format has no variables, loops or expressions (see [What the format deliberately is
not](#what-the-format-deliberately-is-not)). The sum is
`Σ amplitude · sin(order · θ + phase)`.

**`amplitude` changes units with `target`, and the split is deliberate.** On `target=radial` it is
a **fraction** of the vertex's own perpendicular radius, so the map is
`radius ← radius · (1 + Σ)`; a scallop authored that way stays proportional as a revolve profile's
radius changes along the axis, which is what a conifer's tiers need. On `target=axial` it is
**Unreal units** added to the axis coordinate, because an axial displacement has no local scale to
be a fraction of. A rim that alternates in *both* radius and height is two `harmonic_deform` lines,
not one op with two amplitudes.

`order` must be a whole number of at least 1, and the parser refuses anything else with
`PWSRC_BAD_VALUE`. A fractional order is the one input that shrinking the amplitude cannot make
safe: the wave does not close on itself after a full turn, so the surface tears at the wrap however
small the amplitude is. Order 0 is a constant offset wearing a harmonic's clothes.

**Winding survives this op, by construction and not by luck.** The radial map is a strictly
positive scale of the perpendicular radius — it preserves each vertex's azimuth and axis
coordinate, so no triangle can reverse its facing normal — and the op **refuses** a radial
amplitude total of 1 or more, where that scale would reach zero and fold the surface through its
own axis. Vertices within a hair of the axis are left where they are on both targets, because
their azimuth is undefined and displacing an apex by the arbitrary `θ = 0` value is what tangles
the fan around it.

**`target=axial` has no equivalent ceiling and cannot have one** — the displacement is absolute, so
no bound on it bounds anything. Its own failure mode is different and is worst **nearest the
axis**: the shift per azimuth step is fixed in world units while the spacing between two adjacent
vertices shrinks toward zero as their radius does, so a pole-adjacent or axis-adjacent ring is
where an axial displacement first outruns its own sampling. Keep the amplitude small against the
smallest ring's circumference, or keep the deformed geometry away from the axis.

The one damage the bounds cannot rule out is **aliasing**, so it is measured instead. The op counts
the distinct azimuths actually present in the mesh — a `revolve steps=48` has 48 — and warns per
term whose `order` reaches half of them: past that limit the surface gets a different, lower-order
wave than the one requested, and the triangles between two badly separated samples can cross. The
fix is a higher segment count on the base primitive, not a smaller amplitude.

`center=` is a point on the axis in part-local space, defaulting to the origin. It is deliberately
**not** the bounding-box centre `spherify` and `cylindrify` fit to: this axis is the one the
geometry was revolved about, and a box-derived centre would move whenever an earlier op changed the
mesh's extent — so the same document would deform differently depending on what ran before it.

### Deformer extents

`twist`, `taper` and `bend` take an `extent` in world units that is a **symmetric half-extent
measured about the origin**: the deform spans `[-extent, +extent]` along its axis. A centred mesh
of height H is fully covered at `extent ≈ H/2`; the natural guess `extent = H` over-covers by 2×.
The semantics are the RPC verbs' semantics unchanged.

**`symmetric_extents=false` is the answer to a mesh that does not straddle the origin**, where a
symmetric extent always covers the wrong half. It switches the span to `[-lower_extent, +extent]`,
so the two ends are set independently. `lower_extent` is read only in that case — the engine field
was dead while `bSymmetricExtents` was pinned true.

`bend` and `twist` additionally take `bidirectional`. True (the default) centres the deform on the
origin and rigidly transforms the regions on both sides of the extents; false starts it at the
lower extent and leaves everything below untouched. **`taper` has no `bidirectional`** —
`FGeometryScriptFlareWarpOptions` carries no such field, which is why the three warps do not share
one parameter list.

### Nested engine option structs are flattened, not nested

`FPwModelValue` carries a number, a tuple, a tuple list, a string or an identifier and **nothing
deeper** — there is no map or sub-object member — so an engine option struct that nests another
cannot be spelled as a block. Two of them are reached anyway, by flattening into prefixed scalars:

| Engine struct | Nested in | Spelled here as |
|---|---|---|
| `FGeometryScriptMeshEditPolygroupOptions` | `extrude`, `inset`, `outset`, `offset_faces`, `poke` | `group_mode=`, `group_id=` |
| `FGeometryScriptGroupLayer` | `split_normals` | `use_default_group_layer=`, `group_layer_index=` |

Each has exactly **one** flattening for all its callers, so the five face ops cannot end up with
five spellings of the same engine field. `area_mode=` and `uv_scale=` are the other two fields
those five share and are plain scalars already.

### Engine options these ops deliberately do not publish

Each of these would reach the engine and provably change nothing, which is the defect an
option-widening pass exists to remove rather than create:

| Op | Field | Why it has no spelling |
|---|---|---|
| `outset` | `bReproject` | `ApplyMeshInsetOutsetFaces` reads `bReproject = (Distance < 0) ? false : bReproject`, and `outset` always passes a negative distance. `inset reproject=` is the one that works. |
| `bevel` | `bApplyFilterBox` | Derived from both filter-box corners being present — see above. |
| `bevel` | `FilterBoxTransform` | The box is already in mesh space — see above. |
| `smooth`, `relax`, `noise_deform` | `EmptyBehavior` | None of the three builds a selection; each passes a default-constructed one unconditionally. The default (`FullMeshSelection`) is what makes the op run on the whole mesh at all, and the only other value makes it an unconditional no-op on every possible input. It becomes a real parameter the moment these ops gain a selection, and not before. |

### Polygroups, and what `bevel` actually chamfers

**The mesh's polygroups *are* `bevel`'s edge selection.** There is no angle filter and no
silhouette filter — the op walks polygroup edges and bevels every one of them — so the result is
decided by whatever grouping the generator left behind. It fails at both ends of that range, and
both now warn:

| Grouping the mesh arrives with | What `bevel` does |
|---|---|
| None | Nothing. The call succeeds and returns the mesh unchanged. |
| Coarse (one group per face, wall or cap) | The intended chamfer, on the edges between those faces. |
| One group per **quad** | Chamfers **every interior quad boundary** — a grid of notches that reads as surface damage, at roughly 3× the triangle cost. One example model spent 30,000 triangles producing an artifact. |

Per-quad grouping is not a hypothetical shape someone has to construct. It is what the **revolved**
generators hand you:

| Op | Engine generator | Polygroups |
|---|---|---|
| `torus`, `arch`, `revolve` | `FBaseRevolveGenerator` | **one per quad** |
| `pipe` | `AppendRevolvePolygon`, then a PinWright pass | **four** — outer wall, bore, top rim, bottom rim |
| `box` | `FGridBoxMeshGenerator` | one per box face |
| `sphere` | `FBoxSphereGenerator` | coarse — the six box faces it is projected from |
| `cylinder`, `cone` | `FCylinderGenerator` | coarse — side wall plus caps |
| `capsule`, `stairs`, `spiral_stairs`, `ramp` | capsule / stair / extrude generators | coarse — a small fixed set, the same shape as above |
| `plane`, `disc`, `ring` | rectangle / punctured-disc generators | one, for the whole surface |

**Nothing on the PinWright side can coarsen the revolved case.** `AppendTorus`,
`AppendRevolvePolygon` and `AppendRevolvePath` never map `FGeometryScriptPrimitiveOptions::PolygroupMode`
onto `FBaseRevolveGenerator::PolygonGroupingMode`, which defaults to
`EProfileSweepPolygonGrouping::PerFace` (`SweepGenerator.h:308`) — and for a sweep "PerFace" means
one group per **quad**: `PolygonId = SweepIndex * NumProfileSegments + ProfileIndex`
(`SweepGenerator.cpp:764`). The only post-pass the engine applies is the `SingleGroup` collapse in
`ApplyPrimitiveOptionsToMesh` (`MeshPrimitiveFunctions.cpp:54`), which would remove **all**
polygroups rather than coarsen them. Worked example: `torus major_segments=16 minor_segments=8` is
128 polygroups over 256 triangles.

The grid, sweep and stair generators escape it because they read the enum only to detect `PerQuad`
(`MeshPrimitiveFunctions.cpp:237`, `:661`, `:1485`) and this compiler never passes it. `pipe` is
kept out deliberately: PinWright assigns its four groups itself after the sweep, classified by face
normal rather than by triangle index, so the count holds at any `radial_steps` / `height_steps`.

**`PerFace` is the engine default for every primitive here** (`MeshPrimitiveFunctions.h:59`), so
per-face polygroups are not a property one generator has and the others lack — what `PerFace`
*means* is what differs per generator family.

The warning's absolute floor of 32 groups is what separates the dense revolved surfaces from a
default `box`, which is 6 groups over 12 triangles — the same 1:2 ratio as per-quad grouping, and a
mesh anyone should bevel.

**`filter_box_min` / `filter_box_max` are the way out of the per-quad case**, and the only edge
filter the engine offers. They bound a box **in mesh space** that the bevelled edges must lie in,
so a box drawn round the silhouette chamfers the silhouette and leaves the interior quad
boundaries alone. Both corners are required: the filter applies when both are present and is off
otherwise, which is why there is no separate `apply_filter_box` — a flag with no box, and a box
with the flag off, are two spellings of a request that silently does nothing. `fully_contained`
(default true) admits only edges entirely inside the box; false admits any edge with one endpoint
in it. `FGeometryScriptMeshBevelOptions::FilterBoxTransform` is deliberately not published: the box
is already in the mesh's own space, so a transform on top of it adds no shape that moving the
corners cannot express, at the cost of four more parameters.

`bevel` separately refuses a mesh with no UV or normal layer; that is a crash guard, not this
condition — see [Ops that refuse a mesh with no UVs](#ops-that-refuse-a-mesh-with-no-uvs).

**The chamfer faces take the material of the surfaces they join**, and that is this format's
default rather than the engine's. `infer_material_id` defaults to **`true`** here: each new face
takes its slot from the two faces either side of its edge when they agree, which is what a chamfer
*is* — an edge break belongs to the surfaces it joins, not to a third material. Where the two sides
disagree the fallback applies, and the fallback is **the slot most of the geometry being bevelled
is on**, never a fixed index.

`material="<Slot>"` names the chamfer faces outright and turns inference off; writing
`infer_material_id=true` alongside it puts inference back and makes the named slot the
disagreement fallback. `material_id=<n>` is still the raw-index escape hatch, and both spellings on
one op is `PWMODEL_MATERIAL_ID_CONFLICT`. Existing triangles are never recoloured either way.

The engine's own defaults are `bInferMaterialID = false, SetMaterialID = 0`, and `0` is the one
value a document must not silently take: slots are a model-wide table in first-use order, so 0 is
whichever slot the *first part in the document* tagged. Measured across one project, **38 of 38
bevels written by three independent teams omitted `infer_material_id`** — including a six-slot
truck whose first-use slot was `Rubber`, so every chamfered edge on its paint, chassis, grille and
glass rendered as tyre rubber. That is a default set the wrong way round, not a choice anyone made.

### The clamped domain is published, and it is not the enforced one

`model.describe_ops` emits two different numeric domains per parameter and they must not be
confused, because acting on the wrong one rejects values the op accepts.

| Fields | Meaning | Outside it |
|---|---|---|
| `min` / `max` | **Enforced.** Checked by the parser before anything runs. | Refused — `PWSRC_BAD_VALUE`, naming the bound. |
| `clampMin` / `clampMax` | **Advisory.** The domain the op silently moves a value into. | **Accepted**, moved to the nearest legal value, and warned about. |

A clamped count therefore carries `clampMin` / `clampMax` and **no** `min` / `max`, deliberately.
Declaring its domain as an enforced range would turn every clamp into a refusal and destroy the
second tier these ops document: a value of **0 or less means "unset"** and takes the verb's own
default, which is legal, useful, and outside the clamped domain by construction. `clampUnsetDefault`
is that default, present only on the parameters that have the tier.

`clampMinClosedSweep` appears only where the floor genuinely depends on the sweep angle — a
revolution that closes wraps its last section onto its first, so it needs one more section than a
partial sweep does. `clampMin` is always the floor at the op's **own default angle**, so a caller
that ignores the extra field still gets the right number for the line it is most likely to write.

Both come from the ops layer's own declared table, whose test **runs** each op at its floor, one
below, at its ceiling, one above and at zero, and fails when a declared row stops matching what
the op does. They are not a third hand-written list.

## Materials

```
materials {
    Shell = "/Game/Materials/M_Metal"
    Trim  = "/Game/Materials/M_Rust"
}
```

The block **binds** slot names to material assets. It does not define materials: MGIR owns material
graphs, and a `UMaterialInterface` is isomorphic to its asset, so a generative format has no place
authoring one. The right-hand side is any `/Game/…` material or material-instance path.

**Slot identity is the name, model-wide.** Two parts tagging `material="Shell"` share one slot; two
parts tagging different names produce two. Slots are allocated in first-use order across the whole
document, and a slot needs no `materials` entry to exist — the entry only binds an asset to it.

**Because the order is model-wide, slot 0 is another part's material, not a neutral default.** That
matters wherever a slot is *not* named: geometry with no tag of its own must not simply fall to ID
0, or it ships in whichever material the first part in the document happened to tag. Untagged
*generators* open `Default` (below); the two appending modifiers, `sweep` and
`extrude_along_spline`, **inherit the slot of the geometry they append onto** and warn
`PWMODEL_MODIFIER_MATERIAL_AMBIGUOUS` when there is no single slot to inherit — see [Path-driven
ops](#path-driven-ops).

Slot **`Default`** is created **only if** some geometry is untagged. A fully tagged model has no
`Default` slot. It is the **one exception to first-use order: it is always the LAST slot**, after
every slot a `material=` tag names. It is therefore ID 0 only when it is the sole slot — the model
whose geometry is untagged throughout. The exception exists because every other slot's index is a
consequence of something the author wrote, while this one's would be a consequence of something
they did *not* write: an untagged op between two tagged ones used to land in the middle of the
table and push every slot after it up one, so dropping a single `material=` renumbered slots the
author had named. It is still reported — `PWMODEL_IMPLICIT_DEFAULT_SLOT`, and only when a
`materials` block that does not bind `Default` is present — because the geometry in it ships on the
engine default material.

`material="Default"` written on any part-level op is a slot the author **named**, so it keeps its
first-use index like any other name, even if an untagged sibling opened it first.

**First-use order is a contract when the target already exists**, because an occupied asset is
rebuilt **in place** and keeps its referencers, all of which address sections by *index* — a placed
actor's `OverrideMaterials`, a section's material assignment, an LOD section setting. Reordering the
parts renumbers every section on every placed instance, with a green compile; on the skeletal path
the engine empties the slot list first, so even `clearedFeatures` stays quiet. Read the response's
**`materialSlotList`** (`index` / `name` / `material`, in slot order) rather than the
`materialSlots` count, which is identical before and after a renumbering. It is on `model.validate`
too, so the order can be checked before the overwrite rather than dug out of the written asset
afterwards.

Slot **names** are the author's names, not `Slot0`…`SlotN`. Nothing in the engine resolves a
material by slot name, but a script that does will see them change the first time a hand-built mesh
is rebuilt from a `.pwmodel`.

Four warnings, all non-fatal:

- Geometry tags a slot that `materials` does not bind. The asset is created with an empty slot.
- `materials` binds a slot no geometry references. The asset has no such slot and the binding is
  dropped. Binding **`Default`** is not this case whenever any untagged geometry exists: that slot
  is allocated, the binding is applied, and it is not warned about.
- An untagged generator allocated **`Default`** in a document whose `materials` block does not bind
  it, so that geometry ships on the engine default material:
  `PWMODEL_IMPLICIT_DEFAULT_SLOT: Op 'box' is untagged, so it allocated the implicit slot 'Default'
  … 'Default' is placed after every slot your tags name, at index 2`. Tag the op, or bind
  `Default`. Nothing the author declared is renumbered by it.
- A bound path does not load as a `UMaterialInterface`. The slot keeps the engine's default
  material and the asset is still valid, which is why this is a warning:
  `PWMODEL_STAGE_WARNING: Material slot 'Shell' is bound to '…', which could not be loaded; using
  the default material`.

**`model.validate` resolves the bindings too**, so this last one is not a compile-only surprise. It
used to be: a document naming a path that did not exist returned **zero** diagnostics from validate
and warned only on compile, and an author iterating on a string has no reason to run a compile they
were told is unnecessary. Validate reports it anchored on the binding's own line; the compile path's
copy comes from asset creation and carries no position. Bindings for slots nothing tags are not
resolved on either path — they are dropped before creation and already have their own warning above.

## UV

```
uv channel=0 mode=box scale=(1, 1)
```

`uv` is a **part-level op** — it applies to the geometry accumulated in the part at that point.
Packing modes therefore pack only that part. For a multi-part atlas, create islands without
packing (`patch_builder auto_pack=false`), then pack once after every part has merged:

```
uv_layout channel=1 texture_resolution=64
```

`uv_layout` is model-level and may appear once per channel. It calls the standard UV packer with
world-space texel-ratio scaling, so the complete atlas is normalized without losing relative density.
If the packer cannot fit the islands, the statement fails instead of returning the unchanged layout.
`texture_resolution` defaults to 1024, accepts 2–16384 (the UV packer's supported range), and
controls island gutter, not an asset or texture size.
Distinct channels are applied in source order; a duplicate channel is `PWSRC_BAD_BLOCK`.

`Examples/pwmodel/chess_rook.pwmodel` is the worked multi-part pattern: its `body`, `crown`,
and `felt` parts each create channel-1 islands with `patch_builder auto_pack=false`, then one
model-level `uv_layout channel=1 texture_resolution=64` performs the final merged packing.

**Channels are indexed 0–7**, matching Unreal; a channel outside that range is `PWSRC_BAD_VALUE`.
Every channel present on the merged mesh carries into the `UStaticMesh` ungated.

| `mode=` | Engine call |
|---|---|
| `box` | `SetMeshUVsFromBoxProjection` |
| `planar` | `SetMeshUVsFromPlanarProjection` |
| `cylindrical` | `SetMeshUVsFromCylinderProjection` (`split_angle=`, default 45) |
| `xatlas` | `AutoGenerateXAtlasMeshUVs` (`max_iterations=`) |
| `patch_builder` | `AutoGeneratePatchBuilderMeshUVs` (segmentation: `initial_patch_count=`, `min_patch_size=`, `patch_curvature_alignment_weight=`, `patch_merging_metric_thresh=`, `patch_merging_angle_thresh=`, `respect_input_groups=`; flatten: `exp_map_normal_smoothing_rounds=`, `exp_map_normal_smoothing_alpha=`; pack: `auto_pack=`, `packing_target_image_width=`, `packing_optimize_island_rotation=`) |
| `layout` | `LayoutMeshUVs` (`layout_type=`, `texture_resolution=`, `layout_scale=`, `translation=`, `preserve_scale=`, `preserve_rotation=`, `allow_flips=`, `enable_udim_layout=`) |

**`mode=xatlas` compacts the mesh first; the other five modes never touch the id space.**
`AutoGenerateXAtlasMeshUVs` refuses a non-compact mesh outright — `TargetMesh is non-Compact,
XAtlas cannot be run` — and a part is non-compact whenever `subtract`, `trim`, `weld_vertices`,
`remove_degenerates` or `simplify_mesh` ran before the `uv` op, which is the ordinary case. There is no
`compact` op in the table, so the compiler calls `CompactMesh` itself, only when the mesh is
non-compact, immediately before the XAtlas call (`PwModelCompiler.cpp`, `ApplyUVOp`). Consequences
worth knowing: vertex and triangle **ids move** (an `edge_split edges=[…]` after an xatlas unwrap
addresses the compacted numbering, not the pre-boolean one), and the compaction itself is
deterministic, so it does not weaken the reproducibility claim below. Documents whose mesh is
already compact are byte-identical either way. Until this landed, `uv mode=xatlas` after a boolean
did nothing at all: the engine refused, the refusal went to a `nullptr` debug argument, and the
part shipped whatever an earlier stage had left on the channel — or failed
`PWMODEL_OP_FAILED` carrying `NO_UV_ELEMENTS` when the channel was new.
`Examples/pwmodel/watchtower.pwmodel` was written against that behaviour and carried two workarounds for it —
a part kept a box projection rather than an atlas, and a head was appended rather than unioned, each with a comment
asserting that the honest spelling made the unwrap silently write nothing. **Both workarounds have been removed**;
the file keeps only past-tense comments recording that they were, which is the shape to expect when reading it.

**Two engine options on these modes have no spelling here, and both are the value grammar rather
than a decision.** `FPwModelValue` carries a number, a tuple, a tuple list, a string or an
identifier and nothing deeper, so `FGeometryScriptLayoutUVsOptions::UDIMResolutions` (a
`TMap<int32, int32>` of per-tile resolutions) has no literal — `enable_udim_layout` is still
exposed and every tile then uses the single `texture_resolution`. `FGeometryScriptPatchBuilder-
Options::GroupLayer` is omitted for a different reason: it selects a *named* polygroup layer that
must already exist on the mesh, and nothing in this format creates one, so every value but the
default would select a layer that is not there.

**`layout_scale` is prefixed and `texture_resolution` is not**, which is not an inconsistency:
`FGeometryScriptLayoutUVsOptions::Scale` is a uniform post-pack scale while `uv` already publishes
`scale` as the 2D projection frame, so the two cannot share a name. Everything that does not
collide keeps the plain snake_case of the engine field. Note also that `packing_target_image_width`
(512) and `texture_resolution` (1024) are **different engine structs feeding different packers** —
matching their defaults up would be inventing one.

**There is no spherical projection in UE 5.8.** `mode=spherical` is rejected by name with
`PWSRC_BAD_VALUE` rather than falling through to a "did you mean" list, because the name is the
right one and the engine simply lacks it. `mode=layout` requires UE 5.5 or newer
(`MeshUVFunctions.h:558`; see `docs/engine-version-support.md`).

**Missing channels are filled, with one warning.** If *any* part writes a channel, every part must
end up with elements in it. Otherwise the merged mesh has elements in that channel — so the bake's
usable-UV guard sees a populated channel and does not fire — while the silent part's triangles
carry none, and the asset ships untextured with no error at all. The compiler box-projects any part
missing a channel using a deterministic bounds-framed projection, and emits **one** warning per
model naming the parts and channels it filled.

**Every populated channel is checked for real cross-part overlap after `uv_layout`.** A
positive-area triangle intersection across two source parts is
`PWMODEL_UV_OVERLAP_ACROSS_PARTS`, naming the channel and parts. It is a warning on an ordinary
texture channel and an error that fails the compile on the channel selected by `lightmap`. It anchors
to the last contributing part-level `uv` statement when one exists; when the UVs originate from
`append_buffers` and no such `uv` op exists, it has model scope and anchors to `lightmap` when that
channel is the lightmap. Overlapping UV bounding boxes alone do not count, and neither do edge or
point contacts.
The declared channel must exist and be assigned on every triangle; an absent, partial, or invalid
UV overlay is `PWMODEL_LIGHTMAP_UV_INVALID`, anchored to the model-level `lightmap` statement.

## Vertex color

`color=(r, g, b, a)` writes the mesh's **single per-corner color overlay**. Components are floats,
nominally 0–1. Unset corners default to white, which is the correct no-tint result, so a model that
never mentions `color=` needs no rule.

`color=` is for **masking and tinting, not for carrying data.** Values quantize to `FColor` (8 bits
per channel) through an sRGB→linear→sRGB pair that cancels approximately rather than exactly, with
the error worst in the darks. Do not round-trip precise values through it.

There is exactly one overlay; vertex colors are not indexed layers.

## Lightmap

```
lightmap channel=N [resolution=M]
```

Model-level and at most once. `channel` sets the asset's `LightMapCoordinateIndex` (and the matching
build setting). It is **not an op** — `UStaticMesh` has one lightmap index, so a per-part value would
have no coherent meaning, which is why it sits at model level rather than inside a part.

`resolution` is optional and sets the asset's lightmap **texture** resolution in texels per side —
`UStaticMesh::LightMapResolution` plus `FMeshBuildSettings::MinLightmapResolution`. Range **4–4096**,
the engine's own: `EnforceLightmapRestrictions` raises anything smaller back to 4 during the build
(`StaticMesh.cpp:9732`) and the `UPROPERTY` declares `ClampMax = 4096` (`StaticMesh.h:1176`). The
engine's convention is a **multiple of 4**, not a power of two (`FixedIncrement="4.0"` on the same
`UPROPERTY`; the LOD-group default is rounded with `(x + 3) & ~3`), but nothing rejects or rounds an
author-set value, so an off-step number is accepted rather than refused.

**Omit `resolution` and the asset keeps the `UStaticMesh` default of 4**, so however much work the
`uv` ops did to author the lightmap channel, it bakes at 4×4. That is legal and reported: a
`lightmap` statement with a `channel` and no `resolution` emits a `PWMODEL_STAGE_WARNING` naming the
default and the fix.

**`resolution` is not derived from `uv … mode=layout texture_resolution=`, and the two are not
wired together.** They are different concepts: `texture_resolution` is a UV *packer* hint that only
sizes the gutter left between islands and writes nothing at that size, it may be given on any
channel, and a document may run several `uv` ops with different values — while a mesh has exactly
one lightmap resolution. Auto-wiring would let whichever `uv` op ran last silently decide an asset
property, on a channel that need not even be the lightmap one. `mode=patch_builder` keeps the same
separation for its own `packing_target_image_width`.

A multi-part lightmap atlas must not be packed independently inside each part. Use
`uv_layout channel=N [texture_resolution=M]` after the part definitions. The compiler checks every
populated channel after merged layouts; a clean final atlas stays silent.

The engine clamps the stored index against the built UV count, so the compiler reads both the index
and the resolution back after the build and **warns when either does not match the request** rather
than reporting a success the asset does not carry.

## Collision

At most one `collision` block per model. It carries a `complexity` flag plus **either** explicit
elements **or** a single `auto` rule — both together is `PWMODEL_COLLISION_CONFLICT`.

Collision is model-level for the same reason as `lightmap`: `UBodySetup` is per-asset.

| Entry | Params | Maps to |
|---|---|---|
| `complexity = <flag>` | see below | `UBodySetup::CollisionTraceFlag` |
| `box` | `size=(x,y,z)`, `at=`, `rotate=` | `FKBoxElem` |
| `sphere` | `radius=`, `at=` | `FKSphereElem` |
| `capsule` | `radius=`, `height=`, `at=`, `rotate=` | `FKSphylElem` |
| `hull { <ops> }` | an inline block of geometry ops | `FKConvexElem` — **the block's result is hulled; concavity is discarded** |
| `convex points=[…]` | explicit hull vertices | `FKConvexElem`, exact |
| `auto` | `method=`, `max_hulls_per_component=`, `simplify_to=`, `detect_boxes=`, `detect_spheres=`, `detect_capsules=` (`max_hulls=` is the accepted old spelling) | Geometry Script collision generation |

Element `at=` / `rotate=` are in **mesh space** — the merged mesh, after every part transform.

**`box size=` is full extents.** `FKBoxElem::X/Y/Z` are documented as "extent of the box along the
axis" and are the full dimension, not a half-extent (`BoxElem.h:34-44`).

**`capsule height=` is total height including the caps, and is converted.** `FKSphylElem::Length`
is the cylindrical segment only — the engine's own comment reads "This is of line-segment ie. add
Radius to both ends to find total length" (`SphylElem.h:38`). So:

```
Length = max(0, height - 2 * radius)
```

A `height` below `2 * radius` cannot be represented; it clamps to `Length = 0` — a sphere of the
given radius — and warns.

### `hull` is named for what it does

`hull { … }` runs its body through the ordinary op pipeline into a transient mesh and fills one
`FKConvexElem` from that mesh's vertices. **Every concave feature is discarded**, so

```
hull { cylinder radius=20 height=60
       subtract { box size=(10, 10, 80) } }
```

silently yields a plain cylinder. The keyword warns before anyone reads this page — which is why it
is not called `convex`, the name of the thing it stores (see [Divergences](#divergences-from-engine-naming)).

Several `hull` blocks are the hand-authored convex-decomposition path: one block per convex piece.
For genuine concavity in a single element, `auto method=level_sets` reaches `FKLevelSetElem`, the
one simple-collision element that represents it.

A `hull` body producing an empty mesh, or `convex points=` with fewer than 4 points, is
`PWMODEL_DEGENERATE_HULL`.

**`convex points=[…]` is not the authoring path.** It exists only so machine-generated hulls have
somewhere to land. Do not hand-write vertex lists.

**A `hull` body may be a bare point cloud, and that is the long form of `convex points=`.** Because
the block keeps only its result's vertex positions, `hull { procedural_mesh + append_vertex … }`
with no triangles at all is legal and hulls correctly — verified against a 4-point body, which
produced one `FKConvexElem` rather than `PWMODEL_DEGENERATE_HULL` ("empty mesh" there means no
vertices, not no triangles). That is also the **only** place a bare `append_vertex` means anything:
inside a part it adds a vertex no triangle can ever reference, since no op builds a triangle from
ids. `Examples/pwmodel/mobius_band.pwmodel` writes one collision element each way, side by side.

**One hull round a closed loop is a disc with the hole filled in.** Convex collision cannot
represent a ring, so emit one `convex points=` per arc segment instead — the same model decomposes a
40-station ring into ten 36-degree slabs, each hulling the section's four corner rails sampled at
three stations.

### `complexity`

Values are snake_case of `ECollisionTraceFlag` with `CTF_` stripped, and a leading `use_` dropped
where what remains still names two representations. **`use_default` keeps its `use_`** — bare
`default` would read as this format's default rather than as the project's physics setting, which is
the opposite of what the flag means. The table is derived from the enum at runtime, not listed in
the parser.

| Value | Enum | Meaning |
|---|---|---|
| `simple_and_complex` (default) | `CTF_UseSimpleAndComplex` | Both representations built. |
| `simple_as_complex` | `CTF_UseSimpleAsComplex` | Simple shapes answer complex queries too. |
| `complex_as_simple` | `CTF_UseComplexAsSimple` | Per-poly geometry answers everything. |
| `use_default` | `CTF_UseDefault` | Resolves through the project physics setting. |

`simple_and_complex` reads like a contradiction and is not one: **both representations are built and
each answers a different query channel** — simple shapes serve simulation and ordinary queries, the
per-poly shape serves only traces that pass `bTraceComplex`.

Two warnings:

- `complex_as_simple` **at all** — a concave trimesh cannot be a moving rigid body.
- `complex_as_simple` **alongside explicit simple elements** — those elements are built and never
  queried.

### `auto`

`method=` is snake_case of `EGeometryScriptCollisionGenerationMethod`, and the accepted set is
**reflected from that enum at runtime** rather than listed in the parser: on UE 5.8 it is
`aligned_boxes`, `oriented_boxes`, `minimal_spheres`, `capsules`, `convex_hulls`, `swept_hulls`,
`min_volume_shapes`, `level_sets`. An unknown method is rejected by name, listing the valid ones
(`PWSRC_BAD_VALUE`). `level_sets` first exists on UE 5.4 (`CollisionFunctions.h:26`); on an older
engine it is absent from the vocabulary and rejected as an unknown method rather than failing at the
call.

**`max_hulls_per_component=` (default 8) is a PER-COMPONENT CEILING, not a quota.**
`ComputeCollisionFromMesh` splits its input into one submesh per connected component *before* any
decomposition runs (`CollisionFunctions.cpp:70-91`), then picks one of two generators by the budget
(`:120`). Above 1 it runs `FMeshSimpleShapeApproximation::Generate_ConvexHullDecompositions`
(`:126`, `MeshSimpleShapeApproximation.cpp:335`) with `ConvexDecompositionMaxPieces` set to the
budget; at 1 or 0 it runs `::Generate_ConvexHulls` (`:130`, `:306`), which emits exactly one hull
per submesh and never reads the budget at all.

**In the decomposition path the count is the decomposer's, not the budget's.** It is settled by
`FConvexDecomposition3::Compute(MaxPieces, NumAdditionalSplits, ErrorTolerance, MinPartThickness)`
(`MeshSimpleShapeApproximation.cpp:442-443`), where `NumAdditionalSplits = floor(MaxPieces *
ConvexDecompositionSearchFactor)` and all three tuning values stay at their struct defaults —
`SearchFactor` `.5`, `ErrorTolerance` `0`, `MinPartThickness` `0.1` (`CollisionFunctions.h:79-85`).
`.pwmodel` sets none of them. A piece that is already convex enough comes back as one hull however
much budget it is handed, so the budget buys splits only where a split reduces hull error.

**There is also a trim after the generators**, which an earlier revision of this page denied.
`bRemoveFullyContainedShapes` defaults **true** (`CollisionFunctions.h:95`) and `.pwmodel` leaves it
there, so `RemoveContainedGeometry()` runs on every multi-component mesh (`CollisionFunctions.cpp:149`)
and drops any hull that lands fully inside another. The second pass, `FilterByVolume`, is gated on
`MaxShapeCount` and never fires here (see below).

**Measured on `ships_wheel` — 11 components, `simplify_to=600`, UE 5.8, one DLL, one session:**

| `max_hulls_per_component` | 1 | 2 | 3 | 4 | 8 | 16 |
|---|---|---|---|---|---|---|
| elements produced | 11 | 11 | 13 | **44 once, then 14 five times** | 22 | 37 |

Three things to read off that row, none of them guessable from the parameter name. Budget `2` ties
budget `1` at 11, because each of the 11 pieces is already convex enough that no split is taken.
Budget `4` can exceed budget `8`, and `16` lands at 37 against a ceiling of 176 — **a larger budget
is not a larger collider, and the count is not monotonic in it.** And the budget-`4` column is one
unmodified file compiled six times against one build: **the element count is not reproducible run to
run.** This page previously reported `1` → 11, `2` → 22, `16` → 176 — the full budget on every
component. That is one outcome this generator produces, not the one it produces reliably.

**So the budget guarantees a ceiling of `budget × components` and nothing else — no floor, no
proportionality, no repeatability.** Read `collisionElements` off the compile response rather than
predicting it, and do not gate a test on an exact count above budget `1`; budget `1` is the only
stable case, because it bypasses the decomposer entirely.

`max_hulls=` is **still accepted** and does the same thing, and warns naming the rename. Supplying
both warns as well; `max_hulls_per_component` wins. Whenever the produced element count exceeds the
budget, a further warning names the budget, the element count and the mesh's component count — the
one number an author cannot derive from the document.

**Two `auto` values are clamped up, and both warn.** `simplify_to` below **4** is raised to 4 —
four triangles is the fewest that can bound a volume, so anything under it describes no solid
(`PwModelCollision.cpp`). `max_hulls_per_component` below **1** is raised to 1, because one hull per
component is the engine's floor and no arithmetic honours a budget beneath it. Both arrive as
`PWMODEL_STAGE_WARNING` naming the value asked for and the value that ran, like every other clamp in
this format. Note `simplify_to` is applied only when the merged mesh actually carries more triangles
than the target; below that it is a no-op and the clamp never fires.

**Renamed rather than reinterpreted, because the old name could not be made true.** Dividing the
figure by the component count cannot honour a budget *below* that count: one hull per component is
the engine's floor, so `max_hulls=1` on an 11-piece mesh is 11 however the number is spent. The only
real whole-asset cap is a post-pass — `MergeSimpleCollisionShapes` with `MaxShapeCount`
(`CollisionFunctions.h:577-583`) — and it **merges hulls across disjoint pieces**, so the merged
hull swallows the air between them: worse collision than the naming confusion it would fix.
`FGeometryScriptCollisionFromMeshOptions::MaxShapeCount` is not that cap either — it is gated on
`MaxShapeCount < Components.Num()` (`CollisionFunctions.cpp:152`), i.e. on the **component** count
rather than the produced count, so it fails to fire in exactly the case that needs it, and when it
does fire it discards the smallest shapes outright.

## Diagnostics

Every diagnostic carries severity, line, column, code, message, the owning part name where one
applies, and suggestions where the parser can offer them. Errors fail the compile and **create
nothing**; warnings do not.

**Warnings carry their own codes.** Match on `code`, never on message text — the message is prose
and is expected to change.

This is the whole set, ordered by pipeline stage. Only the compiler codes need a built mesh, which
is the line between the stages: a document the parser accepts is spelled correctly, so anything from
`PWMODEL_OP_FAILED` down is about geometry rather than grammar.

| Code | Severity | Raised when |
|---|---|---|
| `PWSRC_UNEXPECTED_CHARACTER` | Error | Tokenizer: a character that starts no token in the grammar. One diagnostic per offending character, at its own column. |
| `PWSRC_UNTERMINATED_STRING` | Error | Tokenizer: a string literal reached end of line or end of file before its closing quote. Strings never span lines, and a `\` before a line break does not escape it — use `\n`. |
| `PWSRC_INVALID_STRING` | Error | Tokenizer: the literal closed but its escape sequences would not decode. The message carries the decoder's reason. |
| `PWSRC_INVALID_NUMBER` | Error | Tokenizer: a numeric literal carries an exponent marker with no exponent digits (`1e`, `2E+`). The malformed run is consumed whole rather than backtracked into `1` followed by the identifier `e`, so the diagnostic names the number instead of an unexpected identifier. |
| `PWSRC_MISSING_VERSION` | Error | No `pwmodel <n>` header. The message shows the expected line. |
| `PWSRC_UNSUPPORTED_VERSION` | Error | Header names a version this build does not accept; the message lists what it does. |
| `PWMODEL_CONSTRUCT_IN_WRONG_FORMAT` | Error | A reserved `.pwmodel` signpost (`skeleton` or `animation`) belongs in `.pwskel` or `.pwanim`. The message names the target format and its documentation page. |
| `PWMODEL_SKELETON_NOT_AN_ASSET_PATH` | Error | The `use skeleton from` value is not a direct mounted Unreal asset path. |

| `PWMODEL_BOOLEAN_NO_EFFECT` | **Error** | A boolean completed and changed nothing, which is what the engine does when the operands are disjoint. It aborts the part, so nothing is created. Was a warning until it shipped twelve green examples of visibly broken models. |
| `PWMODEL_UV_CHANNEL_FILLED` | Warning **or** Error | One code, two severities, because it is one condition at two repair outcomes. The **warning** is the repaired case and the only one a document is expected to see. It is emitted **once** per model and carries up to three clauses, one per repair the compiler performed: *filled* — a part carried no elements in a UV channel another part writes, and was box-projected into it before merging; *padded* — an op appended geometry with no UVs into a channel its part was already using, and the appended geometry was box-projected at the append rather than left with unset triangles (`FCompiler::ReconcileUVChannelsForAppend`); *REPLACED* — a channel carried UVs on some triangles and none on others, which no in-place patch can repair, so the **whole channel was reprojected and the authored UVs in it were lost**. Only the third costs you something you wrote: re-author it with a `uv` op. The partial state comes from ops that add triangles in place — `bridge`, `edge_split` — since the append path now reconciles the generator route. The **error** is the unrepairable case — the channel could not be created at all. It is reported per offending part, fails the compile and creates nothing, because the merged mesh would show a populated channel to the bake's usable-UV guard while that one part's triangles shipped untextured. **No `pwmodel 0` document is known to reach the error**: it guards `SetNumUVSets`, which refuses more than 8 sets, and both routes to it are already capped below that — `uv channel=` is range-checked to 0-7, and the channel set this stage iterates is derived from channels that already exist on some part, so it can never name one above 7. Treat the error as a guard held against a future op that widens the ceiling, not as a condition to author around. |
| `PWMODEL_UV_OVERLAP_ACROSS_PARTS` | Warning, or **Error** for `lightmap` | A populated UV channel has positive-area triangle overlap between source parts after model-level `uv_layout` statements have run. Names the channel and involved parts. Ordinary texture channels warn; the channel selected by `lightmap` fails compilation. Anchors to the last contributing part-level `uv` statement when one exists; without one it has model scope and uses the `lightmap` declaration when applicable. UV AABB overlap and edge/point contact are excluded. |
| `PWMODEL_LIGHTMAP_UV_INVALID` | **Error** | The channel selected by `lightmap` is absent, is not assigned on every triangle, or has invalid overlay topology. Anchors to the model-level `lightmap` statement and fails before asset creation. |
| `PWMODEL_UNUNIONED_OVERLAP` | Warning | Two ops in one part or nested block produced geometry whose bounding boxes interpenetrate, and the second was **appended** onto the first rather than unioned with it. Siblings in a block are always appended — there is no implicit union — so the shared volume keeps its buried interior faces and the next boolean is handed a self-intersecting mesh. Use `union { }` to resolve it — a generator inside the block carries its own `material=` through the model-wide slot table, so unioning different-material geometry keeps both slots. Otherwise move them apart or keep the overlap deliberate. One diagnostic per op, not per overlapping pair. The test is bounding boxes, so it also fires on solids that do not actually overlap (petals around a ring, an L about a corner); ignore it there. Deliberately not raised for merely adjacent geometry — the overlap must have positive thickness on all three axes. **BOTH operands must enclose a volume**: a mesh with boundary edges bounds no interior, so there is no shared volume to bury faces in and `union { }` is not a legal operation on it. That is what stops nine warnings coming out of a twelve-triangle `append_triangle` patch, and it applies equally to `plane`, `disc`, `ring`, an uncapped `revolve` and any `procedural_mesh` + `append_buffers` shell. What it trades away: two overlapping open shells go unreported. They still z-fight, and only the "move them apart" half of the advice ever applied to them. **It also cannot see across an op that appends from the MODIFIER path** — `sweep`, `extrude_along_spline`, `mirror`, the three `array_*` — which append with no separable per-op footprint, and which clear the recorded boxes because a modifier may move or multiply geometry. Parts built that way are still compared **as wholes** by `PWMODEL_UNUNIONED_OVERLAP_PARTS` below. |
| `PWMODEL_UNUNIONED_OVERLAP_PARTS` | Warning | Two or more **parts** produced geometry whose bounding boxes interpenetrate. The sibling of the row above, one level up: the op-level check compares ops within one mesh (`RunOps` scopes it to a part, a boolean tool or a hull body), so parts were never compared with each other at all — and `harmonic_deform` carries one `center=` and one phase, so per-piece deformation *forces* one part per piece and the op-level check goes blind exactly where it is most wanted. Raised **once per model**, naming the pair count and the first several pairs, because interpenetrating parts are how this format builds an organic model and a per-pair warning runs to dozens on entirely correct work. A separate code and not the one above, because `union { }` is an op *inside* a part and so is **not available across parts** — the remedy is to move a part, or to merge two into one part and union there — a generator inside the block keeps its own `material=`, so the merge costs no slot. Same geometry rules as the op-level check: positive-thickness overlap on all three axes, and both parts must enclose a volume. |
| `PWMODEL_MESH_NOT_CLOSED` | Warning | The merged mesh has boundary edges: it is an open shell, not a solid. Such a mesh renders one-sided from behind and its complex collision is not solid. Warning rather than error because open is the right answer for a card, a plane or an `append_buffers` surface, and the compiler cannot tell those from a cut that broke through a wall. Gate on `health.boundaryEdges` rather than on this message — see [Mesh health](#mesh-health). |
| `PWMODEL_DEGENERATE_GEOMETRY` | Warning | The merged mesh carries near-zero-area triangles, bowtie vertices, or both. | `PWMODEL_FLOATING_COMPONENT` | Warning | The proximity graph found a component island outside the island anchored by the largest individual edge-connected component. The result reports island count and every floater's triangle count, signed volume, centre, exact nearest distance and owning part indices/names. `allow_floating=true` applies only to the named model part that carries it; the measurement remains visible and only that part's warning is suppressed. |
| `PWMODEL_SELF_INTERSECTING_SURFACE` | Warning | A single edge-connected **shell** passes through itself: a membrane spanning a solid's interior, or two walls pushed through each other. It is the one fault no other health field can express, and it walks straight through the documented gate rather than degrading it. A membrane's two axis fans are oppositely wound, so their contributions to `signedVolume` **cancel exactly** — the number that comes back is the figure the intended solid would have had, on a ring with a lid across its bore, with `isClosed: true`, `boundaryEdges: 0`, `orientationConsistent: true` and zero degenerates. A pinched sweep moves `signedVolume` **smoothly** instead, measured at 62% and 25% of its analytic volume with every other field still green, and flips sign only long after it stopped being a solid. Usual causes: a `revolve` whose profile ends sit off the axis at the *same height* (repeat the first point as the last so it is read as a closed section), a swept or twisted section thinner than the sag its own rotation puts into each ruled quad, or a displacement op whose magnitude approached the local edge length. **Counted per shell, never across shells** — appended parts and appended sibling ops interpenetrate on purpose in this format and are reported by `PWMODEL_UNUNIONED_OVERLAP_PARTS` / `PWMODEL_UNUNIONED_OVERLAP` instead; pooling them here would put this warning on a large fraction of correct documents. | `PWMODEL_EXTRUDE_FACING_OPPOSED` | Warning | A whole-mesh `extrude` whose `direction` points **against** the surface's own facing normal, which produces a slab that is inside out. The engine displaces the *original* triangles by `direction * distance` keeping their authored winding (`OffsetMeshRegion.cpp:696-705`) and reverses the stationary duplicate (`:734-744`), so outward requires `direction` parallel to the facing normal — and the facing normal is the **negation** of the right-hand rule, because `VectorUtil::Normal` returns `(V2-V0) x (V1-V0)` on a left-handed engine. Negate `direction`. Nothing downstream can catch it: the slab is closed, manifold, `boundaryEdges: 0`, and renders identically to a correct one — only `health.signedVolume` separates them. Raised for the narrow case where the sign decides the answer: `direction_mode=fixed_direction`, non-zero `distance`, no `face_direction`, an **open** accumulated mesh, and a coherent facing (area-weighted mean normal keeping at least half the total area). See [Mesh health](#mesh-health) for what each exclusion protects. |
| `PWMODEL_REVOLVE_PROFILE_REVERSED` | Warning | A `revolve` whose finished sweep encloses **negative** volume — the twin of the row above, one op over, and the same silent inversion. `profile`'s `x` is the radius and `y` is the height, and the sweep keeps the winding the point order gives it, so the section must be traversed **counter-clockwise** in that `(x, y)` plane: up the OUTER face, over the top, back down the INNER face, i.e. the enclosed material stays on the left. Reverse the point list. Nothing downstream can catch it: measured on a 16-point closed off-axis dome section at `steps=36` revolved both ways, `isClosed`, `boundaryEdges`, `degenerateTriangles`, `nonManifoldVertices`, `orientationConsistent`, `floatingCount`, `bounds` and `meshTriangleCount` were identical and only `health.signedVolume` flipped, `+1.73e9` against `-1.73e9`. Tested on the mesh the op produced rather than on the point list, so the closed-section branch, the axis-capped lathe and a `capped` partial sweep are all covered by one predicate. Two exclusions: an **open** result, where signed volume means nothing, and a negative-determinant `scale=` on the op, which reverses winding for a reason of its own and would make this warning blame the wrong parameter. Read `signedVolume` **per part** — see [Mesh health](#mesh-health). |
| `PWMODEL_MODIFIER_MATERIAL_AMBIGUOUS` | Warning | An **appending** modifier — `sweep`, `extrude_along_spline` — produced triangles whose material slot cannot be derived from the geometry it was appended onto, and the op carried no `material=` to say what it should be. Two cases, one code, distinguished in the message. **Mixed**: the geometry it extends carries more than one slot, so the op takes the slot most of those triangles are on (ties to the lower index) and names the alternatives. **Nothing to inherit**: the op was handed an empty mesh — a `procedural_mesh` that appended nothing in front of it — so the new triangles keep material ID 0, which is *not* a neutral default but whichever slot the first part in the document tagged. Write `material="<Slot>"` on the op. Raised at the call site because nothing downstream can: the op allocates no slot, so the slot count is unchanged and the mesh is valid, and the only place the choice shows is which section the new faces render in. **Not** raised for the ordinary case — a modifier appending onto geometry that carries one slot inherits it silently. |
| `PWMODEL_BOOLEAN_MATERIAL_AMBIGUOUS` | Warning | A **boolean** produced faces whose material slot cannot be derived, and the op carried no `material=` to say what it should be. The boolean twin of the row above, with the same two cases in one code. **Mixed**: the geometry the boolean was applied to carries more than one slot — so untagged block geometry, and the walls a `subtract` opens, have no single slot to inherit. The op takes the slot most of that geometry is on (ties to the lower index) and names the alternatives. **Nothing to inherit**: the boolean was applied to an empty mesh, so its faces keep material ID 0, which is whichever slot the first part in the document tagged. A separate code from the modifier one because the remedy differs: a boolean's new faces can be named on the op itself *or* on any generator inside its block, and neither spelling exists for a sweep. **Not** raised when the target speaks with one voice — the walls a cut opens in a single-material part join that material silently. |
| `PWMODEL_BOOLEAN_MATERIAL_UNUSED` | Warning | A `material=` on a boolean, or on a generator inside its block, opened a slot that no triangle of the result carries — so the tag did nothing and the asset gains an empty section. The realistic source is a tool solid the operation discards entirely — most often one that misses the target while its siblings in the block hit it, which is why `PWMODEL_BOOLEAN_NO_EFFECT` stays quiet: the boolean as a whole did change the geometry. Not `trim`, which dispatches the same engine boolean as `subtract` and so turns its tool surface into the cut face. The opposite direction to `PWMODEL_UNUSED_MATERIAL`, which reports a *binding* no tag names; only the finished mesh can see this one, which is why the compiler raises it rather than the parser. |
| `PWMODEL_EMPTY_MESH` | Error | Every part ran and the merged mesh has no triangles. |
| `PWMODEL_MESH_TOO_LARGE` | Error | The merged mesh exceeds `GEOM_MAX_TRIANGLES_PER_DYNAMIC_MESH`. |
| `PWMODEL_INVALID_GEOMETRY` | Error | A vertex position is NaN or infinite. Checked before creation because the value survives the bake and resurfaces later as a mesh with an infinite bounding box. |
| `PWMODEL_MATERIAL_ID_OUT_OF_RANGE` | Warning | A triangle carries a material ID past the end of the model-wide slot list, which only `append_buffers material_id=` can produce. Slots are padded so the asset stays valid. |
| `PWMODEL_IMPLICIT_DEFAULT_SLOT` | Warning | An untagged generator allocated the implicit `Default` slot in a document whose `materials` block does not bind it, so that geometry ships on the engine default material rather than on anything the author named. `Default` is the one slot exempt from **first-use order** — it is placed **last**, after every slot a `material=` tag names — so nothing the author declared is renumbered by it; the message still names the index it took, because a referencer binding by index has to stay off it. | `PWMODEL_COLLISION_FAILED` | Error | Collision construction failed with no more specific code of its own. |

`PWSRC_*` and `PWMODEL_*` codes travel inside diagnostics. They are **not** RPC error codes: a
call that fails outright also returns a registered `ERR_MODEL_*` code (`Handlers/ErrorCodes.h`)
through `Ctx.SendError`, with the diagnostics attached as structured content.
### Regenerating this table

`PinWright.core.pwmodel_diagnostics.DocumentedCodesMatchEmittedCodes` fails the build when this
table and the source disagree, so the reconciliation below is a diagnostic aid, not the contract.
The test compares three sets in every direction that can rot — the shared registry
(`Source/PinWright/Private/PwSource/PwDiagnostic.h`) plus the model registry
(`Source/PinWright*/Private/Model/PwModelDiagnostic.h`), the emit sites
(`Source/PinWright/Private/PwSource/*.cpp` plus `Source/PinWright*/Private/Model/*.cpp`) and this
table — and additionally rejects any `PWSRC_<NAME>` or `PWMODEL_<NAME>` named anywhere on this
page that is not registered. A typo in a paragraph therefore fails rather than sending a reader
to grep for a name that does not exist. It lives in the always-loaded main module
(`Tests/Core/TestPwModelDiagnosticCatalog.cpp`) because PinWrightGeometry is optional and gated:
hosting it beside the other `PinWright.Model.*` tests would stop the contract from running on
exactly the configurations nobody watches.
**The Severity column is not covered.** `PWMODEL_UV_CHANNEL_FILLED` is one code at two severities
by design, and the emitted severity is a call argument no source scan can attribute to a code, so a
severity that rots — `PWMODEL_BOOLEAN_NO_EFFECT` was documented `Warning` after it became an
error — is still a manual review item.

Before the test existed this table rotted once: 18 codes shipped undocumented, and
`PWSRC_UNCLOSED_BRACE`'s behaviour was described twice without the page ever naming the code, so
the catalog could not be grepped for it. To reproduce the comparison by hand:

```powershell
# From the plugin root.
$Pattern = '((PWMODEL|PWSRC)_[A-Z][A-Z0-9_]*)'
$Registry = (Select-String -Path 'Source/PinWright/Private/PwSource/PwDiagnostic.h', 'Source/PinWright*/Private/Model/PwModelDiagnostic.h' -Pattern $Pattern -AllMatches).Matches.Value | Sort-Object -Unique
$Emitted  = (Select-String -Path 'Source/PinWright/Private/PwSource/*.cpp', 'Source/PinWright*/Private/Model/*.cpp' -Pattern $Pattern -AllMatches).Matches.Value | Sort-Object -Unique
Compare-Object $Registry $Emitted   # empty: every registered code is emitted and every emitted code registered
$Registry.Count                     # must equal the number of rows above
```

A `<=` arrow from `Compare-Object` is a registered code nothing emits; a `=>` arrow is a code
emitted as a raw literal, which is the `ERR_*` mistake `PinWright.core.error_codes.AllEmittedCodesAreRegistered`
guards against on the dispatcher side. The snippet names both implementation roots for readability; the test discovers those roots
at runtime, so a second module carrying pipeline sources is covered the day it lands.


## Recommended source placement

Keep a `.pwmodel` directly beside the `.uasset` it generates, under the project's `Content/`
tree, with the same basename:

```text
Content/Characters/Hero/Meshes/SKM_Hero_Body.uasset
Content/Characters/Hero/Meshes/SKM_Hero_Body.pwmodel
```

This is a recommendation, not a migration requirement. It makes the source-to-asset mapping
obvious, makes an orphaned source or an unstamped asset visible at a glance, and turns a rename
of the asset and its source into one coherent operation. Existing projects may keep source
anywhere and continue passing an explicit `outputPath`.

Text under `Content/` is safe. Unreal's asset registry recognizes `.uasset` and `.umap`, not
`.pwmodel`, and typical Git LFS rules are extension-based rather than path-based. The source
therefore remains ordinary, diffable text unless a project has added a broader custom rule.

The placement is load-bearing when `outputPath` is omitted. A source at
`<ProjectDir>/Content/<Rel>/<Name>.pwmodel` derives exactly `/Game/<Rel>/<Name>`. Any source
outside that `Content/` tree, with the wrong extension, or producing an invalid package path is
refused with `SOURCE_OUTPUT_PATH_NOT_DERIVABLE`; the message explains why and tells the caller to
pass `outputPath='/Game/.../AssetName'`. No default path is guessed. Derivation only chooses the
target: the normal provenance and `overwrite` guard still runs, so a derived target stamped from
a different source refuses unless `overwrite=true`.

## Compiling

| Verb | Source | Writes |
|---|---|---|
| `model.compile` | `filePath` (**required**) | One asset at explicit or derived `outputPath`. |
| `model.validate` | `text` **or** `filePath` (exactly one) | Nothing. |
| `model.describe_ops` | — | Nothing. A compact index, or complete details when `op` narrows it, in the two arrays (`ops` and `paramSets`). |

`model.compile` takes `filePath`, optional `outputPath` (a single `/Game/…` **asset** path, not a
directory — one file yields one asset), `overwrite` (default `false`) and `save` (default `true`).

**`model.compile` does not accept inline `text`.** An asset compiled from an RPC payload has no
recoverable source — the exact failure this format exists to prevent, reproduced inside the tool
meant to prevent it — and it defeats the provenance stamp, since every inline compile would stamp
an empty source path and therefore match every other one. Iterate with `model.validate` on a
string; write the file when you want the asset.

`.pwmodel` files may live at **any filesystem path**, inside the project or not. There is no source
directory setting and no `/Game/` sanitizing of `filePath`. **A relative `filePath` resolves against
`FPaths::ProjectDir()`**, not against the process working directory — which for the editor is the
engine's `Binaries` folder, and is the reading no author would predict. The resolved path is what
goes into the provenance stamp, so two spellings of one file cannot produce two stamps.

### `assetClass` is omitted when the run could not determine it

`assetClass` and `skeletal` say what the run was going to write. One declaration decides it —
`use skeleton from` — so a parse that failed before reaching one has not seen it, and **both fields
are then omitted rather than defaulted**. Absent means *not determined*, exactly as it does for the
asset counts below.

Three cases, and they are deliberately distinct:

- A recovered `use skeleton from` **is** the answer, whatever else failed. The parser recovers
  rather than aborting, so a document that failed on line 40 usually still carries its declaration
  from line 2.
- A **complete** parse with no declaration is the static answer, and stays it through a later stage
  failure — nothing after the parse turns a static document into a skeletal one.
- An **incomplete** parse with no declaration knows nothing, and says so by omission.

These used to be written unconditionally off a flag that defaults to false, so every failed parse
answered `assetClass: "UStaticMesh", skeletal: false` — including for sources that plainly declare
a skeleton. A caller cannot tell that answer from a real one.

### `unboundSlots`: the slots that shipped on the default material

`unboundSlots` names every material slot the created asset left on the default surface material:
one no `materials` entry binds, and one whose binding names a path that **would not load**. The
second is the case no other field can see — it is bound in the source and unbound in the mesh, so
`materialSlotList` reports a path while that section renders grey.

**Present only on a run that created an asset.** `model.validate` resolves no bindings, and an
empty array there would assert that every slot is bound. Validate answers the same question with
diagnostics instead: `PWMODEL_UNBOUND_MATERIAL` for a slot nothing binds, and a
`PWMODEL_STAGE_WARNING` naming any binding that will not load.

### Four counts: two for the mesh, two for the asset

The response reports `meshTriangleCount` and `meshVertexCount` — per part and for the merged
whole — plus `assetTriangleCount` and `assetVertexCount` for the whole only. The pairs are
different numbers, and the `mesh*` pair is **never** the asset's.

Both `mesh*` fields are the `UDynamicMesh`'s, taken before the `UStaticMesh` bake. The bake moves
them in opposite directions:

| | What the bake does | Direction |
|---|---|---|
| Triangles | Drops every triangle with two corners inside `THRESH_POINTS_ARE_SAME` (`FMeshBuildSettings::bRemoveDegenerates`, default **true**; `StaticMeshBuilder.cpp:1666-1674`) | asset **≤** mesh |
| Vertices | Splits a position into one render vertex per distinct normal/tangent/UV/color | asset **≥** mesh |

**This table is the single normative statement of that relationship.** Every source comment that
explains the same pair cites this section by path instead of restating it — five hand-copies of one
set of numbers is what produced the drift described next, and a citation cannot drift silently.

**It deliberately carries no worked per-example pairs.** Three mesh → asset triangle pairs and three
vertex pairs stood in a fourth column here until **2026-08-29**, when they were withdrawn rather
than refreshed. Their *mesh* halves disagreed with the dated corpus table in
[`model.examples`](wiki-src/model.examples.md) — in one case by more than a factor of ten — and their
*asset* halves could not be checked at all, because `model.validate` publishes no asset count and no
`model.compile` measurement was available to replace them. Replacing one unverified number with
another would have re-created the defect.

Where to get each count instead: per-example **mesh** triangle counts, carrying the date they were
taken, are the `Tris` column of [`model.examples`](wiki-src/model.examples.md). An **asset** count has
exactly one source — run `model.compile` on the document and read `assetTriangleCount` /
`assetVertexCount` off the response. Any asset figure written into prose is a copy of one run on one
engine version and will go stale the way these did.

Both fields are named for the mesh because the honest name is the fix. Under the old names
(`vertexCount`, `triangleCount`) an author added `split_normals` — an op whose entire purpose is to
create those seams — saw a byte-identical compile response and concluded the op was a no-op; and an
author sizing a mesh against a triangle budget was reading a number the asset does not have,
against documentation that claimed `triangleCount` *was* the asset's.

**`assetTriangleCount` / `assetVertexCount` are the asset's own LOD0 counts**, read back off the
built render data. They appear only on a run that wrote an asset: `model.validate` creates nothing
to measure and omits them rather than publishing a `0` that would read as an empty mesh. Gate on
these, or on `static_mesh.describe`. There is deliberately no per-part asset count — parts merge
into one mesh before the bake, so the asset cannot attribute a triangle to a part.

**Boolean cleanup telemetry is top-level and conditional.** After a successful boolean, the
compiler welds coincident boundary edges and runs the repair layer in `DeleteOnly` mode to remove
degenerate triangles. `.pwmodel` dimensions are already Unreal centimetres (there is no
per-document unit declaration), so the cleanup length is the larger target/tool characteristic
extent multiplied by `1e-6` and clamped to `[1e-6, 1e-3]`; the triangle-area threshold is that
extent squared multiplied by `1e-9` and clamped to `[1e-12, 1e-3]`. If that boolean reaches
cleanup, `trianglesBefore` and `trianglesAfter` report the target triangle count around those
repair passes, and `sliversRemoved` reports the triangle delta from the degenerate-delete pass.
They describe the most recent boolean and are omitted when no boolean reached cleanup;
`meshTriangleCount` remains the final merged dynamic-mesh count. This targeted repair keeps
disconnected compound `subtract` tools from carrying zero-area slivers into
`health.degenerateTriangles`.

### `bounds`: the size, per part and for the whole

A run that reached the merge reports a `bounds` object — `min`, `max`, `size`, `center`, each an
`{x, y, z}` in **mesh space** — on the response and on every entry of `parts`. Per part as well as
model-wide because the model-wide box says only that *something* reaches an extreme; the per-part
box names which part does.

**It is on `model.validate` too**, and that is the point of the field rather than an incidental
consequence. Size is an acceptance criterion whenever a model replaces an existing asset in place,
fills a socket, or has to match a prefab slot — and until this field existed the only way to read
one was to `model.compile` an asset and call `static_mesh.describe` on it, which made the surface
documented as *creating nothing* unusable for the most common numeric check an author runs.

**Fitting a box is iterative, not arithmetic.** `noise_deform` displaces along the vertex normal by
up to its `magnitude`, and `harmonic_deform` scales the perpendicular radius by up to
`1 + Σ amplitude`, so the extent a primitive reaches is **not** the `radius=` its line names and
cannot be derived from the source text. Fitting means compiling, reading `bounds`, correcting, and
repeating; two or three passes converge.

`min` / `max` / `size` / `center` rather than the `origin` + `extent`
[`static_mesh.describe`](static_mesh.describe.md) publishes for the built asset: both describe the
same box, but an acceptance test is written as `bounds.min.z == -12` and `bounds.size.x <= 910`, and
halving an extent by hand to get there is where the arithmetic mistake goes. The two boxes are not
guaranteed identical — this one is the dynamic mesh's, before the bake drops degenerates.

**Absent, never zeroed**, on a run that produced no geometry: an all-zero box would read as a model
collapsed to a point rather than as "not measured", the same distinction the sentinels above carry.

### Mesh health

A run that reached the merge also reports a `health` object on the response: `isClosed`,
`boundaryEdges`, `degenerateTriangles`, `nonManifoldVertices`, `componentCount`,
`unreferencedVertices`, `signedVolume`, `orientationConsistent`, `inconsistentEdges`,
`selfIntersections`, `selfIntersectingComponents`, `selfIntersectionsTruncated`. It is measured on
the merged dynamic mesh, alongside the `mesh*` counts above and before the bake.

**Gate on these fields, never on the diagnostic text.** Two of the measurements also surface as
`PWMODEL_MESH_NOT_CLOSED` and `PWMODEL_DEGENERATE_GEOMETRY` warnings; those are what an author
reads, this object is what a caller tests. Refusing an open mesh means checking
`health.boundaryEdges == 0`, not string-matching a message.

The object is **omitted** on a run that never built a mesh — a document that failed to parse has
nothing to measure, and a `boundaryEdges` of `0` would read as "closed" rather than as "not
measured". Field meanings match `geometry.check_health`, which reports the same set from the same
`FMeshHealth` — with the one difference that the three `selfIntersection*` fields are opt-in there
(`checkSelfIntersection: true`) rather than always measured, because that verb runs per live actor
and the measurement is a different cost class. See `docs/wiki-src/geometry.md`.

**`unreferencedVertices` is the field that reconciles `meshVertexCount` with `bounds`**, which
otherwise describe the same mesh and disagree about what is in it. The box is reduced over
**triangles** (see "Bounds" above), so a vertex left referenced by nothing cannot widen it, while
`meshVertexCount` is the vertex buffer and still counts it. Both numbers are right; until this one
there was nothing naming the difference. Non-zero is also a signal in its own right — an op
removed geometry and did not clean up after itself, which is the class of fault that made the
triangle reduction necessary. **It is in no verdict**, here or in the compiler: the bake is driven
by triangles, so an orphan reaches no asset and changes nothing on disk, and failing a model on it
would refuse correct meshes. Model-wide only — there is no per-part equivalent, because the
per-part measurement runs the orientation walk and not this one. `geometry.check_health` reports
it too, from the same `FMeshHealth`.

**`signedVolume` is the only field that can see an inverted shell, and it is the only one with a
precondition: it means something only when `isClosed`.** A closed mesh whose winding is uniformly
reversed renders *identically* to a correct one — backface culling shows the camera whichever wall
faces it, and the two walls carry opposite normals — so `isClosed`, `boundaryEdges`,
`degenerateTriangles`, `nonManifoldVertices`, `componentCount` and both `mesh*` counts are
**byte-identical** between the two. An A/B luminance comparison of a render of each moves by
0.000004, a measurement that cannot fail, and it was twice quoted as proof a shipped mesh was fine.
It matters because winding — not shading — is what the offline consumers read: the mesh distance
field decides inside from outside by counting backface hits
(`MeshDistanceFieldUtilities.cpp:261-281`), so an inverted shell inverts its field and Lumen / DFAO
light the part as though the camera were inside it. **Read it as
`health.isClosed && health.signedVolume > 0`** — never `signedVolume` alone, and never as the whole
gate either: `selfIntersections` below is the third term, and it is the one this pair cannot
substitute for. On an open mesh the number is the integral of an unclosed surface and means
nothing. It is emitted anyway, next to the
`isClosed` that qualifies it, because a field that vanished on the open case would make
`signedVolume < 0` read as false for "no signal" as well as for "correct".

**`orientationConsistent` is independent of it, not a summary of it.** It counts interior edges
whose two triangles traverse the shared edge in the same direction instead of opposite ones, so it
catches a *partly* inverted surface — a nastier fault, because no single sign describes it. A
**uniform** inversion leaves every pair of neighbours agreeing, so `orientationConsistent` is `true`
on exactly the shell `signedVolume` catches. Neither substitutes for the other.
`inconsistentEdges` is the count behind the boolean.

**Both are also reported per part**, on each `parts[]` entry, as `isClosed`,
`orientationConsistent` and `signedVolume`. The model-wide number averages an inverted part away: a
correct 20-cube (`+8000`) beside an inverted 10-cube (`-1000`) sums to a healthy-looking `+7000`,
and one inverted part inside an otherwise correct model is the realistic case. The per-part entry is
the only field that names *which* part. Per-part values are measured after the part transform is
baked, so a negative-determinant `scale=` — which the transform compensates for by reversing the
winding — is reflected rather than reported against pre-transform geometry.

One legitimate negative exists: a part authored as an **inward-facing inner shell**, the hand-built
way to carve a void out of a solid it is merged with. The model-wide sum stays positive because the
void is smaller than what encloses it, and the per-part number is correctly negative — it is
describing an anti-solid on purpose. `.pwmodel` has `subtract` and `shell` for that job, so this is
rare; read a negative per-part `signedVolume` as "this part is wound inward", and decide whether
that was the intent.

The merge stage raises **no diagnostic** for a negative `signedVolume`, deliberately: at merge time
the compiler cannot say which op inverted what, and a model-level "something is inside out" with no
line number is a worse answer than a number a caller gates on. The authoring mistake that causes it
is caught at its call site instead, with a line, by `PWMODEL_EXTRUDE_FACING_OPPOSED`.

**`selfIntersections` is the field for the fault that defeats `isClosed && signedVolume > 0`
outright, rather than degrading it.** Everything above measures the surface's *connectivity* and its
*winding*. Neither can say whether the surface is the **boundary** of the region it appears to
enclose, and two ordinary shapes are not:

- **A membrane spanning a solid's interior.** Revolving a section whose two ends sit off the axis at
  the same height caps *both* ends to the axis, leaving a disc across the bore. The two fans are
  oppositely wound, so their contributions to `signedVolume` **cancel exactly** — the number that
  comes back is the figure the intended ring would have had, not an approximation of it. `isClosed`
  is `true` because the surface really is closed, `boundaryEdges` is `0`, `orientationConsistent` is
  `true`, `degenerateTriangles` and `nonManifoldVertices` are `0`, `componentCount` is `1`, and the
  triangle count of the filled form equals the triangle count of the ring that was wanted. Nothing
  else in the response moves.
- **A solid whose walls were pushed through each other.** A section swept along a rotating path sags
  at each ruled quad's centre by about `half_width * dtheta / 2`, against a budget of the section's
  *half thickness*; past that the top wall crosses the bottom one. `signedVolume` then degrades
  **smoothly** — measured at 62% and 25% of the analytic swept volume with every other field green —
  and changes sign only long after the mesh stopped being a solid. There is no threshold on it.

So **the gate is `health.isClosed && health.signedVolume > 0 && health.selfIntersections === 0`.**
`selfIntersections` counts distinct pairs of triangles whose surfaces cross or coincide; pairs that
share a vertex are excluded, because neighbours in any tessellation meet along their shared edge by
construction and a cone apex has a whole fan meeting at one point.

**It is counted per shell — per edge-connected component — and never across shells, and that
restriction is what makes it usable rather than noise.** Parts are appended, never unioned, and so
are sibling ops inside a part, so two interpenetrating lobes are two *components*. That arrangement
is how this format builds an organic model, and it already has its own two codes
(`PWMODEL_UNUNIONED_OVERLAP_PARTS`, `PWMODEL_UNUNIONED_OVERLAP`). Pooling those pairs into this
count would make it non-zero on a large fraction of correct documents, and a signal that fires on
correct work gets switched off wholesale. What stays at zero under the per-shell rule: a hollow shell
(two nested shells), a torus, two disjoint parts, an open sheet, and a lathe whose axis cap is
coplanar with — and edge-joined to — its own base face.

`selfIntersectingComponents` says how many shells are at fault; `1` narrows the search to one shell
rather than to the whole model, and it is the nearest thing to "which part" this measurement can say,
since triangle ids do not map back to source lines. `selfIntersectionsTruncated` is `true` when the
count hit its recording cap and is a **floor** rather than a total; the verdict is unaffected,
because a floor above zero is still above zero. The warning that accompanies a non-zero count is
`PWMODEL_SELF_INTERSECTING_SURFACE`, and it carries a coordinate for the first crossing found —
an interior surface is invisible in every render, so a point is the only locator there is.

**The three fields are absent, never zeroed**, on a mesh the measurement declined. It builds an AABB
tree per component, so it is skipped above a triangle budget rather than approximated; a `0` there
would read as "no crossings" instead of "not measured", which is the same cannot-fail gate this whole
block exists to remove. An absent field fails `=== 0` in every caller, which is the correct way
round. It is **not** reported per part: unlike winding, a crossing between two parts' shells is not
a fault, so a per-part number would answer a different question from the model-wide one.

### Provenance and the overwrite rule

Every generated asset carries a stamp recording the source path it was compiled from (and a hash of
that source, recorded but not yet used). The overwrite rule is derived from the stamp rather than
from a bare flag:

| Target | Behaviour |
|---|---|
| Nothing at the path | Create and stamp. |
| Stamped with the **same** source path and no out-of-band change | Rebuild freely, no flag. This is ordinary source iteration. |
| Stamped with the **same** source path but carrying changed asset state the source does not reproduce | Refuse with `PWSRC_RECOMPILE_UNMANAGED_STATE` unless `overwrite=true`. |
| Stamped with a **different** source path | Refuse unless `overwrite=true`. When current state differs from the incoming source, name it with `PWSRC_RECOMPILE_UNMANAGED_STATE`; explicit overwrite keeps that list as a warning. |
| Present but **unstamped** | Refuse unless `overwrite=true`, with the same state-loss reporting when the incoming source changes or omits current state. |
| A **different asset class** at the path | Refuse, whatever `overwrite` says — a non-StaticMesh cannot be rebuilt as one. |

**A material slot is compared by the asset it names, not by how the path is spelled.** The live
value is the object path `/Pkg.Object`; `materials` binds the package path `/Pkg`. Both are
normalized before the comparison, so a slot whose source already names the live material is not
reported as a loss — which matters because "put the state in the source" is the remedy the
diagnostic prints, and no `.pwmodel` can write the object form.

**`overwrite` is permission, not mechanism.** It answers "may this compile take over content it did
not generate?" and nothing else. The mechanism is fixed: a same-class occupant is always **rebuilt
in place** (`AssetCreatePolicy::EAction::UpdateInPlace` → `FStaticMeshAssetOptions::UsePackage`), so
`StaticAllocateObject` reconstructs the same `UStaticMesh` at the same address and every actor and
asset pointing at it keeps resolving. Nothing is deleted, so **being referenced is never a reason a
compile is refused**, and `ASSET_IN_USE` is unreachable from `model.compile`. The compile response
does not distinguish a rebuild from a create — `FStaticMeshCreateResult::bUpdatedInPlace` carries it
internally and no field publishes it — so use the provenance stamp, not the response, to tell
whether a path was already occupied.

This is the shape the format's motivating case needs. Migrating existing content — a hand-authored
or `geometry.convert_to_static_mesh` mesh, already placed in a level — is one `overwrite=true`
compile: unstamped, so permission is required; referenced, which does not matter. Passing the flag
through to the delete-then-recreate branch instead made that first compile impossible in both
directions (`docs/lessons.md`, "Two guards that each name the other as the remedy").

The source path is stored **project-relative when the source lies under the project directory, and
absolute otherwise** — an always-absolute stamp would mismatch on every second machine and train
the habit of always passing `overwrite`, which is exactly how the destructive case becomes
invisible.

**Generated assets are derived.** Hand-edits to a baked mesh — in the editor or through typed
authoring verbs — are not silently carried into later output. The provenance stamp records the
last generated semantic state. A recompile that would discard a changed material, collision
setting, socket, LOD, Nanite setting, physics asset, morph target, or other inventoried authored
state stops before rebuild. Move an expressible edit into source, or pass `overwrite=true` to
discard it deliberately; the permitted compile retains the same diagnostic as a warning.

A takeover does not trust a baseline written by another source. It compares the live asset directly
with the incoming source and names every value the takeover changes or omits. Without
`overwrite=true`, that list is part of the ownership refusal; with it, the takeover succeeds and the
list remains visible as a warning.

## Reproducibility

"The text is the durable artifact and the asset is derived" is only true if compiling one source
twice gives the same mesh. It does, on one engine version and one machine, and this section states
what that guarantee covers and where it stops. **It is a measured property, not a design intent** —
re-measure it rather than inheriting the claim.

**The compiler contributes no nondeterminism of its own.** Audited 2026-08-19 over
`Private/Model/` and every `GeometryOps_*` family the compiler dispatches to: no `FMath::Rand`,
`FRandomStream` or `rand()` on any reachable path (the module's single RNG call site is
`geometry.duplicate_along_spline`, an actor verb with no op and no op-table entry); no
`FDateTime::Now`, `FPlatformTime`, `FGuid::NewGuid` or `MakeUniqueObjectName`; no `ParallelFor`,
`Async` or task-graph work, so there is no order-sensitive float accumulation; no `TMap`/`TSet`
keyed by a pointer or `FName`, and no sort by `UObject*` or `FName::operator<` — the one `TSet`
whose order could reach geometry (the UV-channel set) is funnelled through a sorted `TArray<int32>`
first. Every `F<Verb>Params` member carries an in-class initialiser, so no op reads an
uninitialised field. All function-local statics in the path are `static const`, so **compiling A
then B is identical to compiling B then A**.

**One thing is the engine's determinism, not the format's.** `uv mode=xatlas` is reached with a
near-default options struct, so whatever guarantee it carries is an engine default this format does
not choose — see the XAtlas paragraph immediately below for why that guarantee holds anyway:

| Op | Engine call | What the format sets |
|---|---|---|
| `uv mode=xatlas` | `AutoGenerateXAtlasMeshUVs` | `max_iterations` only — the struct's only field |
| `uv mode=patch_builder` | `AutoGeneratePatchBuilderMeshUVs` | every field but `GroupLayer` |
| `uv mode=layout` | `LayoutMeshUVs` | every field but `UDIMResolutions` |
| `collision { auto }` | `GenerateCollisionFromMesh` | `method`, `max_hulls_per_component`, the three detect flags (plus `simplify_to`, which is not a field on this struct — it is a pre-pass run on a scratch copy of the merged mesh before the call, see [`auto`](#auto)) |

The `patch_builder` and `layout` rows used to read "nothing" and "`texture_resolution` only", which
was true and was the defect: both were called with a default-constructed options struct, so ten and
seven engine settings respectively had no spelling in any front-end. The two remaining omissions are
value-grammar limits and are named in the [UV](#uv) section, not settings the format declined.

**XAtlas is deterministic by construction**, not by a seed: the vendored
`GeometryProcessing/.../ThirdParty/xatlas/xatlas.cpp` has exactly four `rand()` calls, all inside
debug TGA-export blocks compiled out by `XA_DEBUG_EXPORT_ATLAS_IMAGES 0` /
`XA_DEBUG_EXPORT_BOUNDARY_GRID 0` (`:156-159`), and all four `srand`-ed from a data value
(`:3709`, `:8085`) rather than a clock. The source-reading half of that stands on its own.

**The XAtlas leg was withdrawn once and is now restored, because its precondition is met.** The
withdrawal stood while `Model.Compiler.RecompilingAnXAtlasUnwrapReproducesTheSameMesh` was measuring
a compiler that handed XAtlas a **non-compact** mesh: the engine refused the unwrap on both compiles,
so the two runs agreed about a **box projection** and nothing about chart seams was being observed.
The compiler now calls `CompactMesh` immediately before the XAtlas call (see the `mode=xatlas` note in
[UV](#uv)), and that test **passes** on a binary carrying the fix — it is the standing check, so cite
the test by name rather than any figure quoted here. The unwrap is therefore reproducible for the same
reason the other legs are, not by exception.

The paragraph this replaces quoted raw counts (2392 triangles, 1643 render vertices) from the
pre-compaction runs. Those numbers describe a box projection and must not be restored; re-measure if a
figure is wanted rather than reinstating them.

**`collision { auto }` was genuinely nondeterministic, and PinWright now corrects it.** This is
the one real defect the reproducibility audit turned up, so the mechanism is worth knowing:
`ComputeCollisionFromMesh` splits the merged mesh into connected components, and both
`FMeshSimpleShapeApproximation::Generate_ConvexHulls` and `::Generate_ConvexHullDecompositions`
run a `ParallelFor` over those components appending results under an `FCriticalSection`
(`MeshSimpleShapeApproximation.cpp:306,335`) — so the hull array is filled in **worker-completion
order**. Measured on UE 5.8: one eight-part document compiled **four** times produced **four
distinct hull orderings**, with an identical hull *set* every time.

Nothing in the counts can see this, and physics cannot either — `FKAggregateGeom` is a set to the
solver. The array order is nevertheless serialized into the `.uasset`, so the same text produced
byte-different assets, which is exactly the claim this format exists to make. Worse, that order
feeds `FSimpleShapeSet3d::RemoveContainedGeometry` (on by default whenever there is more than one
component), whose volume sort at `SimpleShapeSet3.cpp:304` is `TArray::Sort` — introsort, **not
stable** — so equal-volume hulls could in principle be *dropped* differently between runs, turning
an ordering wobble into a different hull set.

`PwModelCollision.cpp` therefore re-sorts the generated elements into a canonical order keyed on
their own geometry (hull bounds, then vertex count, then vertices; centre and radius for the
detected box/sphere/capsule shapes) before they reach the body setup. Keying on geometry rather
than on generation index is what makes it a fix: the result cannot depend on how the work was
scheduled. **`method=level_sets` is the exception** — `FKLevelSetElem` carries a dense grid with no
cheap geometric key and is left in completion order.

A single-part document never showed any of this, and that is the trap: one connected component
reduces the generator to `ParallelFor(1, ...)`, which cannot observe scheduling at all. Any future
measurement of this property has to use a **multi-part** document, which is why the standing test
fixture is eight disjoint equal-volume boxes rather than one box.

Pinned by `PinWright.Model.Compiler.RecompilingOneSourceReproducesTheSameMesh` and its two
solver-specific siblings `...RecompilingSolverOpsReproducesTheSameMesh` (multi-part collision, and
the only one that asserts hull order) and `...RecompilingAnXAtlasUnwrapReproducesTheSameMesh`, kept
apart so a regression is attributable. A noise-plus-boolean document reproduces its bounds to the
last float digit (`extent (41.83634376525879, 31.591428756713867, 22.633594512939453)`).

**`noise_deform` is deterministic and steerable, which is not the same thing.** Perlin noise here is
a spatial field: displacement is a pure function of position, `seed` and `frequency_shift`. Verified
against the engine directly — seed 0 reproduces its bounding box exactly across calls, while seeds
0, 101 and 202 give three distinct fields, and a non-zero `frequency_shift` gives a fourth. Before
`seed` was exposed the op ran at the engine default of 0 unconditionally, so a *family* of variants
generated from one recipe came out identical no matter how it was seeded; that is fixed, and
omitting `seed` still reproduces the old field exactly.

**Not guaranteed, and do not assume:**

- **Vertex and triangle ORDER.** Nothing measures it and nothing pins it. What the tests assert is
  counts, bounds, slot and collision tallies, and — for the convex hulls specifically — array
  order. Mesh element order is not in that list, so do not build a diffing or hashing workflow on
  it without measuring first.
- **`collision { auto } method=level_sets` element order.** The canonical sort covers hulls, boxes,
  spheres and capsules; `FKLevelSetElem` has no cheap geometric key and stays in the engine's
  completion order, so a multi-component level-set collision is still order-unstable between runs.
- **Across engine versions.** Every unset field in the table above is an engine default; a 5.9 that
  changes one changes the mesh, silently, with the source untouched.
- **Across machines.** Not measured, and there is a specific reason to be careful: XAtlas runs its
  own `TaskScheduler` (`xatlas.cpp:3151`), and thread count is exactly the input a single-host
  measurement cannot vary. Number literals are also parsed with `FCString::Atod`, which is
  `LC_NUMERIC`-sensitive.
- **Under memory pressure.** `union` / `subtract` / `intersection`, `array_linear`, `array_radial`,
  `array_along_path`,
  `subdivide` and `poke` each refuse at ≥90% physical memory used and fail the compile with
  `PWMODEL_OP_FAILED` carrying `ERR_MEMORY_PRESSURE`. That is ambient machine state deciding the
  outcome of a fixed source — it fails loudly rather than producing a different mesh, but it does
  mean "same source, same result" is conditional on the host.
- **When a bound material will not load.** A `materials` entry whose asset fails to load falls back
  to the default surface material and warns; the asset genuinely differs. The path is in the source,
  the resolution is not.
- **`savedToDisk`.** It reports whether the file on disk moved (mtime, size, pre-save dirty flag),
  not whether the mesh is the same. A byte-identical rewrite can report `false`. It is not a
  reproducibility signal and the tests do not compare it.
- **The update-in-place path.** Recompiling *onto an existing asset* rebuilds the occupant rather
  than constructing a fresh object, behind a provenance gate the create path never reaches. There
  is no referencer gate — being in use neither refuses the compile nor changes what is produced —
  but the rebuilt asset inherits its package, its object address and its `FAssetData` identity from
  the occupant, so "the same source yields the same asset" is measured by compiling to two fresh
  paths rather than by comparing a create against a rebuild.

## Divergences from engine naming

Engine names are kept wherever they describe the same thing. Three do not, each because the engine
name describes what it *stores* while the author needs to know what happens to their *input*:

1. **`size=(x, y, z)` instead of `width` / `height` / `depth`.** The underlying parameter struct
   holds an `FVector`; the axis mapping behind the engine's names is a documented trap
   (`geometry.create_box`'s vertical dimension is `depth`, not `height`). The RPC handler is the
   side that carries backward compatibility, not this format.
2. **`hull { … }` instead of `convex`.** `FKConvexElem`'s own header calls itself one convex hull;
   feeding it a mesh's vertices discards concavity. The keyword warns at the call site instead of
   requiring the reader to have found this page.
3. **Generator ops drop the `create_` prefix.** `geometry.create_box` is `box`. The recipe reads as
   a list of shapes rather than a list of calls, and it makes the collision block's `box` / `sphere`
   / `capsule` the same tokens as the part-level generators, disambiguated by context.

Separately, every op parameter is snake_case here and camelCase on the RPC — `height_steps` against
`heightSteps` — which is a spelling convention rather than a naming decision.

### Divergent names in diagnostics

**A diagnostic names the parameter as *this* format spells it — warnings and failures alike.** That
is not free: the clamps and refusals live in the shared geometry layer, one layer below both
front-ends, and they label with the RPC's parameter name because that is the name a `geometry.*`
caller passed and greps its response for. One label cannot serve both surfaces, so the geometry
layer keeps the RPC's and the compiler rewrites on re-emission (`PwModelWarningNames`,
`Model/PwModelParser.cpp`). Before that, a document that wrote `segments=(6, 5, 4)` was told about
`widthSegments` — a name this format does not have, which sends the author looking for a parameter
that does not exist.

**Warnings and failures are rewritten by different rules**, because a clamp label always LEADS its
message (`%s clamped from …`) while a refusal names its parameter mid-sentence. Warnings get a
strict leading-token rewrite, so a prose warning that merely contains a mapped English word is left
intact. Failures get a whole-word rewrite over the entire message: a `pipe` with
`inner_radius=30 outer_radius=10` now fails with `'pipe' failed [INVALID_PARAMS]: pipe requires
0 < inner_radius < outer_radius; got inner_radius=30, outer_radius=10`, which is the same condition
this page states under `PWMODEL_OP_FAILED` in the same spelling. It used to forward
`FOpResult::ErrorMessage` verbatim and read `0 < innerRadius < outerRadius`.

| Op | Diagnostic names | RPC names the same value |
|---|---|---|
| `box` | `size.x` / `size.y` / `size.z` | `width` / `height` / `depth` |
| `box` | `segments.x` / `segments.y` / `segments.z` | `widthSegments` / `heightSegments` / `depthSegments` |
| `plane` | `subdivisions.x` / `subdivisions.y` | `widthSubdivisions` / `depthSubdivisions` |
| `cylinder`, `cone`, `pipe` | `height_steps` | `heightSteps` |
| `capsule` | `hemisphere_steps` | `hemisphereSteps` |
| `torus` | `major_segments` / `minor_segments` | `majorSegments` / `minorSegments` |
| `arch` | `major_steps` / `minor_steps` | `majorSteps` / `minorSteps` |
| `pipe` | `radial_steps` | `radialSteps` |
| `pipe` | `inner_radius` / `outer_radius` | `innerRadius` / `outerRadius` |
| `uv` | `channel` | `uvChannel` |
| `stairs`, `spiral_stairs` | `num_steps` | `numSteps` |
| `bridge` | `edge_group_a` | `edgeGroupA` |

The last two rows exist for FAILURE text rather than for a clamp. `uv`'s is unreachable from a
parsed document — `channel` is declared 0–7 and the parser rejects anything else before the
compiler runs — and is carried so a hand-built op cannot leak the RPC spelling either.

The `.x` / `.y` / `.z` suffix is diagnostic notation, not a parameter you can write: where one
vector here is three scalars on the RPC there is no single name that is both `size` and the axis
that moved, so the warning keeps the parameter an author greps for and adds which component it was.

Every other clamp label is already the same word on both surfaces — `sphere subdivisions`,
`cylinder`/`cone`/`capsule`/`disc`/`ring` `segments`, `revolve steps`, `sweep steps`,
`spherify`/`cylindrify` `factor`, `subdivide iterations` — and is forwarded untouched.

One name is **not** a divergence but reads like one: **`sphere` is a box-sphere.** It calls
`AppendSphereBox`, so it is a rounded cube — six subdivided quad faces projected onto the sphere,
no poles, no seam, uniform quad density — with a triangle count of `12*(subdivisions-1)^2`
(measured: 2 → 12, 3 → 48, 4 → 108, 5 → 192, 16 → 2700). It is **not** `AppendSphereLatLong`: a
recipe ported from a lat/long sphere yields a different polyhedron *and* a different triangle count
at the same nominal `subdivisions`, which has already cost one authoring cycle. The primitive is
documented rather than changed, because switching it would silently alter the geometry of every
model that already uses `sphere`.

At its floor, **`radius=` is not the half-extent**. `AppendSphereBox`'s `EdgeVertices` counts
vertices per cube edge (`MeshPrimitiveFunctions.cpp:379-382`), so `subdivisions=2` leaves only the
8 cube corners, and `FBoxSphereGenerator` projects a corner to `sqrt(1/3)` per axis before scaling
by the radius (`Generators/BoxSphereGenerator.h:53,69`). The shape therefore measures
`radius/sqrt(3)` = `0.5774 * radius` on every axis — `sphere radius=100 subdivisions=2` reports a
`bounds` size of 115.5, `subdivisions=3` reports 200 — and anything placed against the nominal
radius sits outside the mesh by 42% of it. Nothing lies (`bounds` is the real, small box) and
nothing warns, because the floor is the cheap 12-triangle primitive callers ask for on purpose:
fit against the reported `bounds` at `subdivisions=2`, or use `box` when a box is what is wanted.
From `subdivisions=3` up, edge and face-centre vertices reach the radius and the box matches it.

`meshTriangleCount` / `meshVertexCount` on the compile response are likewise named for what they
are, and `assetTriangleCount` / `assetVertexCount` for what they are: see [Compiling](#compiling).

`complexity`'s values are the counter-example: they are mechanical snake_case of
`ECollisionTraceFlag` because the engine's names describe exactly what the author is choosing.

## Version policy

**`pwmodel 0` carries no compatibility promise.** The grammar may change and existing files may
need regenerating. The version bumps to `1` once real models have exercised it; from `1` on, a
breaking change bumps the integer and old parser paths are kept.

Freezing now would mean committing to support a vocabulary derived from parameter structs that no
model has been authored against. The `model` namespace ships at the `experimental` maturity tier
for the same reason.

**No migration machinery ships in version 0** — no parser version branches, no upgrade paths, no
compatibility tests. Adding them before there is anything to migrate would be maintaining a
mechanism against a hypothesis.
